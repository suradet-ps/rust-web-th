# การส่งข้อความและแพตเทิร์นแชนเนล

ถึงจุดหนึ่ง ทาสก์แบบแอซิงก์ของคุณจำเป็นต้องสื่อสารกันเอง เมื่อถึงเวลานั้น คุณมีทางเลือกพื้นฐานอยู่สองทาง: สถานะที่ใช้ร่วมกันที่ป้องกันด้วยล็อก หรือการส่งข้อความผ่านแชนเนล ทั้งสองแบบมีที่ทางของมัน แต่จากประสบการณ์ของผม แชนเนลคือค่าเริ่มต้นที่ดีกว่าสำหรับงานเว็บแอปพลิเคชันส่วนใหญ่ เพราะมันบังคับการประมวลผลแบบเรียงลำดับตามธรรมชาติ ทำให้การโอนย้ายความเป็นเจ้าของชัดเจน และทำงานเข้ากันได้ดีกับ `tokio::select!`

ในบทนี้ เราจะเดินดูพรามิทีฟแชนเนลที่ Tokio มอบให้ แพตเทิร์นที่มันเปิดทางให้ และวิธีรวมมันเข้ากับโมเดลแอ็กเตอร์/เซอร์วิสเวิร์กเกอร์ที่ผมพบว่าค้ำจุนแอปพลิเคชัน Rust แบบพร้อมกันที่มีโครงสร้างดีส่วนใหญ่

## ชนิดแชนเนลสามแบบ

Tokio มอบแชนเนลสามชนิด และแต่ละชนิดออกแบบมาสำหรับรูปทรงการสื่อสารที่ต่างกัน มาดูกันว่ามันทำอะไร และเมื่อไหร่ที่คุณควรหยิบใช้แต่ละชนิด

### mpsc: ผู้ผลิตหลายราย ผู้บริโภครายเดียว

`mpsc` คือตัวทำงานหลัก ทาสก์หลายตัวสามารถส่งข้อความเข้ามา และทาสก์หนึ่งตัวรับและประมวลผลตามลำดับ ถ้าคุณกำลังสร้างคิวคำสั่ง การกระจายงาน หรือแพตเทิร์นการประสานงานใดๆ ก็ตาม นี่น่าจะเป็นจุดที่คุณจะเริ่มต้น

```rust
use tokio::sync::mpsc;

let (tx, mut rx) = mpsc::channel::<Command>(32); // bounded, capacity 32

// Senders can be cloned and shared across tasks.
let tx2 = tx.clone();

// The receiver processes commands one at a time.
while let Some(cmd) = rx.recv().await {
    process(cmd).await;
}
```

สิ่งหนึ่งที่สำคัญจริงๆ ใน production คือการเลือกใช้แชนเนลแบบจำกัดขอบเขตหรือแบบไม่จำกัด **แชนเนลแบบจำกัด** (สร้างด้วย `mpsc::channel(capacity)`) ให้แบ็กเพรสเชอร์ตามธรรมชาติ: เมื่อแชนเนลเต็ม `send().await` จะบล็อกผู้ส่งจนกว่าผู้รับจะตามทัน สิ่งนี้ป้องกันผู้ผลิตที่เร็วเกินไปไม่ให้ท่วมผู้บริโภคที่ช้าด้วยคิวที่ยาวขึ้นเรื่อยๆ ส่วน**แชนเนลแบบไม่จำกัด** (สร้างด้วย `mpsc::unbounded_channel()`) ไม่เคยบล็อกผู้ส่ง แต่มันสามารถกินหน่วยความจำไม่จำกัดถ้าผู้รับตามไม่ทัน ผมแนะนำให้ใช้แชนเนลแบบจำกัดเป็นค่าเริ่มต้น และค่อยหยิบใช้แบบไม่จำกัดเมื่อคุณมีเหตุผลเฉพาะเจาะจงเท่านั้น

### oneshot: คำขอ-การตอบกลับแบบครั้งเดียว

คุณจะหยิบใช้ `oneshot` เมื่อต้องการคำตอบหนึ่งครั้งต่อคำขอหนึ่งครั้ง แพตเทิร์นมีหน้าตาแบบนี้: คุณสร้างแชนเนล oneshot ส่งฝั่ง `Sender` ไปพร้อมกับคำสั่งของคุณ แล้วรอ `Receiver` เพื่อรับผลลัพธ์กลับมา

```rust
use tokio::sync::oneshot;

enum Command {
    Get {
        key: String,
        reply: oneshot::Sender<Option<String>>,
    },
    Set {
        key: String,
        value: String,
    },
}

// Caller side: send a command and wait for the response.
async fn get_value(tx: &mpsc::Sender<Command>, key: String) -> Option<String> {
    let (reply_tx, reply_rx) = oneshot::channel();
    tx.send(Command::Get { key, reply: reply_tx }).await.ok()?;
    reply_rx.await.ok()?
}
```

นี่คือวิธีสร้างการสื่อสารแบบคำขอ-การตอบกลับเหนือแชนเนลคำสั่งแบบ mpsc ฝั่งผู้เรียกสร้างคู่ oneshot แนบ `Sender` เข้าไปในคำสั่ง แล้วรอ `Receiver` อีกฝั่งหนึ่ง ทาสก์ผู้ประมวลผลรับคำสั่ง ทำงานของมัน แล้วส่งผลลัพธ์กลับผ่าน oneshot ตอนแรกมันอาจดูเป็นพิธีรีตองเยอะแยะ แต่คุณจะพบว่ามันกลายเป็นเรื่องธรรมชาติอย่างรวดเร็ว

### broadcast: การกระจายหนึ่งต่อหลาย

แชนเนล `broadcast` ให้ผู้ส่งหนึ่งรายส่งทุกข้อความไปยังรีซีฟเวอร์ที่ทำงานอยู่ทั้งหมด รีซีฟเวอร์แต่ละตัวจะได้รับสำเนาของตัวเองสำหรับทุกข้อความที่ส่งมาหลังจากที่มันสมัครรับ

```rust
use tokio::sync::broadcast;

let (tx, _rx) = broadcast::channel::<Event>(100);

// Each subscriber gets a receiver by calling subscribe().
let mut rx1 = tx.subscribe();
let mut rx2 = tx.subscribe();

// Both rx1 and rx2 will receive this event.
tx.send(Event::CertificateReady { id: cert_id })?;
```

แชนเนล broadcast เหมาะมากสำหรับการกระจายอีเวนต์ สัญญาณการทำให้แคชไม่ถูกต้อง หรือการเปลี่ยนแปลงการตั้งค่าไปยังผู้บริโภคหลายราย เรื่องหนึ่งที่ต้องระวัง: ถ้ารีซีฟเวอร์รับไม่ทัน มันจะเจอข้อผิดพลาด `RecvError::Lagged(n)` ที่บอกว่ามันพลาดข้อความไปกี่ข้อความ คุณจะต้องแน่ใจว่าผู้บริโภคของคุณจัดการเคสนั้นอย่างนุ่มนวล

## แพตเทิร์นแอ็กเตอร์/เซอร์วิสเวิร์กเกอร์

มาถึงแพตเทิร์นที่ผมตื่นเต้นที่สุดกัน โมเดลแอ็กเตอร์ (หรือเซอร์วิสเวิร์กเกอร์) คือสิ่งที่สำคัญที่สุดที่แชนเนลเปิดทางให้ และเมื่อคุณเห็นมันแล้ว คุณจะเริ่มใช้มันทุกที่ แนวคิดเรียบง่าย: แอ็กเตอร์คือทาสก์ที่ครอบครองสถานะบางอย่าง รับคำสั่งผ่านแชนเนล และประมวลผลทีละอัน โค้ดภายนอกโต้ตอบกับแอ็กเตอร์ผ่าน struct ไคลเอนต์ที่ห่อฝั่งส่งของแชนเนลและมอบ API แบบแอซิงก์ที่มีชนิดข้อมูลสวยงามให้คุณ

มาดูตัวอย่างสมบูรณ์ของแอ็กเตอร์แคชธรรมดา:

```rust
use std::collections::HashMap;
use tokio::sync::{mpsc, oneshot};

// The commands the actor understands.
enum CacheCommand {
    Get {
        key: String,
        reply: oneshot::Sender<Option<String>>,
    },
    Set {
        key: String,
        value: String,
    },
    Invalidate {
        key: String,
    },
}

// The client that external code uses. It hides the channel details.
#[derive(Clone)]
pub struct CacheClient {
    sender: mpsc::Sender<CacheCommand>,
}

impl CacheClient {
    pub async fn get(&self, key: &str) -> Option<String> {
        let (tx, rx) = oneshot::channel();
        self.sender
            .send(CacheCommand::Get {
                key: key.to_string(),
                reply: tx,
            })
            .await
            .ok()?;
        rx.await.ok()?
    }

    pub async fn set(&self, key: String, value: String) {
        let _ = self
            .sender
            .send(CacheCommand::Set { key, value })
            .await;
    }

    pub async fn invalidate(&self, key: &str) {
        let _ = self
            .sender
            .send(CacheCommand::Invalidate {
                key: key.to_string(),
            })
            .await;
    }
}

// Spawn the actor and return the client.
pub fn spawn_cache(shutdown: CancellationToken) -> CacheClient {
    let (tx, rx) = mpsc::channel(64);
    tokio::spawn(run_cache_actor(rx, shutdown));
    CacheClient { sender: tx }
}

async fn run_cache_actor(
    mut commands: mpsc::Receiver<CacheCommand>,
    shutdown: CancellationToken,
) {
    let mut store: HashMap<String, String> = HashMap::new();

    loop {
        let cmd = tokio::select! {
            cmd = commands.recv() => match cmd {
                Some(c) => c,
                None => return, // All clients dropped.
            },
            _ = shutdown.cancelled() => return,
        };

        match cmd {
            CacheCommand::Get { key, reply } => {
                let _ = reply.send(store.get(&key).cloned());
            }
            CacheCommand::Set { key, value } => {
                store.insert(key, value);
            }
            CacheCommand::Invalidate { key } => {
                store.remove(&key);
            }
        }
    }
}
```

แล้วทำไมแพตเทิร์นนี้ถึงเข้ากับโค้ด production อย่างเป็นธรรมชาติขนาดนั้น ให้ผมไล่ดูว่าอะไรที่ทำให้มันทำงานได้ดีขนาดนี้

**ไม่ต้องล็อก.** HashMap ถูกครอบครองโดยทาสก์แอ็กเตอร์แต่เพียงผู้เดียว ไม่มี `Mutex` ไม่มี `RwLock` ไม่มีการแย่งชิง แชนเนล mpsc จัดการเรียงลำดับการเข้าถึงให้เราโดยธรรมชาติ

**ทนทานต่อการยกเลิก.** คำสั่งแต่ละอันถูกประมวลผลจนเสร็จก่อนวน `select!` รอบถัดไป ไม่มีความเสี่ยงที่จะดรอปฟิวเจอร์กลางการกลายพันธุ์สถานะ ซึ่งเป็นบั๊กที่ซ่อนเร้นซึ่งคอยหลอกหลอนคุณกับแนวทางอื่นๆ

**ทดสอบได้.** คุณสามารถทดสอบแอ็กเตอร์ได้โดยการสร้างแชนเนล ส่งคำสั่ง แล้วตรวจสอบผลของการตอบกลับ ไม่ต้องใช้เหตุผลเกี่ยวกับจังหวะเวลาที่ทำงานพร้อมกัน ซึ่งเป็นการชนะครั้งใหญ่

**ประกอบได้.** `CacheClient` สามารถอยู่ใน `AppState` ของคุณและถูกแยกออกมาในแฮนเดิล Axum ได้เหมือนดีเพนเดนซีที่ใช้ร่วมกันตัวอื่นๆ มันเป็น `Clone` และ `Send` ซึ่งเป็นทุกอย่างที่ Axum ต้องการ

## เมื่อไหร่ควรใช้แชนเนลเทียบกับสถานะที่ใช้ร่วมกัน

คุณอาจสงสัยว่าเมื่อไหร่ควรใช้แชนเนลแทนที่จะแค่ตี `Mutex` ลงบนสถานะของคุณ นี่คือวิธีที่ผมคิดเกี่ยวกับเรื่องนี้

แชนเนลและแพตเทิร์นแอ็กเตอร์คือเครื่องมือที่ถูกต้องเมื่อ:

- สถานะต้องการการประมวลผลแบบเรียงลำดับ (คำสั่งต้องไม่สอดแทรกกัน)
- คุณต้องการห่อหุ้มสถานะไว้หลัง API แบบแอซิงก์
- รูปแบบการเข้าถึงเกี่ยวข้องกับทั้งการอ่านและการเขียนที่ต้องประสานงานกัน
- คุณใช้ `tokio::select!` เพื่อมัลติเพล็กซ์แหล่งอีเวนต์หลายแหล่งอยู่แล้ว

สถานะที่ใช้ร่วมกัน (`Arc<RwLock<T>>`, `Arc<DashMap<K, V>>`) คือเครื่องมือที่ถูกต้องเมื่อ:

- รูปแบบการเข้าถึงส่วนใหญ่เป็นการอ่าน โดยมีการเขียนนานๆ ครั้ง
- คุณต้องการให้ทาสก์จำนวนมากอ่านพร้อมกันโดยไม่ต้องถูกเรียงลำดับ
- สถานะง่ายพอที่ล็อกไม่เพิ่มความซับซ้อนอย่างมีนัยสำคัญ
- คุณไม่ต้องประสานงานสถานะกับแหล่งอีเวนต์อื่นในลูป `select!`

อีกเรื่องหนึ่งก่อนไปต่อ: สำหรับการตั้งค่าแอปพลิเคชัน แชนเนล `watch` ก็ควรค่าแก่การรู้จักไว้เช่นกัน มันเก็บค่าเดียวที่รีซีฟเวอร์จำนวนเท่าไหร่ก็ได้สามารถสังเกตได้ และรีซีฟเวอร์จะเห็นค่าล่าสุดเสมอ สิ่งนี้มีประโยชน์มากสำหรับการตั้งค่าที่โหลดซ้ำตอนรันไทม์หรือสถานะสุขภาพที่ทาสก์จำนวนมากต้องตรวจสอบ เราจะเห็นการประสานงานแบบนี้เพิ่มเติมในบทต่อๆ ไป
