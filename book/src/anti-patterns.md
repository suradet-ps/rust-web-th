# แอนติแพตเทิร์น

ทุกโปรเจกต์เว็บ Rust ที่ผมเคยทำงานด้วยล้วนสะดุดเข้ากับความผิดพลาดชุดเดิมสองสามอย่าง บางอย่างผมทำเอง บางอย่างผมจับได้ในระหว่างการรีวิวโค้ด และอีกสองสามอย่างผมได้รับสืบทอดมาจากโค้ดเบสที่สอนบทเรียนผมอย่างเจ็บปวด บทนี้รวบรวมสิ่งที่ผมเห็นบ่อยที่สุด อธิบายว่าทำไมมันจะทำร้ายคุณ และชี้ไปยังทางเลือกที่ดีกว่าที่ครอบคลุมอยู่ในส่วนอื่นของหนังสือเล่มนี้

## SQL ในแฮนด์เลอร์

**หน้าตาเป็นแบบนี้:** ฟังก์ชันแฮนด์เลอร์ที่มีการเรียก `sqlx::query!` โดยตรง จัดการธุรกรรมและแปลงข้อผิดพลาดของฐานข้อมูลตรงนั้นในบอดี้ของแฮนด์เลอร์ HTTP

**ทำไมถึงเจ็บปวด:** มันเชื่อมเลเยอร์ HTTP ของคุณเข้ากับสกีมาของฐานข้อมูลอย่างถาวร คุณไม่สามารถทดสอบแฮนด์เลอร์ได้ถ้าไม่มีฐานข้อมูล คุณไม่สามารถนำตรรกะควิวรีไปใช้ซ้ำจากจุดเริ่มต้นอื่น (เครื่องมือ CLI, เวิร์กเกอร์เบื้องหลัง, แฮนด์เลอร์อื่น) และเมื่อควิวรีเปลี่ยน คุณต้องแก้ไฟล์ที่ควรจะเกี่ยวกับความกังวลของ HTTP

**ควรทำอย่างไรแทน:** ย้ายการเข้าถึงฐานข้อมูลเข้าไปใน struct ของรีพอสิทอรีหรือควิวรี ตามที่เราอธิบายไว้ในบท [เลเยอร์ฐานข้อมูล](./database.md) แฮนด์เลอร์จะเรียกเมธอดของเซอร์วิสหรือรีพอสิทอรีและทำงานกับชนิดข้อมูลโดเมน มันไม่เคยแตะต้อง SQL หรือชนิดข้อมูลข้อผิดพลาดเฉพาะฐานข้อมูล

**เมื่อไหร่ที่แบบนี้โอเคจริงๆ:** สำหรับเซอร์วิสขนาดเล็กที่มีรูปทรงแบบ CRUD ที่เอนด์พอยต์แต่ละตัวแมปตรงไปยังควิวรีหนึ่งหรือสองตัว และไม่มีโอกาสจริงที่จะมีจุดเริ่มต้นที่สอง SQL ในแฮนด์เลอร์ถือเป็นการลดความซับซ้อนที่สมเหตุสมผลได้ อิมพลีเมนเทชันอ้างอิง [launchbadge/realworld-axum-sqlx](https://github.com/launchbadge/realworld-axum-sqlx) เลือกแนวทางนี้โดยเจตนา และควิวรีแบบอินไลน์ของมันมีโครงสร้างที่ดีและอ่านง่าย สิ่งสำคัญคือการตัดสินใจเลือกแบบนั้นอย่างตั้งใจแทนที่จะเป็นโดยค่าเริ่มต้น และรู้ว่าเมื่อไหร่ที่แฮนด์เลอร์สะสมตรรกะควิวรีมากพอจนควรถูกแยกออกไป ถ้าคุณพบว่าตัวเองกำลังทำควิวรีซ้ำข้ามแฮนด์เลอร์ หรือถ้าแฮนด์เลอร์กำลังเรียบเรียงควิวรีหลายตัวที่ต้องสำเร็จหรือล้มเหลวพร้อมกัน นั่นคือสัญญาณให้คุณนำเลเยอร์รีพอสิทอรีหรือเซอร์วิสเข้ามา

## แฮนด์เลอร์อ้วน

**หน้าตาเป็นแบบนี้:** แฮนด์เลอร์ที่ตรวจสอบความถูกต้องของอินพุต แฮชรหัสผ่าน ควิวรีฐานข้อมูล ส่งการแจ้งเตือนทางอีเมล เผยแพร่เหตุการณ์ และสร้างการตอบกลับ HTTP ทั้งหมดในฟังก์ชันเดียว

**ทำไมถึงเจ็บปวด:** มันทำให้แฮนด์เลอร์ทดสอบแยกเดี่ยวไม่ได้ เข้าใจยาก และแก้ไขอย่างเจ็บปวด มันยังหมายความว่าการเพิ่มจุดเริ่มต้นที่สองสำหรับตรรกะทางธุรกิจเดียวกัน (เช่น เอนด์พอยต์สำหรับผู้ดูแลระบบ หรือคอนซูเมอร์ของคิวข้อความ) ต้องทำตรรกะทั้งหมดนั้นซ้ำ

**ควรทำอย่างไรแทน:** ทำให้แฮนด์เลอร์ของคุณบาง ดึงตรรกะทางธุรกิจออกไปไว้ในเมธอดของเซอร์วิสในเลเยอร์โดเมน หน้าที่ของแฮนด์เลอร์คือดึงข้อมูลจากคำขอ เรียกเมธอดของเซอร์วิส และคืนการตอบกลับ ถ้าแฮนด์เลอร์ของคุณยาวเกิน 15 ถึง 20 บรรทัด มันอาจกำลังทำมากเกินไปแล้ว

## การใช้ `unwrap()` ในเส้นทางของคำขอ

**หน้าตาเป็นแบบนี้:** การเรียก `.unwrap()` หรือ `.expect()` บน `Result` หรือ `Option` ภายในแฮนด์เลอร์หรือโค้ดใดก็ตามที่รันระหว่างการประมวลผลคำขอ

**ทำไมถึงเจ็บปวด:** panic ในแฮนด์เลอร์จะทำให้คำขอนั้นล้มด้วยข้อผิดพลาด 500 ที่มืดมัว ยิ่งแย่ไปกว่านั้น ถ้า panic เกิดขึ้นขณะถือ mutex มันจะทำให้ mutex เป็นพิษ (poison) และสามารถลุกลามไปยังคำขออื่นๆ ไคลเอนต์ไม่ได้รับข้อมูลข้อผิดพลาดที่เป็นประโยชน์ และล็อกของคุณอาจไม่จับบริบททั้งหมด

**ควรทำอย่างไรแทน:** ใช้โอเปอเรเตอร์ `?` เสมอเพื่อกระจายข้อผิดพลาดผ่านชนิดข้อมูล `Result` ถ้าคุณต้องแปลง `Option` เป็นข้อผิดพลาด ให้ใช้ `.ok_or(AppError::NotFound)?` หรืออะไรทำนองนั้น สงวน `unwrap()` ไว้สำหรับสถานการณ์ที่คุณพิสูจน์ได้ว่าค่ามีอยู่เสมอ (เช่น regex แบบฮาร์ดโค้ด) และ `expect()` ไว้สำหรับโค้ดตอนเริ่มต้นที่ค่าที่หายไปหมายความว่าแอปพลิเคชันไม่สามารถรันได้

## การปล่อยให้ชนิดข้อมูลฐานข้อมูลรั่วเข้าไปใน API

**หน้าตาเป็นแบบนี้:** การคืน struct เดียวกันจากเลเยอร์ฐานข้อมูลและแฮนด์เลอร์ HTTP หรือการ derive ทั้ง `sqlx::FromRow` และ `serde::Serialize` บนชนิดข้อมูลเดียวกันแล้วคืนมันตรงๆ เป็น `Json<UserRow>`

**ทำไมถึงเจ็บปวด:** มันหมายความว่าการเพิ่มคอลัมน์ฐานข้อมูลจะเพิ่มมันเข้าไปในการตอบกลับ API ของคุณโดยอัตโนมัติ ถ้าคอลัมน์นั้นมีข้อมูลที่ละเอียดอ่อน (แฮชรหัสผ่าน, แฟล็กภายใน, เครื่องหมายลบแบบอ่อน) ตอนนี้มันก็มองเห็นได้กับคอนซูเมอร์ API ทุกคน มันยังหมายความว่าการเปลี่ยนชื่อหรือจัดโครงสร้างคอลัมน์ฐานข้อมูลใหม่กลายเป็นการเปลี่ยนแปลง API ที่ทำลายความเข้ากันได้

**ควรทำอย่างไรแทน:** รักษาชนิดข้อมูลแยกกันสำหรับแต่ละขอบเขต ตามที่เราอธิบายไว้ในบท [การสร้างแบบจำลองโดเมน](./domain-modeling.md) `UserRow` แมปกับฐานข้อมูล `User` แทนเอนทิตีของโดเมน `UserResponse` นิยามสัญญาของ API การอิมพลีเมนต์ `From` อย่างชัดเจนจะเชื่อมช่องว่างและทำให้การแปลงตรวจสอบได้ง่าย

## การเปิดเผยข้อผิดพลาดภายในให้ไคลเอนต์เห็น

**หน้าตาเป็นแบบนี้:** การคืนข้อความข้อผิดพลาดดิบจากข้อผิดพลาดของฐานข้อมูล ข้อผิดพลาดของระบบไฟล์ หรือการเรียกเซอร์วิสภายใน ตรงๆ ในบอดี้ของการตอบกลับ HTTP

**ทำไมถึงเจ็บปวด:** ข้อความข้อผิดพลาดภายในอาจมีชื่อตารางฐานข้อมูล เส้นทางไฟล์ ควิวรี SQL เทรซสแตก และข้อมูลอื่นๆ ที่ช่วยให้ผู้โจมตีเข้าใจภายในระบบของคุณ แม้ไม่มีเจตนาร้าย ข้อความเหล่านี้ก็ทำให้คอนซูเมอร์ API สับสน เพราะมันอธิบายรายละเอียดของการนำไปใช้แทนที่จะเป็นปัญหาทางธุรกิจที่แท้จริง

**ควรทำอย่างไรแทน:** บันทึกข้อมูลรายละเอียดข้อผิดพลาดทั้งหมดฝั่งเซิร์ฟเวอร์ที่เลเวล `error` คืนข้อความแบบทั่วไปที่ผู้ใช้มองเห็นให้ไคลเอนต์ วาเรียนต์ `AppError::Internal` ที่เราอธิบายไว้ในบท [การจัดการข้อผิดพลาด](./error-handling.md) จัดการแพตเทิร์นนี้ได้อย่างสะอาด

## ความลับแบบฮาร์ดโค้ด

**หน้าตาเป็นแบบนี้:** ความลับของ JWT หรือรหัสผ่านฐานข้อมูลที่นิยามเป็นสตริงลิเทอรัลในซอร์สโค้ด หรือถูกคอมมิตเข้าระบบควบคุมเวอร์ชันในไฟล์ `.env`

**ทำไมถึงเจ็บปวด:** ใครก็ตามที่เข้าถึงซอร์สโค้ด (หรือประวัติ git) ตอนนี้ก็มีความลับสำหรับ production ของคุณ ซึ่งรวมถึงนักพัฒนาทุกคนในทีม ระบบ CI ทุกระบบที่เช็กเอาต์รีโพสิทอรี และใครก็ตามที่พบรีโพสิทอรีนี้ถ้ามันเผลอถูกเปิดเป็นสาธารณะ

**ควรทำอย่างไรแทน:** โหลดความลับจากตัวแปรสภาพแวดล้อม ตามที่เราอธิบายไว้ในบท [การตั้งค่า](./configuration.md) ใช้ `SecretString` จากครีต `secrecy` เพื่อปกป้องมันในหน่วยความจำ เพิ่ม `.env` ลงใน `.gitignore` จัดเตรียมไฟล์ `.env.example` ที่บันทึกตัวแปรที่จำเป็นไว้โดยไม่มีค่าจริง

## การอิมพอร์ตข้ามเลเยอร์

**หน้าตาเป็นแบบนี้:** โมดูลโดเมนอิมพอร์ตบางอย่างจากโมดูล `api` (เช่น ชนิดข้อมูลตัวแยกข้อมูลของ Axum) หรือจากโมดูล `infra` (เช่น `PgPool`)

**ทำไมถึงเจ็บปวด:** มันทำลายกฎของดีเพนเดนซีซึ่งเป็นรากฐานของ clean architecture ถ้าโดเมนดีเพนเดนซีบน Axum คุณจะใช้มันในเครื่องมือ CLI ไม่ได้โดยไม่ต้องลากเฟรมเวิร์ก HTTP ทั้งหมดเข้ามา ถ้ามันดีเพนเดนซีบน SQLx คุณจะทดสอบมันไม่ได้ถ้าไม่มีฐานข้อมูล

**ควรทำอย่างไรแทน:** ดีเพนเดนซีชี้เข้าหาใจกลาง เลเยอร์ API ดีเพนเดนซีบนโดเมน เลเยอร์โครงสร้างพื้นฐานดีเพนเดนซีบนโดเมน โดเมนไม่ดีเพนเดนซีบนสิ่งใดภายนอก ถ้าโดเมนต้องการความสามารถจากโลกภายนอก มันนิยามเทรต (พอร์ต) ที่เลเยอร์โครงสร้างพื้นฐานนำไปปฏิบัติ (ในฐานะอะแดปเตอร์) เราครอบคลุมเรื่องนี้อย่างละเอียดในบทสถาปัตยกรรม

## การบล็อก async runtime

**หน้าตาเป็นแบบนี้:** การเรียกฟังก์ชันที่ใช้ CPU หนัก (เช่น การแฮชรหัสผ่านด้วย Argon2), I/O ไฟล์แบบซิงโครนัส หรือการเรียกไลบรารีที่บล็อก ตรงๆ ภายในแฮนด์เลอร์แบบแอซิงก์

**ทำไมถึงเจ็บปวด:** รันไทม์ของ Tokio ใช้เธรดเวิร์กเกอร์จำนวนน้อยเพื่อรันทาสก์แอซิงก์จำนวนมากแบบร่วมมือกัน ทาสก์ที่บล็อกเธรดหนึ่งจะขัดขวางทาสก์อื่นๆ ทั้งหมดบนเธรดนั้นไม่ให้ดำเนินต่อไป เมื่อมีโหลด สิ่งนี้ก่อให้เกิดความหน่วงพุ่งสูงและการเสื่อมของปริมาณงานที่วินิจฉัยยากมาก

**ควรทำอย่างไรแทน:** ใช้ `tokio::task::spawn_blocking()` สำหรับงานที่ใช้ CPU หนักหรืองานที่บล็อก ใช้ `tokio::fs` แทน `std::fs` ตรวจสอบให้แน่ใจว่าไดรเวอร์ฐานข้อมูลของคุณเป็นแอซิงก์จริงๆ (SQLx และ diesel-async เป็น ส่วน Diesel ตัวหลักไม่เป็น)

## ค่าโดเมนที่ใช้ String เป็นชนิด

**หน้าตาเป็นแบบนี้:** การแทนอีเมล ชื่อผู้ใช้ และค่าโดเมนอื่นๆ เป็นชนิดข้อมูล `String` เปล่าๆ ตลอดทั้งแอปพลิเคชัน

**ทำไมถึงเจ็บปวด:** ฟังก์ชันที่รับ `(String, String, String)` สำหรับชื่อ อีเมล และรหัสผ่านสามารถถูกเรียกด้วยอาร์กิวเมนต์ในลำดับใดก็ได้ และคอมไพเลอร์จะไม่จับความผิดพลาดนั้น คุณยังสูญเสียความสามารถในการบังคับใช้ค่าคงที่ (เช่น "อีเมลต้องมี @") ในที่เดียว ซึ่งนำไปสู่ตรรกะการตรวจสอบความถูกต้องที่กระจัดกระจายไปทั่วโค้ดเบส

**ควรทำอย่างไรแทน:** ใช้แพตเทิร์น newtype ที่เราอธิบายไว้ในบท [การสร้างแบบจำลองโดเมน](./domain-modeling.md) นิยามชนิดข้อมูลอย่าง `Email`, `UserName` และ `UserId` ที่บังคับใช้ค่าคงที่ของมันตั้งแต่ตอนสร้างค่า ตอนแรกมันอาจดูเหมือนโบยเลอร์เพลตเพิ่มเติม แต่มันคืนทุนให้ตัวเองอย่างรวดเร็ว

## การขาด health check

**หน้าตาเป็นแบบนี้:** แอปพลิเคชันที่ถูกดีพลอยต์ไปยังออร์เคสเตรเตอร์คอนเทนเนอร์โดยไม่มีเอนด์พอยต์ตรวจสุขภาพ หรือมีลีฟเนสพรอบที่ตรวจสอบดีเพนเดนซีภายนอก

**ทำไมถึงเจ็บปวด:** หากไม่มีการตรวจสุขภาพ ออร์เคสเตรเตอร์ไม่มีทางรู้ว่าแอปพลิเคชันของคุณทำงานจริงหรือไม่ มันไม่สามารถรีสตาร์ทโพรเซสที่ค้าง หรือหยุดส่งทราฟฟิกไปยังอินสแตนซ์ที่สูญเสียการเชื่อมต่อฐานข้อมูลได้ และลีฟเนสพรอบที่ตรวจสอบฐานข้อมูลจะทำให้เกิดการรีสตาร์ทโดยไม่จำเป็นเมื่อฐานข้อมูลดับชั่วคราว ซึ่งทำให้สถานการณ์แย่ลง ไม่ได้ดีขึ้น

**ควรทำอย่างไรแทน:** อิมพลีเมนต์ลีฟเนสพรอบและเรดดิเนสพรอบแยกกัน ตามที่เราอธิบายไว้ในบท [การดีพลอยต์](./deployment.md) ลีฟเนสพรอบควรไม่มีเงื่อนไข ส่วนเรดดิเนสพรอบควรตรวจสอบดีเพนเดนซี

## การออกแบบเกินจำเป็นตั้งแต่เริ่ม

**หน้าตาเป็นแบบนี้:** โปรเจกต์ใหม่ที่มีครีตในเวิร์กสเปซสามครีต รีพอสิทอรีแบบใช้เทรตพร้อมเซอร์วิสแบบเจเนอริก แพตเทิร์น CQRS และอีเวนต์บัส ทั้งหมดสำหรับแอปพลิเคชันที่มีเอนด์พอยต์ CRUD ห้าตัว

**ทำไมถึงเจ็บปวด:** นามธรรมก่อนวัยอันควรเพิ่มความซับซ้อนที่ทำให้คุณช้าลงโดยไม่ให้ประโยชน์ที่สมดุลกัน ทุกเลเยอร์ของการอ้อมเพิ่มขึ้นคืออีกหนึ่งสิ่งที่ต้องเข้าใจ อีกหนึ่งที่ที่บั๊กซ่อนตัวได้ และอีกหนึ่งอุปสรรคต่อการเปลี่ยนแปลง จากประสบการณ์ของผม โปรเจกต์ที่ส่งมอบเร็วที่สุดคือโปรเจกต์ที่เริ่มจากง่ายและเพิ่มโครงสร้างเมื่อมันต้องการจริงๆ

**ควรทำอย่างไรแทน:** เริ่มจากโครงสร้างที่ง่ายที่สุดที่ให้การแยกอย่างสะอาด ตามที่เราอธิบายไว้ในบท [โครงสร้างโปรเจกต์](./project-structure.md) เพิ่มนามธรรมเมื่อความซับซ้อนของปัญหาต้องการมันจริงๆ ไม่ใช่เพื่อคาดการณ์ความซับซ้อนที่อาจไม่มาถึงเลย คุณสามารถรีแฟกเตอร์จากโครงสร้างแบบราบไปเป็นแบบเลเยอร์ได้เสมอเมื่อความต้องการชัดเจนขึ้น อย่ากังวลกับการทำให้สถาปัตยกรรม "สมบูรณ์แบบ" ตั้งแต่วันแรก
