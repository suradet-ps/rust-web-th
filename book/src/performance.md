# ประสิทธิภาพ

หนึ่งในข้อดีของการเลือก Rust และ Axum คือคุณได้เส้นฐานประสิทธิภาพที่แข็งแรงจริงๆ โดยไม่ต้องทำอะไรพิเศษ นามธรรมต้นทุนศูนย์ ไม่มี garbage collector และรันไทม์แอซิงก์ของ Tokio ทำงานร่วมกัน หมายความว่าแอปพลิเคชัน Axum ธรรมดาๆ ของเราสามารถรองรับการเชื่อมต่อพร้อมกันหลายพันรายการบนฮาร์ดแวร์ขนาดพอประมาณ ถึงอย่างนั้น มันก็ยังเป็นไปได้ที่เราจะทิ้งประสิทธิภาพไว้บนโต๊ะ ถ้าเราไม่ไตร่ตรองถึงวิธีใช้เครื่องมือ

ในบทนี้ เราจะเดินดูแนวปฏิบัติที่รักษาแอปพลิเคชันของเราให้เร็ว และหลุมพรางที่ผมเห็นคนสะดุดอยู่บ่อยๆ

## อย่าบล็อก async runtime

ถ้ามีกฎประสิทธิภาพข้อเดียวที่คุณจะได้จากหนังสือทั้งเล่มนี้ ให้มันเป็นข้อนี้ รันไทม์ของ Tokio ใช้พูลเธรดเพื่อรันทาสก์แบบแอซิงก์อย่างร่วมมือกัน (cooperatively) ถ้าทาสก์หนึ่งบล็อกเธรดไว้ (ทำงานที่กิน CPU, I/O แบบซิงโครนัส หรือเรียกฟังก์ชันไลบรารีที่บล็อก) เธรดนั้นจะไม่ว่างสำหรับทาสก์อื่นจนกว่างานที่บล็อกจะเสร็จ เนื่องจาก Tokio ค่าเริ่มต้นเป็นเวิร์กเกอร์เธรดหนึ่งตัวต่อหนึ่งคอร์ CPU การบล็อกแม้เพียงเธรดเดียวก็ทำให้ทรูพุตเสียหายให้เห็นได้ชัด

ส่วนที่ยุ่งยากคืออาการมันละเอียดอ่อน แอปพลิเคชันของเราจัดการโหลดระดับปานกลางได้อย่างสบาย แต่ภายใต้การทำงานพร้อมกันที่สูงขึ้น เราจะเริ่มเห็นความหน่วงพุ่งเป็นสไปก์และทรูพุตลดลง สิ่งที่เกิดขึ้นจริงคือทาสก์แอซิงก์ถูกเข้าคิวรอเธรดที่ติดอยู่กับงานซิงโครนัสบางอย่าง

ทางแก้คือย้ายงานที่บล็อกไปยังพูลเธรดเฉพาะ:

```rust
// CPU-intensive work (password hashing, image processing, etc.)
let hash = tokio::task::spawn_blocking(move || {
    hash_password(&password)
})
.await
.context("password hashing task panicked")??;
```

`spawn_blocking` รันคลอเชอร์บนพูลเธรดแบบบล็อกของ Tokio ซึ่งแยกจากเธรดเวิร์กเกอร์แอซิงก์ ขณะที่มันรอผลลัพธ์ ทาสก์แอซิงก์ของเราสละ (yield) คืน ทำให้เธรดเวิร์กเกอร์ว่างไปจัดการคำขออื่น

มีเรื่องหนึ่งที่ต้องจำไว้: `spawn_blocking` เป็นช่องทางหนี (escape hatch) ไม่ใช่ตัวจัดตารางงานคำนวณทั่วไป พูลแบบบล็อกของ Tokio ค่าเริ่มต้นสูงสุดที่ 512 เธรด ถ้าเรา spawn ทาสก์แบบบล็อกหนึ่งตัวต่อคำขอขาเข้าหนึ่งรายการในช่วงทราฟฟิกพุ่ง เราสามารถทำให้พูลอิ่มตัว และการเรียก `spawn_blocking` ทุกครั้งต่อๆ ไปก็แค่เข้าคิว สำหรับงานที่กิน CPU ภายใต้การทำงานพร้อมกันสูง ผมแนะนำให้จำกัดจำนวนทาสก์บล็อกที่ทำงานพร้อมกันด้วย `tokio::sync::Semaphore` หรือย้ายงานไปยังพูลเธรดเฉพาะอย่าง `rayon` และควรรู้ไว้อีกอย่างว่า เมื่อทาสก์แบบบล็อกเริ่มแล้ว มันไม่สามารถยกเลิกได้ ถ้าแอปพลิเคชันของเรากำลังปิดระบบ มันจะรอให้ทาสก์แบบบล็อกทั้งหมดเสร็จก่อนจึงจะออกจากโพรเซส

แหล่งที่มาทั่วไปของการบล็อกโดยไม่ตั้งใจ ได้แก่:

- **การแฮชรหัสผ่าน** ด้วย Argon2 หรือ bcrypt (กิน CPU โดยการออกแบบ)
- **I/O ไฟล์แบบซิงโครนัส** (ใช้ `tokio::fs` แทน `std::fs`)
- **การแก้ DNS** ในไคลเอนต์ HTTP บางตัว (ใช้ไคลเอนต์แบบแอซิงก์โดยกำเนิดอย่าง `reqwest`)
- **การเรียก `.lock()` บน `std::sync::Mutex`** (ใช้ `tokio::sync::Mutex` ถ้าล็อกถูกถือข้ามจุด await)

## พูลการเชื่อมต่อ

การสร้างการเชื่อมต่อฐานข้อมูลใหม่สำหรับทุกคำขอมีราคาแพง เรากำลังพูดถึง TCP handshake, การเจรจา TLS และการยืนยันตัวตน ซึ่งรวมกันแล้วบวกได้ง่ายๆ หลายสิบมิลลิวินาที พูลการเชื่อมต่อกระจายต้นทุนนั้นด้วยการรักษาชุดการเชื่อมต่อที่สร้างไว้ล่วงหน้าซึ่งคำขอของเรายืมใช้แล้วส่งคืน

`PgPool` ของ SQLx จัดการเรื่องนี้ให้เราแบบโปร่งใส สิ่งสำคัญคือปรับขนาดพูลให้เหมาะสม:

```rust
PgPoolOptions::new()
    .max_connections(10)
    .min_connections(2)
    .acquire_timeout(Duration::from_secs(3))
```

ถ้าพูลเล็กเกินไป คำขอจะเข้าคิวรอการเชื่อมต่อ ถ้าใหญ่เกินไป เราก็เปลืองหน่วยความจำบนเซิร์ฟเวอร์ฐานข้อมูลพร้อมเสี่ยงชนขีดจำกัดการเชื่อมต่อของ PostgreSQL จุดเริ่มต้นที่ดีคือ 2 ถึง 4 การเชื่อมต่อต่อหนึ่งคอร์ CPU บนเซิร์ฟเวอร์แอปพลิเคชัน จากนั้นปรับตามว่าเวลาของคำขอเราถูกใช้ในฐานข้อมูลมากเท่าไรเทียบกับงานอื่น

`acquire_timeout` คือตาข่ายนิรภัยของเรา ถ้าการเชื่อมต่อทั้งหมดถูกใช้อยู่และคำขอใหม่ไม่สามารถหาการเชื่อมต่อได้ภายในระยะเวลาที่กำหนด มันจะล้มเหลวทันทีแทนที่จะค้างอยู่อย่างไม่มีกำหนด ดีกว่าการให้คำขอนั่งในคิว 30 วินาทีก่อนหมดเวลาที่ระดับ HTTP มาก

## การบีบอัดการตอบกลับ

การบีบอัดบอดี้การตอบกลับด้วย gzip หรือ brotli สามารถลดปริมาณข้อมูลที่เราส่งผ่านเน็ตเวิร์กได้อย่างมีนัยสำคัญ โดยเฉพาะกับ API แบบ JSON ซึ่งบอดี้การตอบกลับเป็นข้อความที่บีบอัดได้ดีมาก

```rust
use tower_http::compression::CompressionLayer;

let app = Router::new()
    .merge(routes)
    .layer(CompressionLayer::new())
    .with_state(state);
```

`CompressionLayer` เจรจาอัลกอริทึมการบีบอัดกับไคลเอนต์โดยอัตโนมัติตามส่วนหัว `Accept-Encoding` สำหรับ API แบบ JSON ส่วนใหญ่ การบีบอัด gzip ลดขนาดการตอบกลับได้ 70 ถึง 90 เปอร์เซ็นต์ ซึ่งแปลว่าการตอบกลับเร็วขึ้นอย่างเห็นได้ชัดสำหรับไคลเอนต์ โดยเฉพาะบนเน็ตเวิร์กที่ช้า

## การจัดการข้อมูลอย่างมีประสิทธิภาพ

**หลีกเลี่ยงการจัดสรรที่ไม่จำเป็น** ในเส้นทางร้อน (hot path) ชอบการยืม (`&str`) มากกว่าชนิดข้อมูลแบบถือครอง (`String`) ตรงที่ทำได้ ใช้ตัววนซ้ำแทนการเก็บรวมลงเวกเตอร์กลาง สิ่งเหล่านี้เป็นการเพิ่มประสิทธิภาพเล็กน้อยทีละจุด แต่มันทบต้นเมื่อเราจัดการทราฟฟิกจำนวนมาก

**ใช้ `Arc` สำหรับข้อมูลร่วมกันที่ไม่เปลี่ยนแปลง** การตั้งค่า สแตติกแอสเซต และข้อมูลอื่นๆ ที่ไม่เปลี่ยนหลังสตาร์ตอัพควรถูกห่อด้วย `Arc` แบบนั้น การโคลน state ของแอปพลิเคชันเราจะถูก (แค่เพิ่มค่า reference count) แทนที่จะแพง (คัดลอกข้อมูลแบบเชิงลึก)

**สตรีมการตอบกลับขนาดใหญ่** สำหรับเอนด์พอยต์ที่คืนข้อมูลปริมาณมาก มาสตรีมการตอบกลับแทนการบัฟเฟอร์ทั้งหมดไว้ในหน่วยความจำ ครีต `axum-streams` รองรับการสตรีมอาร์เรย์ JSON, ไฟล์ CSV และรูปแบบอื่นๆ

## การปรับควิวรีฐานข้อมูลให้เหมาะสม

จากประสบการณ์ของผม ฐานข้อมูลเกือบจะเป็นคอขวดเสมอในเว็บแอปพลิเคชัน แนวปฏิบัติไม่กี่อย่างสร้างความแตกต่างจริงๆ ที่นี่:

**เพิ่มดัชนีให้คอลัมน์ที่คุณกรอง** ถ้าเราคิวรีผู้ใช้ด้วยอีเมล เราต้องแน่ใจว่าคอลัมน์ `email` มีดัชนี ถ้าไม่มี ฐานข้อมูลต้องสแกนทุกแถวในตารางสำหรับทุกควิวรี

**ใช้ `EXPLAIN ANALYZE` เพื่อเข้าใจแผนควิวรี** เมื่อควิวรีช้า ให้รันมันด้วย `EXPLAIN ANALYZE` ในไคลเอนต์ฐานข้อมูลของคุณเพื่อดูว่าฐานข้อมูลรันมันจริงๆ อย่างไร มองหา sequential scan บนตารางใหญ่ ซึ่งมักชี้ว่าดัชนีหายไป

**ดึงเฉพาะสิ่งที่คุณต้องการ** ถ้าแฮนด์เลอร์ต้องการแค่ชื่อและอีเมลของผู้ใช้ อย่า `SELECT *` แล้วดึงทุกคอลัมน์กลับมา การเลือกคอลัมน์เฉพาะลดปริมาณข้อมูลที่ถูกส่งและประมวลผล

**ใช้การแบ่งหน้าสำหรับเอนด์พอยต์แบบลิสต์** ตามที่เรากล่าวถึงในบท [การออกแบบ API](./api-design.md) ให้แบ่งหน้าคิวรีแบบลิสต์เสมอ `SELECT * FROM users` แบบไม่มีขอบเขตบนตารางที่มีหนึ่งล้านแถวจะทำให้แอปพลิเคชันของเราคุกเข่าลงในที่สุด

## การวัดประสิทธิภาพและการวิเคราะห์ประสิทธิภาพ

เมื่อเราจำเป็นต้องปรับให้เหมาะสม มาวัดก่อน การเดาคอขวดด้านประสิทธิภาพไม่น่าเชื่อถือ เพราะคอขวดจริงมักไม่ได้อยู่ตรงที่คุณคาด

**Criterion** คือเฟรมเวิร์กการวัดประสิทธิภาพมาตรฐานสำหรับ Rust มันให้เบนช์มาร์กที่รัดกุมเชิงสถิติพร้อมช่วงความเชื่อมั่น เราจึงบอกได้ว่าการเปลี่ยนแปลงนั้นปรับปรุงประสิทธิภาพจริงหรือแค่บังเอิญให้ผลเร็วขึ้นในการรันครั้งเดียว

**Flamegraph** แสดงภาพว่าแอปพลิเคชันของเราใช้เวลา CPU ไปที่ใด ผมพบว่ามันมีประโยชน์มากสำหรับการระบุจุดร้อนในเวิร์กโหลดที่ใกล้เคียง production

**DHAT** วิเคราะห์การจัดสรรหน่วยความจำ ซึ่งช่วยเราหาโค้ดที่จัดสรรเกินความจำเป็น

**tokio-console** คือเครื่องมือวินิจฉัยที่สร้างมาเพื่อแอปพลิเคชัน Rust แบบแอซิงก์โดยเฉพาะ มันแสดงให้เห็นว่าทาสก์ใดกำลังรัน ทาสก์ใดถูกบล็อก และรันไทม์จัดตารางงานอย่างไร นี่มีประโยชน์เป็นพิเศษสำหรับการวินิจฉัยปัญหา "รันไทม์ถูกบล็อก" ที่เราพูดถึงตอนต้นบท

## สิ่งที่ไม่ควรปรับให้เหมาะสม

ควรจำไว้ว่าการปรับให้เหมาะสมก่อนเวลาอันควร (premature optimization) คือต้นทุนจริง การไมโครออปติไมซ์แฮนด์เลอร์ที่ใช้เวลา 2 มิลลิวินาทีในขณะที่ควิวรีฐานข้อมูลข้างในใช้เวลา 50 มิลลิวินาที? นั่นคือการเสียแรงเปล่า มาพุ่งเป้าความพยายามปรับให้เหมาะสมของเราไปที่คอขวดจริง ซึ่งในเว็บแอปพลิเคชันเกือบมักเป็นควิวรีฐานข้อมูล, I/O เน็ตเวิร์ก และการบล็อก async runtime โดยไม่ตั้งใจ

เขียนโค้ดที่ชัดเจนและเป็นสำนวนก่อน แล้วโปรไฟล์ภายใต้โหลดที่สมจริง จากนั้นปรับให้เหมาะสมเฉพาะสิ่งที่โปรไฟเลอร์บอกว่าช้า จากประสบการณ์ของผม วิธีนี้ให้แอปพลิเคชันที่ทั้งเร็วและบำรุงรักษาได้อย่างน่าเชื่อถือ และนั่นคือสิ่งที่เราจะต้องใช้เมื่อเราดูวิธีรักษาแอปพลิเคชันของเราให้สังเกตการณ์ได้ในบทถัดไป
