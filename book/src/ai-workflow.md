# เวิร์กโฟลว์การพัฒนาร่วมกับ AI

ถ้าคุณเคยสร้างงานด้วยเอเจนต์เขียนโค้ด AI คุณอาจสังเกตเห็นว่าพวกมันเก่งเรื่องพ่นโค้ดออกมา แต่แย่มากเรื่องการรู้กฎ *ของ* โปรเจกต์คุณ บทนี้เกี่ยวกับการเชื่อมช่องว่างนั้น เราจะมาดูวิธีนำหลักการจากคู่มือนี้ไปเปลี่ยนเป็นคำสั่งระดับรีโพสิทอรีที่เอเจนต์ AI (Claude Code, Codex, Cursor, Aider) ใช้ได้อย่างมีประสิทธิภาพ เพื่อให้พวกมันเลิกเดาและเริ่มทำตามสถาปัตยกรรมของคุณ

## ปัญหาของการวางคู่มือทั้งเล่มลงไป

ผมเข้าใจนะ แรงดึงดูดใจมันมีจริง คุณคัดลอกคู่มือทั้งเล่ม วางลงในแชท แล้วขอให้เอเจนต์ "สร้างแอป Rust" ผมก็เคยทำแบบนั้น ผลลัพธ์คือ... ไม่ค่อยดีเท่าไหร่ โมเดลแยกไม่ออกว่าอะไรคือกฎตายตัว อะไรคือข้อเสนอแนะดีๆ ให้เลือกใช้ มันก็เลยเลือกชิ้นที่ดูง่ายที่สุดแล้วเพิกเฉยส่วนที่เหลือ

สิ่งที่ผมพบว่าทำงานได้ดีกว่ามากคือการกลั่นกฎที่ยอมไม่ได้ของคุณลงในไฟล์ถาวรในรีโพสิทอรีที่เอเจนต์โหลดอัตโนมัติเมื่อเริ่มเซสชันทุกครั้ง จากนั้นคุณก็มอบความรู้เชิงขั้นตอน (วิธีเพิ่มเอนด์พอยต์ วิธีเขียนไมเกรชัน) ในรูปแบบสกิลเฉพาะที่เอเจนต์จะเรียกใช้เมื่อมันต้องการ มาดูวิธีตั้งค่าสิ่งนี้กัน

## โครงสร้างไฟล์คำสั่งในรีโพสิทอรี

เครื่องมือเขียนโค้ด AI ส่วนใหญ่ในปัจจุบันรองรับคำสั่งแบบไฟล์ถาวรที่ถูกโหลดอัตโนมัติเมื่อเอเจนต์เริ่มเซสชัน:

- **Claude Code** อ่าน `CLAUDE.md` ที่รากของรีโพสิทอรี รวมถึง `.claude/rules/` สำหรับกฎที่จำกัดขอบเขต
- **Codex** อ่าน `AGENTS.md` ที่รากของรีโพสิทอรี รวมถึงไฟล์ `AGENTS.md` ที่ซ้อนอยู่ในซับไดเรกทอรี
- **Cursor** อ่าน `.cursor/rules/` หรือ `AGENTS.md`
- **Aider** ใช้ repo map เพื่อทำความเข้าใจโครงสร้าง และสามารถให้ไฟล์ข้อตกลง (conventions) ได้

ชื่อไฟล์ต่างกัน แต่แนวคิดเหมือนกัน: คำสั่งที่สั้น เจาะจง และยั่งยืนที่อาศัยอยู่ในรีโพสิทอรีและถูกโหลดเมื่อเริ่มเซสชันทุกครั้ง นั่นคือที่อยู่ของกฎของคุณที่ดีกว่าข้อความในแชทที่คุณจะลืมวางในครั้งหน้า

รีโพสิทอรีนี้มีไดเรกทอรี `templates/` ที่มาพร้อมไฟล์คำสั่งพร้อมใช้ คุณสามารถคัดลอกมันลงในโปรเจกต์ของคุณและปรับให้เข้ากับโค้ดเบสของคุณได้

## คำสั่งระดับราก

`AGENTS.md` (หรือ `CLAUDE.md`) ระดับรากของคุณควรมีเพียงกฎที่ใช้กับทุกเซสชันและทุกไฟล์เท่านั้น ผมแนะนำให้เก็บให้ต่ำกว่า 40 บรรทัด ลองมองมันเป็นสิ่งที่คุณจะบอกสมาชิกทีมใหม่ในวันแรก:

- โครงสร้างเลเยอร์ของโปรเจกต์และกฎของดีเพนเดนซี
- กฎสไตล์โค้ดแบบตายตัว (ห้าม unwrap ในแฮนด์เลอร์, ใช้ newtype สำหรับค่าโดเมน, ฯลฯ)
- คำสั่งตรวจสอบความถูกต้องที่นิยามคำว่า "เสร็จ"
- ตัวชี้ไปยังไฟล์คำสั่งที่ซ้อนกันสำหรับกฎเฉพาะเลเยอร์

```
templates/
  AGENTS.md                          # Root rules (copy to your repo root)
```

จงเก็บไฟล์นี้ให้เล็กโดยตั้งใจ ทุกอย่างที่ใช้เฉพาะกับเลเยอร์ใดเลเยอร์หนึ่งจะไปอยู่ในไฟล์ที่ซ้อนกัน ซึ่งเราจะดูกันต่อไป

## คำสั่งระดับเลเยอร์ย่อย

แต่ละเลเยอร์ของสถาปัตยกรรมมีไฟล์คำสั่งของตัวเองพร้อมกฎเฉพาะสำหรับเลเยอร์นั้น วิธีนี้ทำให้เอเจนต์โหลดเฉพาะคำแนะนำที่เกี่ยวข้องเมื่อมันกำลังแก้ไฟล์ในไดเรกทอรีนั้น ไม่ต้องเอากฎฐานข้อมูลไปยัดเยียดใส่เมื่อมันกำลังทำงานกับแฮนด์เลอร์

```
templates/
  src/http/AGENTS.md                 # Handler, DTO, middleware, routing rules
  src/domain/AGENTS.md               # Model, service, port, error rules
  src/infra/db/AGENTS.md             # Repository, query, migration rules
```

คำสั่งของเลเยอร์ HTTP ครอบคลุมขีดจำกัดความยาวของแฮนด์เลอร์ ข้อตกลงเกี่ยวกับตัวแยกข้อมูล (extractor) ลำดับของมิดเดิลแวร์ และกฎของ DTO คำสั่งของเลเยอร์โดเมนบังคับใช้กฎปลอดดีเพนเดนซีจากเฟรมเวิร์ก (zero-framework-dependency) และแพตเทิร์น newtype/คอนสตรักเตอร์ที่เราคุยกันไปก่อนหน้านี้ คำสั่งของเลเยอร์ฐานข้อมูลครอบคลุมแพตเทิร์นควิวรี การแมปแถวสู่โดเมน และข้อตกลงเกี่ยวกับไมเกรชัน

## สกิลสำหรับเวิร์กโฟลว์แบบขั้นตอน

กฎบอกเอเจนต์ว่าต้องทำอะไร สกิลบอกมันว่า *ทำอย่างไร* คุณอาจสงสัยว่าทำไมความแตกต่างนี้ถึงสำคัญ จากประสบการณ์ของผม เอเจนต์เก่งอย่างน่าประหลาดใจในการทำตามขั้นตอนทีละขั้น แต่แย่มากในการคิดค้นขั้นตอนขึ้นมาจากศูนย์ สกิลโดยพื้นฐานแล้วคือสูตรสำเร็จสำหรับงานทั่วไปที่เอเจนต์สามารถทำตามได้เมื่อมันต้องการ

```
templates/
  .agents/skills/add-endpoint/SKILL.md    # Domain -> DB -> Handler -> Test flow
  .agents/skills/add-migration/SKILL.md   # Migration creation and verification
  .agents/skills/review-pr/SKILL.md       # Architecture and security review checklist
```

สกิล add-endpoint พาคุณผ่านเวอร์ติคอลสไลซ์ทั้งเส้นของเรา: นิยามชนิดข้อมูลโดเมน สร้างไมเกรชัน อิมพลีเมนต์เมธอดของรีพอสิทอรี เพิ่มตรรกะของเซอร์วิส เขียน DTO และแฮนด์เลอร์ ลงทะเบียนเส้นทาง เขียนเทสต์ เพิ่ม tracing แล้วรันการตรวจสอบความถูกต้อง นี่คือขั้นตอนที่เราอยากให้เอเจนต์ทำตามทุกครั้งที่มันเพิ่มเอนด์พอยต์ API ใหม่ และมันสะท้อนวิธีที่เราจะทำด้วยตัวเองทุกประการ

สกิล review-pr คือเช็กลิสต์ที่ครอบคลุมสถาปัตยกรรม (ทิศทางของดีเพนเดนซี, ความหนาของแฮนด์เลอร์) ความถูกต้อง (ห้าม unwrap, การแปลงข้อผิดพลาดที่เหมาะสม) ฐานข้อมูล (ควิวรีแบบมีพารามิเตอร์, การแปลงด้วย TryFrom) ความปลอดภัย (การตรวจสอบความถูกต้องของอินพุต, ห้ามมีความลับในล็อก) การทดสอบ (happy path และ error path) และการปฏิบัติการ (tracing, ห้ามบล็อก, การหมดเวลาแบบขาออก)

## เช็กลิสต์สำหรับการตรวจทานโดยมนุษย์

แม้ว่าเอเจนต์ AI จะเป็นคนเขียนโค้ด คุณก็ยังต้องการมนุษย์คอยตรวจทานอยู่ดี อย่าข้ามส่วนนี้ไป เช็กลิสต์ฟีเจอร์จะให้เส้นทางที่มีโครงสร้างผ่านการตรวจทานนั้น:

```
templates/
  docs/checklists/feature.md              # End-to-end feature implementation checklist
```

## ลูปการสนทนาสามเฟส

นี่คือเวิร์กโฟลว์ที่ผมลงตัวด้วยหลังลองผิดลองถูกมาหลายครั้ง มันคือลูปสามเฟส และมันได้ผลเพราะมันบังคับให้เอเจนต์คิดตามลำดับเดียวกับที่เราคิด: ขอบเขตก่อน แล้วการนำไปใช้ แล้วการตรวจทาน

**เฟส 1: วางแผน (Plan).** ขอให้เอเจนต์อ่านไฟล์คำสั่ง สรุปข้อจำกัดทางสถาปัตยกรรมที่เกี่ยวข้อง เสนอเวอร์ติคอลสไลซ์ที่เล็กที่สุดที่จะนำไปใช้ และระบุรายการไฟล์ที่มันวางแผนจะแก้ อย่าให้มันเขียนโค้ดในตอนนี้ มันอาจดูน่าเบื่อ แต่ขั้นตอนนี้ดักจับสมมติฐานที่ผิดก่อนที่มันจะกลายเป็นโค้ดที่ผิด

**เฟส 2: นำไปใช้ (Implement).** เอเจนต์นำไปใช้ครั้งละหนึ่งสไลซ์ มันหยุดเมื่อโค้ดคอมไพล์ผ่านและเทสต์ผ่าน แล้วจึงแสดงให้คุณเห็นว่าอะไรเปลี่ยนไปและเหลืออะไรอยู่

**เฟส 3: ตรวจทาน (Review).** เอเจนต์ตรวจทาน diff ของตัวเองเทียบกับเช็กลิสต์การตรวจทาน มันชี้ให้เห็นความเบี่ยงเบนทางสถาปัตยกรรม ชนิดข้อมูลที่รั่วไหล เทสต์ที่ขาดหาย การเรียกที่บล็อก และปัญหาด้านความปลอดภัย มันเสนอการแก้ไขเพียงเล็กน้อย

คุณจะแปลกใจว่าผลลัพธ์ดีขึ้นมากแค่ไหนเมื่อเทียบกับพรอมพ์ปลายเปิดเพียงอันเดียว ข้อจำกัดของการทำงานเป็นเฟสทำให้เอเจนต์ไม่หลุดกรอบไปสร้างสิ่งที่คอมไพล์ผ่านแต่ฝ่าฝืนกฎสถาปัตยกรรมของคุณไปครึ่งเล่ม

## อัปเกรดการแก้ไขให้เป็นความทรงจำของรีโพสิทอรี

เมื่อเอเจนต์ทำผิดแบบเดิมซ้ำสอง และมันจะทำแน่นอน (ปล่อยให้ชนิดข้อมูลฐานข้อมูลรั่วเข้าไปใน API ใส่ SQL ลงในแฮนด์เลอร์ ลืมติดตั้งเครื่องมือ tracing) อย่าแค่แก้มันในแชท ให้ไปอัปเดตไฟล์คำสั่งระดับรากหรือระดับที่ซ้อนกัน เซสชันถัดไปจะเริ่มต้นอย่างฉลาดขึ้นเพราะการแก้ไขนั้นเป็นส่วนหนึ่งของบริบทถาวรของโปรเจกต์แล้ว

นี่คือที่มาของมูลค่าทบต้นที่แท้จริง เมื่อเวลาผ่านไป ไฟล์คำสั่งของคุณจะพัฒนากลายเป็นการเข้ารหัสมาตรฐานของทีมที่แม่นยำและผ่านการพิสูจน์จริง สิ่งที่ผมพบคือหลังจากผ่านไปไม่กี่สัปดาห์ ทั้งมนุษย์และเอเจนต์จะทำตามกฎชุดเดียวกันอย่างสม่ำเสมอ ซึ่งก็คือประเด็นทั้งหมดนั่นแหละ

## เริ่มต้นใช้งาน

1. คัดลอกเนื้อหาของไดเรกทอรี `templates/` ลงในโปรเจกต์ Rust ของคุณ
2. เปลี่ยนชื่อ `AGENTS.md` เป็น `CLAUDE.md` ถ้าคุณใช้ Claude Code (หรือเก็บไว้ทั้งสองก็ได้ มันไม่ขัดแย้งกัน)
3. ปรับกฎให้เข้ากับโปรเจกต์เฉพาะของคุณ ปรับเส้นทางของเลเยอร์และเพิ่มข้อตกลงเฉพาะโปรเจกต์ใดก็ตามที่คุณมี
4. ย้ายไฟล์คำสั่งที่ซ้อนกันให้ตรงกับโครงสร้างไดเรกทอรี `src/` จริงของคุณ
5. เริ่มเซสชันแชทและขอให้เอเจนต์อ่านไฟล์คำสั่งของมันก่อนเริ่มทำงานใดๆ

ขั้นตอนสุดท้ายสำคัญมาก ถ้าคุณไม่ขอให้เอเจนต์อ่านคำสั่งของมันก่อน มันก็จะเพิกเฉยอย่างมีความสุขและทำอะไรก็ตามที่มันอยากทำ เมื่อคุณทำให้เวิร์กโฟลว์นี้ทำงานได้แล้ว คุณจะพบว่าเอเจนต์กลายเป็นผู้ร่วมงานที่มีประโยชน์อย่างแท้จริง แทนที่จะเป็นเครื่องกำเนิดโค้ดที่ต้องคอยดูแล
