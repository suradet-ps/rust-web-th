# การดีพลอยต์ (Deployment)

เราสร้างเว็บเซอร์วิสของเรา ทดสอบแล้ว และมันรันได้ดีบนแล็ปท็อป แล้วไงต่อ? การนำมันขึ้น production เกี่ยวข้องกับบางอย่างที่เราต้องทำให้ถูกต้อง: การสร้างอิมเมจคอนเทนเนอร์ที่เล็ก การปิดระบบอย่างนุ่มนวลเพื่อไม่ให้ทิ้งคำขอที่ยังค้างอยู่ และการให้เอนด์พอยต์การตรวจสุขภาพกับออร์เคสเตรเตอร์ของเราเพื่อให้มันรู้ว่าเกิดอะไรขึ้นกับแอปของเรา มาดูกันทีละอย่าง

## Docker และบิลด์แบบหลายสเตจ

ถ้าคุณคอมไพล์ Rust สำหรับ GNU Linux target เริ่มต้น (`x86_64-unknown-linux-gnu`) ไบนารีของคุณจะถูกลิงก์แบบไดนามิกกับ glibc แต่ไม่มีดีเพนเดนซีรันไทม์อื่น คุณยังสามารถคอมไพล์ด้วย musl target (`x86_64-unknown-linux-musl`) เพื่อให้ได้ไบนารีแบบสแตติกล้วน ไม่ว่าทางไหน คอนเทนเนอร์ production ของเราไม่ต้องการ Rust toolchain ซอร์สโค้ด หรือดีเพนเดนซีบิลด์ใดๆ นอกเหนือจากไลบรารี C นั่นเป็นข่าวดี เพราะมันหมายความว่าเราสามารถใช้ Docker บิลด์แบบหลายสเตจ: คอมไพล์ในสเตจหนึ่ง จากนั้นคัดลอกแค่ไบนารีลงในอิมเมจรันไทม์จิ๋ว

```dockerfile
# Build stage
FROM rust:1-slim AS builder

WORKDIR /app

# Cache dependencies by copying just the manifest files first.
# For more robust dependency caching, consider the cargo-chef crate,
# which is purpose-built for this problem in Docker builds.
COPY Cargo.toml Cargo.lock ./
RUN mkdir src && echo "fn main() {}" > src/main.rs
RUN cargo build --release && rm -rf src

# Now copy the actual source and rebuild (only changed files recompile)
COPY . .
RUN touch src/main.rs && cargo build --release

# Runtime stage
FROM debian:bookworm-slim

RUN apt-get update \
    && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# Run as a non-root user
RUN useradd --create-home appuser
USER appuser

COPY --from=builder /app/target/release/my-app /usr/local/bin/my-app

EXPOSE 3000

CMD ["my-app"]
```

เคล็ดลับการแคชดีเพนเดนซีในสเตจบิลด์คุ้มที่จะทำความเข้าใจ เราคัดลอกแค่ `Cargo.toml` และ `Cargo.lock` ก่อนแล้วรันบิลด์ ซึ่งทำให้ Docker แคชดีเพนเดนซีที่คอมไพล์แล้วเป็นเลเยอร์ได้ เมื่อเราเปลี่ยนโค้ดแอปพลิเคชันแต่ไม่เปลี่ยนดีเพนเดนซี (ซึ่งคือสิ่งที่เกิดขึ้นส่วนใหญ่) Docker จะใช้เลเยอร์แคชนั้นซ้ำและคอมไพล์แค่โค้ดของเรา ถ้าไม่มีสิ่งนี้ คุณจะต้องคอมไพล์ดีเพนเดนซีทุกตัวใหม่ในทุกบิลด์ และด้วยเวลาคอมไพล์ของ Rust แบบที่เป็นอยู่ มันจะเจ็บปวดเร็วมาก

คุณอาจสงสัยว่าทำไมเราถึงติดตั้ง `ca-certificates` ในอิมเมจรันไทม์ ก็เพราะแอปพลิเคชันของเราอาจส่งคำขอ HTTPS ขาออก (ไปยัง API ภายนอก ผู้ให้บริการชำระเงิน และอื่นๆ) และจำเป็นต้องใช้ชุดใบรับรอง CA เพื่อตรวจสอบการเชื่อมต่อ TLS ถ้าข้ามขั้นตอนนี้ คุณจะเจอข้อผิดพลาด TLS ปริศนาตอนรันไทม์ ซึ่งไม่มีวันสนุกที่จะดีบักใน production

ถ้าคุณอยากเล็กลงไปอีก คุณสามารถคอมไพล์ด้วย `x86_64-unknown-linux-musl` เพื่อผลิตไบนารีที่ถูกลิงก์แบบสแตติกเต็มรูปแบบ แล้วใช้ `FROM scratch` เป็นเบสรันไทม์ของคุณ นี่ให้อิมเมจที่ต่ำกว่า 20 MB ซึ่งน่าประทับใจ ข้อแลกเปลี่ยนคือคุณจะไม่มีเชลล์หรือเครื่องมือดีบักในคอนเทนเนอร์เลย ซึ่งทำให้การแก้ปัญหายากขึ้นมากเมื่อมีอะไรผิดพลาดตอนตีสอง จากประสบการณ์ของผม อิมเมจ Debian slim เป็นจุดกึ่งกลางที่ดีสำหรับทีมส่วนใหญ่

## การปิดระบบอย่างนุ่มนวล

เมื่อออร์เคสเตรเตอร์คอนเทนเนอร์อย่าง Kubernetes, ECS หรือ Docker Swarm ตัดสินใจหยุดแอปพลิเคชันของเรา มันจะส่งสัญญาณ SIGTERM และให้ช่วงเวลาผ่อนผัน (โดยทั่วไป 30 วินาที) แก่โพรเซสในการทำงานที่ค้างอยู่ให้เสร็จก่อนส่ง SIGKILL ถ้าแอปพลิเคชันของเราไม่จัดการ SIGTERM สิ่งเลวร้ายจะเกิดขึ้น: คำขอที่อยู่ระหว่างดำเนินการถูกทิ้ง ธุรกรรมฐานข้อมูลถูกปล่อยให้อยู่ในสถานะไม่ชัดเจน และไคลเอนต์เห็นการรีเซ็ตการเชื่อมต่อ คุณคงไม่อยากให้เป็นแบบนั้นจริงๆ

ข่าวดีคือ Axum ให้กลไกในตัวสำหรับการปิดระบบอย่างนุ่มนวล:

```rust
use tokio::signal;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    // ... setup code ...

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
    tracing::info!("listening on {}", listener.local_addr()?);

    axum::serve(listener, app)
        .with_graceful_shutdown(shutdown_signal())
        .await?;

    tracing::info!("server shut down cleanly");
    Ok(())
}

async fn shutdown_signal() {
    let ctrl_c = async {
        signal::ctrl_c()
            .await
            .expect("failed to install Ctrl+C handler");
    };

    #[cfg(unix)]
    let terminate = async {
        signal::unix::signal(signal::unix::SignalKind::terminate())
            .expect("failed to install SIGTERM handler")
            .recv()
            .await;
    };

    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        _ = ctrl_c => {},
        _ = terminate => {},
    }

    tracing::info!("shutdown signal received, draining connections");
}
```

เมื่อสัญญาณปิดระบบดังขึ้น Axum จะหยุดรับการเชื่อมต่อใหม่แต่ยังคงประมวลผลคำขอที่อยู่ระหว่างดำเนินการ เมื่อคำขอที่ค้างอยู่ทั้งหมดเสร็จสิ้น (หรือช่วงเวลาผ่อนผันหมดลง) เซิร์ฟเวอร์ก็จะออกจากระบบอย่างสะอาด

เรื่องนี้สำคัญมากสำหรับการดำเนินการฐานข้อมูล ถ้าคำขออยู่กลางธุรกรรมตอนที่ SIGKILL มาถึง ฐานข้อมูลจะโรลแบ็กธุรกรรมในที่สุดหลังการหมดเวลาการเชื่อมต่อของมัน แต่ไคลเอนต์เห็นข้อผิดพลาด ด้วยการปิดระบบอย่างนุ่มนวล ธุรกรรมจะเสร็จสมบูรณ์ตามปกติและไคลเอนต์ได้รับการตอบกลับที่ถูกต้อง มันเป็นหนึ่งในสิ่งที่อาจดูเหมือนรายละเอียดเล็กน้อย แต่มันสร้างความแตกต่างจริงใน production

## การตรวจสุขภาพ

เอนด์พอยต์การตรวจสุขภาพบอกออร์เคสเตรเตอร์คอนเทนเนอร์หรือโหลดบาลานเซอร์ของเราว่าแอปพลิเคชันยังมีชีวิตและพร้อมเสิร์ฟทราฟฟิกหรือไม่ ออร์เคสเตรเตอร์ส่วนใหญ่แยกแยะการตรวจสองประเภท และมันคุ้มที่จะเข้าใจความต่าง เพราะการเข้าใจผิดอาจทำให้เกิดพฤติกรรมที่สับสนมาก

**Liveness probe** ตอบคำถาม "โพรเซสยังมีชีวิตและไม่ติดอยู่หรือเปล่า?" ถ้า liveness probe ล้มเหลว ออร์เคสเตรเตอร์จะรีสตาร์ตคอนเทนเนอร์ การตรวจนี้ควรเรียบง่ายและเร็ว นี่คือส่วนสำคัญ: อย่าตรวจดีเพนเดนซีภายนอกใน liveness probe ของคุณ ถ้าฐานข้อมูลของคุณใช้การไม่ได้ชั่วคราว คุณไม่ต้องการให้ออร์เคสเตรเตอร์ฆ่าและรีสตาร์ตแอปของคุณ เพราะนั่นแค่เพิ่มโหลดให้ฐานข้อมูลที่เครียดอยู่แล้ว

```rust
async fn health_live() -> StatusCode {
    StatusCode::OK
}
```

**Readiness probe** ตอบคำถามต่างออกไป: "อินสแตนซ์นี้พร้อมรับทราฟฟิกหรือยัง?" ถ้า readiness probe ล้มเหลว ออร์เคสเตรเตอร์จะหยุดส่งทราฟฟิกมาที่อินสแตนซ์นี้แต่ไม่รีสตาร์ตมัน นี่คือจุดที่เราตรวจว่าการเชื่อมต่อฐานข้อมูลแข็งแรง แคชที่จำเป็นเข้าถึงได้ และแอปพลิเคชันเสร็จสิ้นการอินิเชียลไลซ์ตอนสตาร์ตอัพ

```rust
async fn health_ready(State(state): State<AppState>) -> StatusCode {
    let db_ok = sqlx::query("SELECT 1")
        .execute(&state.db)
        .await
        .is_ok();

    if db_ok {
        StatusCode::OK
    } else {
        StatusCode::SERVICE_UNAVAILABLE
    }
}
```

เราวนต์เอนด์พอยต์เหล่านี้ไว้นอกเส้นทาง API ที่กำหนดเวอร์ชัน:

```rust
let app = Router::new()
    .route("/health", get(health_live))
    .route("/health/ready", get(health_ready))
    .nest("/api/v1", api_routes())
    .with_state(state);
```

ในการดีพลอยต์แบบ Kubernetes คุณจะตั้งค่า probe ใน pod spec แบบนี้:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /health/ready
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 10
```

## การตั้งค่าจากสภาพแวดล้อม

ตามที่เรากล่าวถึงในบท [การตั้งค่า](./configuration.md) แอปพลิเคชันของเราอ่านการตั้งค่าทั้งหมดจากตัวแปรสภาพแวดล้อม นี่หมายความว่าอิมเมจ Docker เดียวกันสามารถถูกดีพลอยต์ไปยัง development, staging และ production ได้ สิ่งเดียวที่เปลี่ยนระหว่างสภาพแวดล้อมคือชุดตัวแปรสภาพแวดล้อมที่แพลตฟอร์มการดีพลอยต์จัดหาให้

อย่าเผาการตั้งค่าเฉพาะสภาพแวดล้อมลงในอิมเมจ Docker ผมเห็นทีมทำแบบนี้แล้วมันนำไปสู่ปัญหาเสมอ อิมเมจควรเป็นอาร์ติแฟกต์ที่ไม่เปลี่ยนรูป (immutable artifact) ที่คุณสร้างครั้งเดียวแล้วดีพลอยต์ได้ทุกที่ เมื่อคุณเลื่อนขั้นอิมเมจที่ทดสอบแล้วจาก staging ไป production คุณอยากมั่นใจอย่างเต็มที่ว่าไบนารีเหมือนกันทุกประการ

## การรันไมเกรชัน

ไมเกรชันฐานข้อมูลของเราควรถูกรันเป็นส่วนหนึ่งของการสตาร์ตอัพแอปพลิเคชัน ก่อนที่เซิร์ฟเวอร์เริ่มรับทราฟฟิก เราจัดการเรื่องนี้ด้วยมาโคร `sqlx::migrate!` ตามที่อธิบายไว้ในบท [เลเยอร์ฐานข้อมูล](./database.md)

ในสภาพแวดล้อม Kubernetes คุณสามารถรันไมเกรชันเป็น init container หรือ pre-deployment job แทนได้ วิธีนั้นชัดเจนกว่าและแยกความล้มเหลวของไมเกรชันออกจากความล้มเหลวของการสตาร์ตอัพแอปพลิเคชันได้ แต่สำหรับแอปพลิเคชันส่วนใหญ่ สิ่งที่ผมพบคือการรันไมเกรชันตอนสตาร์ตอัพนั้นเรียบง่ายกว่าและทำงานได้ดี โดยเฉพาะเมื่อผสานกับ readiness probe readiness probe ทำให้มั่นใจว่าแอปพลิเคชันของเราจะไม่รับทราฟฟิกจนกว่าไมเกรชันจะเสร็จสิ้นและฐานข้อมูลเข้าถึงได้ ซึ่งให้ตาข่ายนิรภัยที่ดีกับเรา

## แล้ว Shuttle ล่ะ?

[Shuttle](https://www.shuttle.dev/) คือแพลตฟอร์มการดีพลอยต์ที่สร้างมาเพื่อ Rust โดยเฉพาะ มันจัดการการเตรียมโครงสร้างพื้นฐาน การตั้งค่าฐานข้อมูล และการดีพลอยต์ด้วยการตั้งค่าน้อยที่สุด ถ้าคุณไม่ต้องการการควบคุมแบบละเอียดเหนือโครงสร้างพื้นฐานการดีพลอยต์ของคุณ มันสามารถแบ่งเบาภาระการดำเนินงานไปจากบ่าของคุณได้มาก

ถึงอย่างนั้น ผมคิดว่าการเข้าใจวิธีดีพลอยต์ด้วย Docker และ Kubernetes มีคุณค่าไม่ว่าคุณจะลงเอยด้วยแพลตฟอร์มไหน แนวคิดพื้นฐานที่เรากล่าวถึงที่นี่ (การปิดระบบอย่างนุ่มนวล การตรวจสุขภาพ การตั้งค่าจากสภาพแวดล้อม อิมเมจที่ไม่เปลี่ยนรูป) ใช้ได้ทุกที่ ถึงแม้คุณจะใช้ Shuttle หรือแพลตฟอร์มคล้ายกัน การรู้ว่าเกิดอะไรขึ้นใต้ฝาจะช่วยคุณดีบักปัญหาเมื่อมันเกิดขึ้น
