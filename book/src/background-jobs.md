# งานเบื้องหลังและการจัดการทาสก์

ถ้าคุณสร้างเว็บแอปพลิเคชันอะไรมาเกินกว่าโปรเจกต์ของเล่น คุณคงเคยเจอเรื่องนี้: งานบางอย่างไม่ควรอยู่ในรอบคำขอ-การตอบกลับ การส่งอีเมลยืนยัน การประมวลผลไฟล์ที่อัปโหลด การสร้างรายงาน การลองส่งการแจ้งเตือน webhook ที่ล้มเหลวซ้ำ การล้างเซสชันที่หมดอายุ ทั้งหมดนี้จะทำให้การตอบกลับ HTTP ของเราช้าลงถ้าเราพยายามทำมันแบบอินไลน์ ในบทนี้ เราจะเดินดูแพตเทิร์นสำหรับจัดการงานเบื้องหลังในแอปพลิเคชันที่ใช้ Tokio เริ่มจากงานแบบ fire-and-forget ธรรมดา แล้วไล่ขึ้นไปจนถึงคิวงานแบบถาวรที่รู้จักการลองใหม่

## การสร้างทาสก์ภายในกระบวนการ

วิธีที่ง่ายที่สุดในการรันงานเบื้องหลังคือ `tokio::spawn` มันสร้างทาสก์แอซิงก์ใหม่ที่ทำงานอย่างอิสระจากตัวที่สร้างมัน โค้ดที่สร้างไม่ต้องรอให้ทาสก์ที่ถูกสร้างเสร็จ เว้นแต่คุณจะ `.await` `JoinHandle` ที่คืนมาอย่างชัดเจน

```rust
async fn create_user(
    State(state): State<AppState>,
    ValidatedJson(payload): ValidatedJson<CreateUserDto>,
) -> AppResult<(StatusCode, Json<UserResponse>)> {
    let user = state.user_service.register(payload).await?;

    // Send the welcome email in the background.
    // The HTTP response does not wait for this to finish.
    let email_client = state.email_client.clone();
    let email = user.email().clone();
    tokio::spawn(async move {
        if let Err(e) = email_client.send_welcome(&email).await {
            tracing::error!(error = ?e, "failed to send welcome email");
        }
    });

    Ok((StatusCode::CREATED, Json(user.into())))
}
```

วิธีนี้ใช้ได้ดีกับผลข้างเคียงที่ไม่สำคัญนักซึ่งความล้มเหลวเป็นครั้งคราวรับได้ (ผู้ใช้ของเรายังคงถูกสร้างอยู่แม้อีเมลจะล้มเหลว) แต่มีข้อควรระวังสำคัญบางอย่างที่คุณควรรู้ไว้

ถ้าทาสก์ที่ถูก spawn แพนิก แพนิกนั้นจะถูกเก็บไว้ใน `JoinHandle` ถ้าคุณไม่ await แฮนเดิล แพนิกจะถูกกลืนหายไปเงียบๆ ซึ่งสร้างความสับสนได้มากเวลาดีบักใน production คุณควร await แฮนเดิลหรือใช้ `JoinSet` ที่รายงานข้อผิดพลาดกลับมาให้คุณ

แต่ปัญหาที่ใหญ่กว่าคือ: ถ้าโพรเซสของคุณรีสตาร์ท (การดีพลอยต์ คราช การถูก OOM kill) ทาสก์ที่ถูก spawn ไว้และกำลังทำงานอยู่จะหายไปเฉยๆ ไม่มีการลองใหม่ ไม่มีการคงอยู่ ไม่มีการรับประกันว่างานเสร็จสมบูรณ์ สำหรับการทำงานที่ *ต้อง* สำเร็จในที่สุด คุณจะต้องมีคิวงานแบบถาวร ซึ่งเราจะพูดถึงในตอนท้ายของบทนี้

## JoinSet สำหรับจัดการกลุ่มทาสก์

เมื่อคุณมีชุดทาสก์ที่รู้จำนวนแน่นอนซึ่งต้องเสร็จทั้งหมด `tokio::task::JoinSet` มอบวิธีที่มีโครงสร้างให้เราในการ spawn พวกมันและเก็บรวบรวมผลลัพธ์:

```rust
use tokio::task::JoinSet;

async fn process_batch(items: Vec<Item>, pool: PgPool) -> anyhow::Result<()> {
    let mut set = JoinSet::new();

    for item in items {
        let pool = pool.clone();
        set.spawn(async move {
            process_item(&pool, &item).await
        });
    }

    // Wait for all tasks to complete.
    while let Some(result) = set.join_next().await {
        match result {
            Ok(Ok(())) => {}
            Ok(Err(e)) => tracing::error!(error = ?e, "item processing failed"),
            Err(e) => tracing::error!(error = ?e, "task panicked"),
        }
    }

    Ok(())
}
```

`JoinSet` ยังมีประโยชน์สำหรับการจำกัดการทำงานพร้อมกัน คุณสามารถตรวจสอบ `set.len()` ก่อน spawn ทาสก์ใหม่ และรอให้ตัวหนึ่งเสร็จถ้าคุณถึงขีดความจุแล้ว และเมื่อ `JoinSet` ถูกดรอป ทาสก์ทั้งหมดในนั้นจะถูก abort ซึ่งทำให้มันเข้ากับสถานการณ์การปิดระบบที่คุณต้องการยกเลิกงานที่เหลืออยู่ได้อย่างเป็นธรรมชาติ

## งานแบบเป็นคาบ

แอปพลิเคชันจำนวนมากต้องการงานเบื้องหลังที่เกิดซ้ำ: การล้างแคชทุก 5 นาที การรายงานเมตริกทุก 30 วินาที การส่ง ping เช็คสุขภาพทุก 10 วินาที เข้าใจแนวคิดใช่ไหม `interval` ของ Tokio คือสิ่งที่เราหยิบใช้ตรงนี้:

```rust
use tokio::time::{interval, Duration};

async fn run_cache_cleanup(
    pool: PgPool,
    shutdown: CancellationToken,
) {
    let mut ticker = interval(Duration::from_secs(300));

    loop {
        tokio::select! {
            _ = ticker.tick() => {
                if let Err(e) = cleanup_expired_sessions(&pool).await {
                    tracing::error!(error = ?e, "session cleanup failed");
                }
            }
            _ = shutdown.cancelled() => {
                tracing::info!("cache cleanup shutting down");
                return;
            }
        }
    }
}
```

เรื่องหนึ่งที่ทำให้ผมสะดุดตอนแรก: `interval` มีการตั้งค่า `MissedTickBehavior` ที่ควบคุมว่าจะเกิดอะไรขึ้นเมื่อทาสก์ของคุณใช้เวลานานกว่าช่วงคาบ ค่าเริ่มต้นคือ `Burst` ซึ่งยิงติ๊กที่พลาดไปทันทีเพื่อตามให้ทัน สำหรับงานบำรุงรักษาเบื้องหลังส่วนใหญ่ `MissedTickBehavior::Skip` คือสิ่งที่คุณต้องการจริงๆ เพราะคุณอยากข้ามติ๊กที่พลาดไประหว่างที่รอบก่อนหน้ายังทำงานอยู่ แทนที่จะสะสมพวกมันทั้งหมดให้ระเบิดพร้อมกัน

```rust
let mut ticker = interval(Duration::from_secs(300));
ticker.set_missed_tick_behavior(tokio::time::MissedTickBehavior::Skip);
```

## การผสาน worker เบื้องหลังเข้ากับ Axum

ในทางปฏิบัติ คุณจะเริ่ม worker เบื้องหลังพร้อมกับเซิร์ฟเวอร์ HTTP โดยแบ่งปันพูลฐานข้อมูลและการตั้งค่าผ่าน `AppState` เดียวกันหรือการ clone พูลโดยตรง บท [การปิดระบบอย่างนุ่มนวล](./graceful-shutdown.md) แสดงแพตเทิร์นเต็มรูปแบบสำหรับการ spawn ซับซิสเต็มหลายตัวและการประสานงานไลฟ์ไซเคิลของมัน

ให้ผมไล่ดูจุดผสานที่สำคัญ:

**สถานะที่ใช้ร่วมกัน.** Worker เบื้องหลังของเราต้องการพูลฐานข้อมูล การตั้งค่า และอาจรวมถึงอินสแตนซ์เซอร์วิสเดียวกันกับแฮนด์เลอร์ HTTP จง clone สิ่งเหล่านี้จากแหล่งเดียวกันตอนเริ่มระบบ

**การปิดระบบที่ประสานงานกัน.** Worker ต้องมี `CancellationToken` เพื่อให้มันหยุดอย่างนุ่มนวลเมื่อแอปพลิเคชันปิดตัวลง คุณต้องการให้ worker ทำงานปัจจุบันให้เสร็จก่อนออกจากลูป แทนที่จะทอดทิ้งงานกลางคัน

**การแยกข้อผิดพลาด.** ทาสก์เบื้องหลังที่แพนิกไม่ควรทำให้เซิร์ฟเวอร์ HTTP ล้มไปด้วย การรัน worker ใน `tokio::spawn` แยกต่างหากทำให้ความล้มเหลวของมันถูกแยกออกจากกัน บันทึกข้อมูลข้อผิดพลาด และขึ้นกับความต้องการของคุณ อาจรีสตาร์ท worker หรือปล่อยให้มันหยุดอยู่แบบนั้น

## คิวงานแบบถาวร

สำหรับงานที่ต้องอยู่รอดการรีสตาร์ทโพรเซส คุณต้องมีคิวแบบถาวรที่หนุนหลังด้วยฐานข้อมูลหรือ message broker ข่าวดีคือมีครีต Rust ที่โตเต็มที่หลายตัวแก้ปัญหานี้ให้เราแล้ว:

**[apalis](https://github.com/geofmureithi/apalis)** คือไลบรารีประมวลผลงานเบื้องหลังที่ปลอดภัยเรื่องชนิดข้อมูลและขยายได้ รองรับแบ็กเอนด์การจัดเก็บหลายแบบ (PostgreSQL, Redis, SQLite) และมาพร้อมการมอนิเตอร์ เมตริก และการปิดระบบอย่างนุ่มนวลในตัว มันทำงานได้ทั้งกับ Tokio และรันไทม์แอซิงก์อื่นๆ

**[fang](https://github.com/ayrat555/fang)** รัน worker แต่ละตัวในทาสก์ Tokio แยกต่างหากพร้อมการรีสตาร์ทอัตโนมัติเมื่อแพนิก มันรองรับงานตามกำหนดเวลาผ่านนิพจน์ cron โหมดการถอยหน่วงการลองใหม่ที่ปรับแต่งได้ และการนิรนัยซ้ำของงานแบบเฉพาะ

**[backie](https://github.com/rafaelcaricio/backie)** ให้การประมวลผลทาสก์แบบถาวรแบบแอซิงก์ที่หนุนหลังด้วย PostgreSQL ออกแบบมาสำหรับการขยายแนวนอนที่ worker ไม่จำเป็นต้องอยู่ในโพรเซสเดียวกับผู้ผลิตคิว

แพตเทิร์นทั่วไปของทั้งหมดนี้เหมือนกัน และเมื่อคุณเห็นมันแล้ว มันก็เข้าใจง่ายมาก: แฮนด์เลอร์ HTTP (หรือเซอร์วิส) ของคุณจัดงานเข้าคิวโดยการแทรกแถวลงในตารางงานหรือเผยแพร่ไปยัง message broker โพรเซส worker แยกต่างหาก (หรือทาสก์เบื้องหลังในโพรเซสเดียวกัน) โพลล์หางานที่รออยู่ ประมวลผลมัน และทำเครื่องหมายว่างานเสร็จสมบูรณ์หรือล้มเหลว งานที่ล้มเหลวจะถูกลองใหม่ด้วยการถอยหน่วงที่ตั้งค่าได้ และหลังจากการลองใหม่ถึงจำนวนสูงสุด มันจะย้ายไปสถานะเดดเล็ตเตอร์ (dead-letter) ที่ใครสักคนสามารถตรวจสอบมันด้วยตนเองได้

## การจัดการข้อผิดพลาดในงานเบื้องหลัง

นี่คือจุดที่เริ่มน่าสนใจ เพราะต่างจากแฮนด์เลอร์ HTTP งานเบื้องหลังไม่มีไคลเอนต์ให้ส่งคืนข้อผิดพลาด เมื่องานเบื้องหลังล้มเหลว คุณต้องมีกลยุทธ์ในการทำให้ความล้มเหลวนั้นมองเห็นได้และลงมือจัดการได้ นี่คือสิ่งที่ผมพบว่าใช้ได้ดี:

**บันทึกข้อมูลข้อผิดพลาดพร้อมบริบท.** ใช้ `tracing::error!` พร้อมฟิลด์แบบมีโครงสร้าง เพื่อให้ความล้มเหลวปรากฏในระบบรวมล็อกของคุณและสามารถเชื่อมโยงกับคำขอต้นทางที่จัดงานเข้าคิวไว้ หากไม่มีสิ่งนี้ คุณจะบินแบบไม่เห็นทางเมื่อมีอะไรผิดพลาดตอนตีสอง

**ลองใหม่พร้อมการถอยหน่วง.** สำหรับความล้มเหลวชั่วคราว (การหมดเวลาของเครือข่าย ฐานข้อมูลไม่พร้อมใช้งานชั่วคราว) ให้ลองดำเนินการอีกครั้งหลังหน่วงเวลาที่เพิ่มขึ้นเรื่อยๆ ครีตคิวงานถาวรส่วนใหญ่จัดการเรื่องนี้โดยอัตโนมัติ คุณจึงไม่ต้องสร้างเอง

**เดดเล็ตเตอร์หลังหมดจำนวนการลองใหม่.** ถ้างานล้มเหลวซ้ำๆ ให้ย้ายมันไปตารางหรือคิวเดดเล็ตเตอร์ที่สามารถตรวจสอบและแก้ไขหรือทิ้งด้วยตนเองได้ อย่าลองใหม่ไม่มีที่สิ้นสุด เพราะงานที่ล้มเหลวถาวรจะกินความจุของ worker และหน่วงทุกอย่างอื่นในคิว

**ปล่อยเมตริก.** ติดตามอัตราความสำเร็จของงาน ระยะเวลาการประมวลผล ความลึกของคิว และจำนวนการลองใหม่ เมตริกเหล่านี้คือระบบเตือนภัยล่วงหน้าของคุณสำหรับปัญหาที่กำลังสะสมก่อนที่มันจะปรากฏแก่ผู้ใช้ จากประสบการณ์ของผม ความลึกของคิวที่พุ่งสูงขึ้นเกือบจะเป็นสัญญาณแรกเสมอว่ามีอะไรกำลังผิดเพี้ยน
