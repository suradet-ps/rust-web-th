# การจัดการสถานะ

ถ้าคุณเคยสร้างเว็บเซอร์วิสแม้แต่ตัวเล็ก คุณจะรู้จักปัญหานี้: แฮนด์เลอร์ของคุณต้องเข้าถึงสิ่งที่ใช้ร่วมกัน เช่น พูลฐานข้อมูล การตั้งค่า อินสแตนซ์เซอร์วิส หรืออาจเป็นแคชในหน่วยความจำ ทุกคำขอล้วนต้องการบางอย่างหรือทั้งหมดจากสิ่งเหล่านี้ และคุณต้องมีวิธีส่งมันไปถึงแฮนด์เลอร์โดยไม่ต้องผ่านอาร์กิวเมนต์ของฟังก์ชันถึงสิบเจ็ดตัว Axum ให้วิธีที่ปลอดภัยด้านชนิดข้อมูลสำหรับจัดการเรื่องนี้ผ่านตัวแยกข้อมูล `State` และเมื่อคุณชินแล้ว มันจะกลายเป็นเรื่องธรรมชาติโดยสมบูรณ์

## struct AppState

แพตเทิร์นที่ผมหยิบใช้ทุกครั้งคือ struct เดียวที่ถือทุกสิ่งที่แฮนด์เลอร์ของเราต้องการ เราส่งมันให้เราเตอร์ผ่าน `.with_state()` แล้ว Axum จัดการที่เหลือให้ เรื่องหนึ่งที่ต้องจำไว้: struct ต้อง implement `Clone` เพราะ Axum clone มันสำหรับทุกครั้งที่เรียกแฮนด์เลอร์

```rust
use sqlx::PgPool;
use std::sync::Arc;

#[derive(Clone)]
pub struct AppState {
    pub config: Arc<Config>,
    pub db: PgPool,
    pub user_service: UserService<PostgresUserRepo>,
    pub post_service: PostService<PostgresPostRepo>,
}

impl AppState {
    pub fn new(config: Config, pool: PgPool) -> Self {
        let user_repo = PostgresUserRepo::new(pool.clone());
        let post_repo = PostgresPostRepo::new(pool.clone());

        Self {
            config: Arc::new(config),
            db: pool,
            user_service: UserService::new(user_repo),
            post_service: PostService::new(post_repo),
        }
    }
}
```

ขอผมเดินดูการตัดสินใจออกแบบไม่กี่อย่างตรงนี้

เราห่อ `Config` ใน `Arc` เพราะมันเป็นแบบอ่านอย่างเดียวหลังเริ่มระบบและอาจมีขนาดค่อนข้างใหญ่ `Arc` ให้การ clone ที่ราคาถูก (มันแค่เพิ่มตัวนับการอ้างอิง) แทนการ deep copy ทั้ง struct การตั้งค่าทุกครั้งที่ `AppState` ถูก clone ความแตกต่างนั้นสำคัญเมื่อคุณจัดการคำขอหลายพันคำขอต่อวินาที

`PgPool` ใช้การนับการอ้างอิงภายในอยู่แล้ว ดังนั้นการ clone มันก็ราคาถูกด้วย คุณจะพบว่าชนิดข้อมูลพูลการเชื่อมต่อส่วนใหญ่ในนิเวศ Rust ทำงานในลักษณะเดียวกัน

เซอร์วิสและรีพอสิทอรีถูกสร้างครั้งเดียวตอนเริ่มระบบ จากนั้นถูกใช้ร่วมกันข้ามทุกคำขอ ผมมองว่านี่คือ composition root ของแอปพลิเคชันเรา จุดเดียวที่เราต่อสายดีเพนเดนซีทั้งหมดเข้าด้วยกัน ถ้าคุณต้องสลับเทสต์ดับเบิลสำหรับรีพอสิทอรี นี่คือที่ที่คุณจะทำ

## การดึงสถานะในแฮนด์เลอร์

แล้วแฮนด์เลอร์ของเราจะเข้าถึงสถานะได้อย่างไร? ผ่านตัวแยกข้อมูล `State`:

```rust
async fn list_users(
    State(state): State<AppState>,
) -> AppResult<Json<Vec<UserResponse>>> {
    let users = state.user_service.list_all().await?;
    Ok(Json(users.into_iter().map(Into::into).collect()))
}
```

ตรงไปตรงมาทีเดียว ใช่ไหม? แต่คุณอาจสังเกตว่าแฮนด์เลอร์ทุกตัวได้รับ `AppState` ทั้งหมด แม้ว่ามันจะแตะเพียงฟิลด์เดียว สำหรับแอปพลิเคชันเล็กๆ นั่นก็โอเคโดยสิ้นเชิง แต่เมื่อสิ่งต่างๆ เติบโตขึ้น คุณอาจต้องการสิ่งที่ละเอียดกว่านั้น

## สถานะย่อยด้วย FromRef

นี่คือจุดที่ `FromRef` เข้ามา มันให้คุณดึงฟิลด์แต่ละตัวออกจากสถานะได้โดยตรง ดังนั้นแฮนด์เลอร์ไม่ต้องรู้จัก struct `AppState` ทั้งหมดเลย ผมพบว่ามันมีประโยชน์มากสำหรับการรักษาลายเซ็นของแฮนด์เลอร์ให้โฟกัส และจำกัดสิ่งที่แต่ละแฮนด์เลอร์เข้าถึงได้จริง

Axum ให้แมโคร derive ที่สร้างการ implement `FromRef` สำหรับแต่ละฟิลด์โดยอัตโนมัติ:

```rust
use axum::extract::FromRef;

#[derive(Clone, FromRef)]
pub struct AppState {
    config: Arc<Config>,
    db: PgPool,
    user_service: UserService<PostgresUserRepo>,
    post_service: PostService<PostgresPostRepo>,
}
```

`derive` ตัวเดียวช่วยเราจากการเขียนบล็อก `impl FromRef<AppState> for ...` ด้วยมือสำหรับทุกฟิลด์ มันสร้างอิมพลีเมนเทชันสำหรับชนิดข้อมูลของแต่ละฟิลด์ โดยใช้ชื่อฟิลด์เพื่อค้นหามันใน struct

ตอนนี้แฮนด์เลอร์ที่ต้องการแค่เซอร์วิสผู้ใช้สามารถขอแค่สิ่งนั้น:

```rust
async fn get_user(
    State(user_service): State<UserService<PostgresUserRepo>>,
    Path(id): Path<Uuid>,
) -> AppResult<Json<UserResponse>> {
    let user = user_service.get_by_id(UserId::from_uuid(id))
        .await?
        .ok_or(AppError::NotFound)?;
    Ok(Json(user.into()))
}
```

แพตเทิร์นนี้ทำงานเข้ากันได้ดีกับตัวแยกข้อมูลแบบกำหนดเองด้วย ตัวอย่างเช่น ตัวแยกข้อมูล `AuthUser` ของเรา (ซึ่งเราจะสร้างในบท [การยืนยันตัวตนและการอนุญาตสิทธิ์](./authentication.md)) สามารถดึง JWT secret จากสถานะผ่าน `FromRef` โดยไม่ต้องรู้จักฟิลด์อื่นๆ แยกส่วนกันอย่างสะอาด

## State เทียบกับ Extension

คุณอาจสงสัยว่าทำไม Axum ถึงมีทั้ง `State` และ `Extension` สำหรับส่งข้อมูลให้แฮนด์เลอร์ ผมเคยเห็นคนหยิบใช้ `Extension` ด้วยความเคยชิน (อาจมาจากเฟรมเวิร์กอื่น) ขอผมอธิบายว่าควรใช้อันไหนเมื่อไหร่

**State** ถูกตรวจสอบชนิดข้อมูลตอนคอมไพล์ ถ้าคุณลืมเรียก `.with_state()` หรือชนิดข้อมูลไม่ตรงกัน คอมไพเลอร์จะจับได้ แค่เรื่องเดียวนี้ก็ทำให้มันเป็นตัวเลือกค่าเริ่มต้นของผมแล้ว

**Extension** เก็บค่าไว้ใน type-map บนคำขอเอง มันถูกตรวจสอบที่รันไทม์เท่านั้น ซึ่งหมายความว่าความไม่ตรงกันจะปรากฏเป็นข้อผิดพลาด 500 เมื่อคำขอจริงมาถึงแฮนด์เลอร์ ไม่ค่อยดีเท่าไหร่ แต่เอ็กซ์เทนชันมีประโยชน์จริงๆ สำหรับค่าที่มิดเดิลแวร์ผูกไว้แบบต่อคำขอ เช่น ผู้ใช้ที่ผ่านการยืนยันตัวตนซึ่งถูกแยกออกมาจาก JWT

นี่คือวิธีที่ผมคิด: ใช้ `State` สำหรับดีเพนเดนซีระดับแอปพลิเคชันที่คุณตั้งค่าตอนเริ่มระบบ (การตั้งค่า พูลฐานข้อมูล เซอร์วิส) ใช้ `Extension` สำหรับข้อมูลต่อคำขอที่มิดเดิลแวร์สร้างขึ้นทันที (on the fly)

## การหลีกเลี่ยงข้อผิดพลาดที่พบบ่อย

ก่อนที่เราจะไปต่อ ขอผมแชร์ไม่กี่เรื่องที่เคยกัดผม (หรือคนในทีมของผม) ใน production

**อย่าใส่ `Mutex<T>` ในสถานะของคุณถ้าคุณยังไม่ได้คิดให้รอบคอบจริงๆ** ผมเคยเห็นบั๊กจากเรื่องนี้มามากพอแล้ว mutex ที่ถือข้ามจุด `.await` อาจ deadlock หรือทำให้เกิดการแย่งชิง (contention) ที่โหดร้ายในโค้ดแอซิงก์ ถ้าคุณต้องการสถานะร่วมที่กลายพันธุ์ได้ (เช่นแคชในหน่วยความจำ) ให้หยิบ `tokio::sync::RwLock` ซึ่งตระหนักถึงแอซิงก์ หรือดียิ่งกว่านั้น ให้ใช้ครีตอย่าง `moka` หรือ `dashmap` ที่สร้างมาเพื่อการเข้าถึงพร้อมกันโดยเฉพาะ

**จงตั้งใจว่าอะไรควรเข้าไปใน AppState** มันเย้ายวนที่จะโยนฟิลด์เข้าไปเรื่อยๆ เมื่อแอปพลิเคชันเติบโต แต่ struct สถานะที่มีฟิลด์เป็นโหลจะเข้าใจยากอย่างรวดเร็ว ถ้าสถานะของคุณเริ่มจัดการไม่ไหว นั่นมักเป็นสัญญาณว่าแอปของคุณจะได้ประโยชน์จากการแยกเป็นโมดูลที่โฟกัสมากขึ้น โดยแต่ละโมดูลมีชนิดข้อมูลสถานะของตัวเองที่คุณประกอบรวมกันที่ระดับเราเตอร์

**สร้างสถานะของคุณครั้งเดียว ตอนเริ่มระบบ** อย่าสร้างอินสแตนซ์เซอร์วิสหรือรีพอสิทอรีใหม่ภายในแฮนด์เลอร์ จุดประสงค์ทั้งหมดของแพตเทิร์น `AppState` คือการต่อสายดีเพนเดนซีเข้าด้วยกันในที่เดียว (ฟังก์ชัน `main` ของเราหรือฟังก์ชันตั้งค่าที่มันเรียก) จากนั้นแชร์มันแบบไม่กลายพันธุ์ข้ามทุกคำขอ เมื่อคุณซึมซับสิ่งนั้น โครงสร้างของแอปพลิเคชันคุณจะตามง่ายขึ้นมาก
