# บทนำ

ถ้าคุณเคยทำงานกับ React มาก่อน คุณอาจเคยได้ยินชื่อ [bulletproof-react](https://github.com/alan2207/bulletproof-react) คู่มือที่นำเสนอแนวทางอย่างมั่นใจ (opinionated guide) เพื่อให้ทีมมีมุมมองร่วมกันว่าจะจัดโครงสร้างแอปพลิเคชันอย่างไร ควรหยิบแพตเทิร์นไหนมาใช้ และตรรกะแต่ละประเภทควรอยู่ตรงไหน มันไม่ได้สร้างแนวคิดใหม่ขึ้นมา หากแต่คัดสรรแนวคิดที่พิสูจน์แล้วว่าได้ผลจริงในระบบ production แล้วจัดระเบียบให้เป็นเรื่องเดียวกันที่เข้าใจได้

ผมต้องการสิ่งเดียวกันสำหรับ **Rust และ Axum** นี่คือที่มาของคู่มือเล่มนี้

Axum ถูกออกแบบให้เรียบง่ายโดยตั้งใจ คุณได้เราเตอร์ ตัวแยกข้อมูล (extractor) และการผสานเข้ากับ Tower อย่างลึกซึ้ง แล้วจากนั้นมันก็ไม่ก้าวก่ายคุณอีกต่อไป ความเรียบง่ายแบบนี้คือจุดแข็งจริงๆ แต่ในขณะเดียวกันก็หมายความว่าโปรเจกต์ Axum สองโปรเจกต์ที่สร้างโดยคนสองทีมอาจมีหน้าตาแตกต่างกันโดยสิ้นเชิง ทีมหนึ่งใส่ SQL ลงในแฮนด์เลอร์โดยตรง อีกทีมหนึ่งสร้างสถาปัตยกรรมเฮกซะโกนัลซับซ้อนด้วยครีตในเวิร์กสเปซห้าครีต ไม่มีวิธีไหนผิดไปซะทีเดียว แต่ความไม่สอดคล้องกันนี่เองที่ทำให้การป้อนงานใหม่ให้คนใหม่ยากขึ้น ทำให้การดูแลระบบในระยะยาวยากขึ้น และทำให้การตัดสินใจว่าตรรกะชิ้นหนึ่งควรอยู่ตรงไหนยากขึ้น ผมเห็นปัญหานี้เกิดขึ้นซ้ำแล้วซ้ำเล่าจนรู้ว่ามันเป็นปัญหาจริงๆ

สิ่งที่ผมพยายามทำในคู่มือนี้คือการรวบรวมคำตอบที่คัดสรรมาอย่างดีสำหรับคำถามเชิงโครงสร้างเหล่านี้ แนวคิดนี้ได้แรงบันดาลใจจากวรรณกรรมเกี่ยวกับสถาปัตยกรรมเฮกซะโกนัลและสถาปัตยกรรมแบบ clean architecture ตลอดจนประสบการณ์จริงที่ผมเก็บสะสมมาจากบล็อกโพสต์ บทความในงานประชุม และโปรเจกต์โอเพนซอร์สจำนวนมากในวงการเว็บ Rust

## หนังสือเล่มนี้ครอบคลุมอะไรบ้าง

หนังสือเล่มนี้จัดเป็นหกส่วน ผมจะพาคุณเดินดูอย่างคร่าวๆ เพื่อให้รู้ว่าอะไรอยู่ตรงไหน

**สถาปัตยกรรม** คือการวางรากฐาน เราจะพูดถึงวิธีจัดระเบียบไฟล์และโมดูล วิธีคิดเกี่ยวกับเลเยอร์และทิศทางของดีเพนเดนซี และวิธีสร้างแบบจำลองโดเมนของคุณด้วยระบบชนิดข้อมูลของ Rust เพื่อให้สถานะที่ไม่ถูกต้องกลายเป็นสิ่งที่ไม่สามารถแทนค่าได้ (unrepresentable) นี่คือสิ่งที่ผมอยากให้ใครสักคนสอนผมตอนเริ่มโปรเจกต์ Axum จริงจังโปรเจกต์แรก

**แพตเทิร์นหลัก** จัดการกับปัญหาที่ทุกเว็บแอปพลิเคชันต้องเผชิญ นั่นคือการจัดการข้อผิดพลาด การเข้าถึงฐานข้อมูล สถานะของแอปพลิเคชัน และการจัดการการตั้งค่า คุณจะได้พบแพตเทิร์นรูปธรรมพร้อมโค้ดจริงที่นำไปปรับใช้กับโปรเจกต์ของคุณเองได้

**เลเยอร์ HTTP** คือส่วนที่เจาะลึกถึงจุดเฉพาะของ Axum ในสแตกทั้งหมด ได้แก่ การกำหนดเส้นทาง แฮนด์เลอร์ การประกอบมิดเดิลแวร์ การตรวจสอบความถูกต้องของคำขอ การยืนยันตัวตน และข้อตกลงในการออกแบบ API เช่น การแบ่งหน้าและการกำหนดเวอร์ชัน

**การนำไปใช้งานจริง** ครอบคลุมสิ่งที่คุณต้องมีเพื่อส่งมอบและดูแลระบบจริง ไม่ว่าจะเป็นการบันทึกข้อมูลแบบมีโครงสร้าง (structured logging) และ tracing การเสริมความปลอดภัย กลยุทธ์การทดสอบ ข้อควรพิจารณาด้านประสิทธิภาพ และการดีพลอยต์ด้วย Docker พร้อมการปิดระบบอย่างนุ่มนวล เพราะการเขียนโค้ดเป็นเพียงครึ่งหนึ่งของงาน ใช่ไหมล่ะ?

**ขั้นสูง** พาคุณเลยข้ามโมเดล HTTP เซิร์ฟเวอร์เดียวไปสู่แพตเทิร์นที่ปรากฏในระบบ production ที่มีความซับซ้อนจริงๆ เราจะเจาะลึกขอบคมของ async ใน Rust (ความปลอดภัยในการยกเลิก, ความหมายของ `select!`) การสื่อสารระหว่างคอมโพเนนต์ด้วยแชนเนล การปิดระบบอย่างประสานงานของแอปพลิเคชันหลายซับซิสเต็ม การจัดการงานเบื้องหลัง การเพิ่มพื้นผิว gRPC ด้วย Tonic และเครื่องจักรสถานะแบบเวลาคอมไพล์ด้วยแพตเทิร์นไทป์สเตต บางเรื่องผมใช้เวลานานกว่าจะคิดออกด้วยตัวเอง ดังนั้นหวังว่ามันจะช่วยประหยัดความปวดหัวของคุณได้บ้าง

**อ้างอิง** มอบตารางค้นควิกของครีต แคตตาล็อกแอนติแพตเทิร์นที่พบบ่อยเพื่อระวัง และรายการหนังสือ บทความ และรีโพสิทอรีตัวอย่างที่คัดสรรมา หากคุณต้องการศึกษาให้ลึกขึ้น

## หลักการชี้นำ

มีค่านิยมบางอย่างที่แทรกอยู่ในทุกคำแนะนำของหนังสือเล่มนี้ มันไม่ใช่แนวคิดดั้งเดิม (ไม่มีอะไรในนี้ดั้งเดิม) แต่มันคือสิ่งที่ผมวนกลับมาหาอยู่เสมอ

**ทำให้แฮนด์เลอร์บาง** หน้าที่ของแฮนด์เลอร์คือดึงข้อมูลออกจากคำขอ เรียกใช้เซอร์วิส แล้วเปลี่ยนผลลัพธ์ให้เป็นการตอบกลับ เท่านั้นแหละ ถ้าแฮนด์เลอร์ของคุณทำการตรวจสอบความถูกต้อง ควิวรีฐานข้อมูล และตรรกะทางธุรกิจในฟังก์ชันเดียว นั่นคือมันทำงานมากเกินไปแล้ว ผมเห็นแฮนด์เลอร์ยาวสองร้อยบรรทัดมาเยอะพอที่จะรู้ว่าหนทางนั้นจบลงที่ไหน ผลักงานพวกนั้นลงไปยังเลเยอร์ที่เหมาะสม

**ให้ระบบชนิดข้อมูลทำงานแทนเรา** ระบบชนิดข้อมูลของ Rust ทรงพลังผิดปกติสำหรับภาษาเชิงระบบ และจากประสบการณ์ของผม มันเปล่งประกายจริงๆ ในเว็บแอปพลิเคชัน นิวนิวไทป์ที่บังคับใช้ค่าคงที่ (invariant) ตั้งแต่ตอนสร้างค่า ชนิด `Result` ที่ทำให้เส้นทางของข้อผิดพลาดชัดเจน การแยกชั้นเชิงนามธรรมด้วยเทรตที่ถอดคัปปลิ้งเลเยอร์ของคุณออกจากกัน สิ่งเหล่านี้จับบั๊กได้ตั้งแต่เวลาคอมไพล์ มิฉะนั้นบั๊กพวกนั้นจะไปโผล่ใน production ตอนตีสอง คุ้มค่ากับความพยายามล่วงหน้าทุกครั้ง

**แยกสิ่งที่เปลี่ยนแปลงด้วยเหตุต่างกัน** การกำหนดเส้นทาง HTTP ของคุณอาจเปลี่ยนเพราะคุณเพิ่มเอนด์พอยต์ใหม่ ควิวรีฐานข้อมูลของคุณอาจเปลี่ยนเพราะคุณปรับเส้นทางที่ช้าให้เร็วขึ้น กฎทางธุรกิจของคุณอาจเปลี่ยนเพราะความต้องการของผลิตภัณฑ์พัฒนาไป เมื่อความกังวลเหล่านี้อยู่ในโมดูลต่างกันที่มีขอบเขตชัดเจน คุณจะเปลี่ยนอันหนึ่งได้โดยไม่ต้องกังวลกับอันอื่น ฟังดูเหมือนเรื่องธรรมดาเมื่อพูดออกมา แต่จริงๆ แล้วมันง่ายมากที่ปล่อยให้มันปนกันจนเลอะเทอะ

**เริ่มจากง่าย แล้วค่อยพัฒนาโดยตั้งใจ** ไม่ใช่ทุกโปรเจกต์ที่ต้องการสถาปัตยกรรมเฮกซะโกนัลกับครีตในเวิร์กสเปซห้าครีต API เล็กๆ ที่มีเอนด์พอยต์ไม่กี่ตัวสามารถอยู่ได้ด้วยโครงสร้างโมดูลแบบเรียบและเรียก SQLx ตรงๆ สิ่งที่สำคัญคือการเข้าใจหลักการเบื้องหลังสถาปัตยกรรมที่ซับซ้อนกว่า เพื่อที่คุณจะได้ขยับเข้าไปหามันแบบค่อยเป็นค่อยไปเมื่อความซับซ้อนของโปรเจกต์เรียกร้องจริงๆ แทนที่จะ over-engineer ตั้งแต่เริ่ม หรือมิฉะนั้นก็ต้องรีแฟกเตอร์กันวุ่นวายตอนที่ของเริ่มรก

**เพิ่มประสิทธิภาพเพื่อผู้อ่านโค้ด** โค้ดถูกอ่านบ่อยกว่าที่ถูกเขียน เรารู้กันดี แต่ก็ลืมง่ายในยามคับขัน แพตเทิร์นในคู่มือนี้ให้ความสำคัญกับความชัดเจนและความสามารถคาดเดาได้มากกว่าความฉลาดเกินจำเป็น เมื่อมีคนใหม่เข้าทีมแล้วเปิดโค้ดเบสเป็นครั้งแรก พวกเขาควรหาสิ่งที่ต้องการเจอและเข้าใจว่าทำไมมันถึงถูกจัดโครงสร้างแบบนั้น

## วิธีใช้คู่มือนี้

คุณไม่จำเป็นต้องอ่านตั้งแต่หน้าแรกจนหน้าสุดท้าย ถ้าคุณกำลังเริ่มโปรเจกต์ใหม่ ส่วนสถาปัตยกรรมจะช่วยคุณวางรากฐานที่แข็งแรง ถ้าคุณกำลังทำงานบนโปรเจกต์เดิมและอยากปรับปรุงจุดใดจุดหนึ่ง ก็ข้ามไปยังบทที่เกี่ยวข้องได้เลย แต่ละบทมีความสมบูรณ์ในตัวเองพอที่จะมีประโยชน์เมื่ออ่านเดี่ยวๆ แม้บางบทจะอ้างอิงถึงกันเมื่อหัวข้อทับซ้อน

ผมพยายามทำให้ตัวอย่างโค้ดสมจริง พวกมันใช้ API ของครีตจริงอย่างที่คุณจะใช้ใน production พร้อมการจัดการข้อผิดพลาดที่เหมาะสมและลายเซ็นชนิดข้อมูลจริง ไม่มี `todo!()` ปลอมๆ หลอกตรงจุดที่ยาก และในจุดที่มีการแลกเปลี่ยน (trade-off) ที่มีความหมายระหว่างแนวทาง เราจะอธิบายทั้งสองทางเลือกและให้บริบทมากพอที่คุณจะตัดสินใจได้ถูกต้องกับสถานการณ์ของคุณ

อีกเรื่องหนึ่ง: นี่คือเอกสารที่มีชีวิต นิเวศเว็บ Rust ยังคงพัฒนาเร็วมาก และสิ่งที่เราถือว่าเป็นแนวปฏิบัติที่ดีที่สุดในวันนี้ก็จะถูกปรับปรุงต่อไปเรื่อยๆ แต่หลักการมักเสถียรกว่าครีตหรือ API เฉพาะ และนั่นคือจุดที่ผมคิดว่าคุณค่าที่ยั่งยืนส่วนใหญ่อยู่ มาเริ่มกันเลย
