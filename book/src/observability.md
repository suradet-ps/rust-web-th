# การสังเกตการณ์ (Observability)

คุณอาจเคยมีช่วงเวลาที่มีอะไรบางอย่างพังใน production แล้วคุณต้องจ้องกำแพงของบรรทัดล็อกที่ช่วยอะไรไม่ได้ พยายามร้อยเรียงว่ามันเกิดอะไรขึ้น ผมเองก็เคย นี่คือสิ่งที่การสังเกตการณ์ช่วยเราหลีกเลี่ยง มันคือวิธีที่เราจะรู้ว่าแอปพลิเคชันของเรากำลังทำอะไรอยู่จริงๆ เมื่อมันถูกรันออกไปในโลกภายนอก โดยไม่ต้องจำลองปัญหานั้นขึ้นมาบนแล็ปท็อปของเรา

นิเวศของ Rust ตกลงร่วมกันที่ครีต `tracing` เป็นมาตรฐานของการบันทึกข้อมูลแบบมีโครงสร้างพร้อมบริบท (structured, contextual logging) เมื่อคุณผสานมันเข้ากับ OpenTelemetry สำหรับการเทรซแบบกระจาย (distributed tracing) และเมตริก คุณก็จะได้สแตกการสังเกตการณ์ที่แข็งแรงซึ่งครอบคลุมเกือบทุกอย่างที่เราจะต้องใช้

## การบันทึกข้อมูลแบบมีโครงสร้างด้วย tracing

ถ้าคุณเคยใช้ `log` หรือ `env_logger` มาก่อน `tracing` ตอนแรกอาจดูคุ้นเคย แต่มันทำสิ่งที่ต่างออกไปพอสมควรภายใต้ฝา แทนที่จะปล่อยสตริงข้อความแบนๆ มันปล่อยเหตุการณ์แบบมีโครงสร้างพร้อมฟิลด์ที่มีชนิดข้อมูล นั่นหมายความว่าเครื่องมือวิเคราะห์ล็อกของคุณสามารถกรอง รวมกลุ่ม และควิวรีบนฟิลด์เฉพาะได้จริงๆ แทนที่จะพยายามแกะมันออกมาจากสตริงข้อความ มันยังรองรับสแปน ซึ่งแทนช่วงเวลาหนึ่ง (เช่น ระยะเวลาของคำขอ HTTP หรือควิวรีฐานข้อมูล) และพกพาบริบทที่จะถูกแนบไปกับเหตุการณ์ทั้งหมดที่อยู่ภายในสแปนนั้นโดยอัตโนมัติ

### การตั้งค่าซับสไครเบอร์

ซับสไครเบอร์ของ tracing เป็นตัวควบคุมว่าเหตุการณ์ถูกจัดรูปแบบอย่างไรและถูกส่งไปที่ไหน ในระหว่างการพัฒนา เราอยากได้เอาต์พุตที่มนุษย์อ่านรู้เรื่องพร้อมสี เพื่อที่เราจะอ่านสิ่งที่เกิดขึ้นในเทอร์มินัลของเราได้จริงๆ ส่วนใน production เราอยากได้เอาต์พุตแบบ JSON ที่ระบบรวบรวมล็อกของเราสามารถแยกวิเคราะห์ได้

```rust
use tracing_subscriber::{
    fmt, layer::SubscriberExt, util::SubscriberInitExt, EnvFilter,
};

pub fn init_tracing(log_level: &str) {
    let env_filter = EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new(log_level));

    // Use runtime configuration rather than build profile to control
    // log format. A release build in staging should still be readable,
    // and a debug build against production data should still emit JSON.
    let json_output = std::env::var("LOG_JSON")
        .map(|v| v == "true" || v == "1")
        .unwrap_or(false);

    let fmt_layer = if json_output {
        fmt::layer().json().boxed()
    } else {
        fmt::layer().pretty().boxed()
    };

    tracing_subscriber::registry()
        .with(env_filter)
        .with(fmt_layer)
        .init();
}
```

`EnvFilter` เปิดให้เราควบคุมระดับการล็อกตอนรันไทม์ผ่านตัวแปรสภาพแวดล้อม `RUST_LOG` คุณสามารถตั้งระดับที่ต่างกันให้แต่ละโมดูลได้ ซึ่งช่วยได้มากเวลาเราต้องการเพิ่มความละเอียดของคอมโพเนนต์ตัวใดตัวหนึ่งโดยไม่ต้องจมอยู่ในล็อกจากอย่างอื่นไปทั้งหมด:

```
RUST_LOG=info,my_app::infra=debug,sqlx=warn
```

### การเทรซคำขอด้วย TraceLayer

`TraceLayer` จาก tower-http สร้างสแปนให้คำขอ HTTP แต่ละคำขอโดยอัตโนมัติ โดยบันทึกเมธอด URI รหัสสถานะ และระยะเวลา เมื่อเราจับคู่มันกับ request ID เราก็จะสามารถตามรอยคำขอหนึ่งคำขอผ่านรายการล็อกทั้งหมดที่มันสร้างขึ้นได้ มาดูกันว่าหน้าตาเป็นแบบไหน

```rust
use tower_http::trace::TraceLayer;

let trace_layer = TraceLayer::new_for_http()
    .make_span_with(|request: &http::Request<_>| {
        let request_id = request
            .headers()
            .get("x-request-id")
            .and_then(|v| v.to_str().ok())
            .unwrap_or("unknown");

        // Prefer the matched route pattern (e.g., "/api/v1/users/{id}")
        // over the raw URI (e.g., "/api/v1/users/550e8400-...").
        // Raw URIs create high-cardinality span fields that can overwhelm
        // metrics backends and make aggregation impossible.
        let matched_path = request.extensions()
            .get::<axum::extract::MatchedPath>()
            .map(|p| p.as_str().to_string())
            .unwrap_or_else(|| request.uri().path().to_string());

        tracing::info_span!(
            "http_request",
            method = %request.method(),
            path = %matched_path,
            request_id = %request_id,
        )
    });
```

เหตุการณ์ล็อกทุกเหตุการณ์ที่ถูกปล่อยออกมาระหว่างประมวลผลคำขอนั้นจะรวมฟิลด์ `method`, `path` และ `request_id` ไว้โดยอัตโนมัติ เพราะสแปนทำหน้าที่เป็นบริบทรอบข้างของงานทั้งหมดที่ทำอยู่ภายในมัน นี่คือหนึ่งในเรื่องที่ฟังดูเล็กน้อยแต่สร้างความแตกต่างมหาศาล เมื่อแอปพลิเคชันของเราจัดการคำขอพร้อมกันหลายร้อยคำขอ เรายังคงหารายการล็อกทุกบรรทัดที่เกี่ยวข้องกับคำขอหนึ่งคำขอได้เพียงแค่กรองด้วย ID ของมัน

### การใส่เครื่องมือวัดให้แฮนด์เลอร์และเซอร์วิส

เราสามารถใช้แอตทริบิวต์ `#[tracing::instrument]` เพื่อให้สร้างสแปนให้ฟังก์ชันแต่ละตัวโดยอัตโนมัติ ผมพบว่ามันมีคุณค่าเป็นพิเศษเมื่อใช้กับเมธอดของเซอร์วิสและการเรียกที่รีพอสิทอรี เพราะมันทำให้คุณเห็นชัดเจนว่าถูกใช้ไปตรงจุดใดบ้าง โดยไม่ต้องต่อสายการสร้างสแปนด้วยมือไปทั่วทุกที่

```rust
#[tracing::instrument(
    skip(state, payload),
)]
async fn create_user(
    State(state): State<AppState>,
    ValidatedJson(payload): ValidatedJson<CreateUserDto>,
) -> AppResult<(StatusCode, Json<UserResponse>)> {
    tracing::info!("creating new user");

    let user = state.user_service.register(payload).await?;

    tracing::info!(user_id = %user.id().as_uuid(), "user created successfully");
    Ok((StatusCode::CREATED, Json(user.into())))
}
```

คำสั่ง `skip(state, payload)` บอกให้มาโคร instrument อย่ารวม state หรือเพย์โหลดของคำขอไว้ในฟิลด์ของสแปน หลังจากการเรียกเซอร์วิสสำเร็จ เราก็ล็อก `user_id` เป็นฟิลด์แบบมีโครงสร้าง สังเกตว่าเราใช้ `user_id` แบบโอเพก (opaque) แทนที่จะเป็น `user.email` ในสแปน นี่คือการตัดสินใจโดยตั้งใจ จากประสบการณ์ของผม การยึดตัวระบุที่มีความเสี่ยงต่ำต่อข้อมูลส่วนบุคคล (user ID, tenant ID, request ID) ดีกว่าข้อมูลส่วนตัว (ที่อยู่อีเมล ชื่อ) ในเอาต์พุตการเทรซของคุณมาก ถ้าคุณต้องโยงการเทรซกับอีเมลจริงเพื่อการดีบัก ก็ให้ค้นหามันจาก user ID คุณคงไม่ต้องการให้ล็อกทุกบรรทัดในระบบรวบรวมล็อกของคุณแบกข้อมูลส่วนตัวไปทั่ว

### แนวปฏิบัติที่ดีที่สุดในการบันทึกข้อมูล

**ใช้ฟิลด์แบบมีโครงสร้างแทนการแทรกสตริง** แทนที่จะเขียน `tracing::info!("Created user {}", user_id)` ให้เขียน `tracing::info!(user_id = %user_id, "user created")` รูปแบบที่มีโครงสร้างจะทำให้ระบบรวบรวมล็อกของคุณทำดัชนีและกรองบนฟิลด์ `user_id` ได้ ซึ่งมีประโยชน์มากกว่าการพยายามแกะมันออกมาจากสตริงข้อความมาก

**ล็อกที่ระดับที่เหมาะสม** อาจฟังดูชัดเจนอยู่แล้ว แต่มันคุ้มที่จะกล่าวให้ชัด ใช้ `error` กับสิ่งที่บ่งชี้ว่ามีบั๊กหรือความล้มเหลวของระบบที่ต้องได้รับการดูแล ใช้ `warn` กับสถานการณ์ที่ผิดปกติแต่จัดการได้ (เช่น คำขอที่ถูกจำกัดอัตราการเรียกหรือ cache miss) ใช้ `info` กับเหตุการณ์ทางธุรกิจที่มีนัยสำคัญ (สร้างผู้ใช้แล้ว, วางคำสั่งซื้อแล้ว) ใช้ `debug` กับข้อมูลการดำเนินงานแบบละเอียดที่ช่วยในระหว่างการพัฒนาหรือการแก้ปัญหา การทำให้ถูกจุดนี้สำคัญ เพราะเมื่อมีอะไรผิดพลาดตอนตีสอง คุณต้องการให้การแจ้งเตือนของคุณมีความหมาย

**ห้ามล็อกความลับเด็ดขาด** ถ้าคุณใช้ครีต `secrecy` กับการตั้งค่าของคุณ (ตามที่เรากล่าวถึงในบท [การตั้งค่า](./configuration.md)) การอิมพลีเมนต์ `Debug` จะปกปิดค่าที่ละเอียดอ่อนให้โดยอัตโนมัติ แต่จงระวังบอดี้ของคำขอ ส่วนหัว และข้อมูลอื่นๆ ที่อาจมีโทเคน รหัสผ่าน หรือข้อมูลส่วนบุคคล

## OpenTelemetry

เมื่อแอปพลิเคชันของเราเติบโตเป็นระบบแบบกระจายที่คำขอของผู้ใช้หนึ่งคำขออาจแตะต้องหลายเซอร์วิส เราจำเป็นต้องมีวิธีตามรอยคำขอนั้นข้ามพรมแดนของระบบ นี่คือจุดที่ OpenTelemetry เข้ามา มันมอบวิธีมาตรฐานให้เราในการแพร่กระจายบริบทของเทรซและเก็บรวบรวมข้อมูลเทเลเมทรี

ครีตหลักๆ คือ:

- **opentelemetry** และ **opentelemetry_sdk** สำหรับคอร์ API และ SDK
- **opentelemetry-otlp** สำหรับส่งออกเทรซไปยังแบ็กเอนด์ที่รองรับ OTLP (Jaeger, Tempo, Datadog ฯลฯ)
- **tracing-opentelemetry** สำหรับเชื่อมสแปนของครีต `tracing` เข้ากับสแปนของ OpenTelemetry
- **axum-tracing-opentelemetry** สำหรับการแพร่กระจายบริบทเทรซอัตโนมัติใน Axum

ด้วยสแตกนี้ ทุกคำขอจะได้รับเทรซ ID ที่ติดตามมันข้ามพรมแดนระหว่างเซอร์วิส เมื่อผู้ใช้รายงานปัญหา เราสามารถค้นเทรซด้วย ID แล้วเห็นภาพทั้งหมด: มีเซอร์วิสใดเกี่ยวข้องบ้าง แต่ละขั้นตอนใช้เวลานานเท่าไร และมีอะไรผิดพลาดตรงไหน

## เมตริก

เมตริกให้เลนส์ที่ต่างจากล็อกและเทรซ ในขณะที่รายการล็อกบอกเราเกี่ยวกับคำขอหนึ่งคำขอที่เฉพาะเจาะจง เมตริกให้ข้อมูลอนุกรมเวลาแบบรวมว่าแอปพลิเคชันของเราทำงานโดยรวมอย่างไร เมตริกตอบคำถามเช่น: ความหน่วงที่เปอร์เซ็นไทล์ที่ 99 เริ่มไต่ขึ้นเรื่อยๆ หรือเปล่า? อัตราข้อผิดพลาดเพิ่มเป็นสองเท่าในห้านาทีที่ผ่านมาหรือไม่? พูลการเชื่อมต่อฐานข้อมูลกำลังรับภาระหนักเกินไปหรือเปล่า?

- **axum-otel-metrics** ให้เมตริกแบบ OpenTelemetry พร้อมการส่งออกไปยัง Prometheus
- **axum-prometheus** ให้เมตริก HTTP ที่เข้ากันได้กับนิเวศของ metrics.rs

การตั้งค่าทั่วไปจะเปิดเผยเอนด์พอยต์ `/metrics` ให้ Prometheus เข้าไปเก็บข้อมูลเป็นช่วงเวลาปกติ จากประสบการณ์ของผม เมตริกที่มีประโยชน์ที่สุดสำหรับเว็บแอปพลิเคชันคือจำนวนคำขอ (แยกตามเมธอด เส้นทาง และรหัสสถานะ) ฮิสโทแกรมของระยะเวลาคำขอ และอัตราข้อผิดพลาด คุณอาจสงสัยว่าจำเป็นต้องมีทั้งสามอย่างตั้งแต่วันแรกหรือไม่ พูดตรงๆ ว่าแค่ระยะเวลาคำขอและอัตราข้อผิดพลาดก็จับปัญหาส่วนใหญ่ได้ก่อนที่ผู้ใช้จะสังเกตเห็นแล้ว

## การรวมทุกอย่างเข้าด้วยกัน

การตั้งค่าการสังเกตการณ์ที่พร้อมใช้ใน production ผสานทั้งสามอย่างนี้เข้าด้วยกัน ล็อกแบบมีโครงสร้างให้ข้อมูลละเอียดเกี่ยวกับเหตุการณ์แต่ละเหตุการณ์ เทรซให้เราเดินตามคำขอผ่านหลายเซอร์วิสเพื่อหาคอขวด และเมตริกให้ภาพรวมของสุขภาพระบบและแนวโน้มประสิทธิภาพ

การตั้งค่าทั้งหมดนี้อาจดูเหมือนงานใหญ่ที่ต้องทำล่วงหน้า และมันก็เป็นงานพอสมควรจริงๆ แต่มันคืนทุนให้ตัวเองตั้งแต่วันแรกที่คุณต้องดีบักปัญหาใน production แทนที่จะเดาว่าเกิดอะไรขึ้นแล้วดีพลอยต์แพตช์ลองผิดลองถูก คุณดูที่ข้อมูลแล้วเห็นสิ่งที่เกิดขึ้นจริงๆ ซึ่งเป็นจุดที่คุณอยากอยู่มากกว่า

เมื่อเรามีรากฐานการสังเกตการณ์เข้าที่แล้ว มาดูกันว่าเราจัดการข้อผิดพลาดและสื่อสารมันกับผู้ใช้ API ของเราอย่างชัดเจนได้อย่างไร
