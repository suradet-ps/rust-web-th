# โครงสร้างโปรเจกต์

ถ้าคุณเคยเปิดโปรเจกต์แล้วไม่รู้ว่าจะวางไฟล์ใหม่ของคุณตรงไหน คุณคงรู้ดีว่าโครงสร้างโฟลเดอร์สำคัญแค่ไหน ฟังดูเป็นเรื่องเล็ก แต่ผมเคยเห็นทีมเสียเวลาหลายชั่วโมงไปกับการถกเถียงว่าโค้ดควรอยู่ตรงไหน และเคยเห็นโปรเจกต์ที่ทุกอย่างไปจบรวมกันในไดเรกทอรี `src/` ยักษ์เดียวเพราะไม่มีใครตัดสินใจตั้งแต่ช่วงแรก ไม่สนุกเอาซะเลย

ไม่มีวิธีจัดโครงสร้างเว็บแอปพลิเคชัน Rust ที่ถูกต้องวิธีเดียว แต่มีแพตเทิร์นที่ใช้ได้ผลดีจริงในทางปฏิบัติ ในบทนี้เราจะดูสองแบบ นั่นคือโครงสร้างครีตเดียวสำหรับโปรเจกต์ขนาดเล็กถึงกลาง และโครงสร้างเวิร์กสเปซสำหรับตอนที่อะไรๆ โตขึ้น ทั้งสองแบบอยู่บนหลักการพื้นฐานเดียวกัน แค่คนละสเกลเท่านั้น

## หลักการ

ก่อนที่เราจะดูแผนผังไดเรกทอรีแบบเจาะจง ขอผมไล่ให้ฟังก่อนว่าแนวคิดอะไรที่ขับเคลื่อนโครงสร้างเหล่านี้

**จัดกลุ่มตามเลเยอร์สถาปัตยกรรมก่อน แล้วค่อยจัดตามความกังวล (concern) ภายในแต่ละเลเยอร์** การแบ่งหลักของเราคือระหว่าง `api`, `domain`, และ `infra` ซึ่งเป็นการบังคับใช้กฎของดีเพนเดนซีที่เราคุยกันก่อนหน้านี้ ภายในแต่ละเลเยอร์ เราจัดโมดูลตามความกังวล (แฮนด์เลอร์, โมเดล, รีพอสิทอรี) ขอบอกตรงๆ ว่าแบบนี้แปลว่าตอนทำงานกับฟีเจอร์ผู้ใช้ คุณยังต้องสลับไปมาระหว่าง `api/handlers/users.rs`, `domain/models/user.rs`, และ `infra/repositories/user_repo.rs` นี่คือการแลกเปลี่ยน (tradeoff) ที่เกิดขึ้นจริง เมื่อโค้ดเบสโตขึ้น บางทีมพบว่าการจัดภายในเลเยอร์ตามแนวฟีเจอร์ (feature slice) เช่น `domain/users/model.rs`, `domain/users/service.rs` มีประโยชน์มากกว่าการจัดตามบทบาทหน้าที่ วิธีไหนก็ใช้ได้ สิ่งที่สำคัญที่สุดคือขอบเขตของเลเยอร์ต้องชัดเจน

**บังคับทิศทางของดีเพนเดนซี** ข้อนี้คือข้อใหญ่ ดีเพนเดนซีควรไหลเข้าหาแกนกลาง จากเลเยอร์ HTTP เข้าหาโดเมน โมดูลโดเมนของคุณไม่ควร import อะไรจาก `api` หรือ `infra` เลย นี่คือสิ่งที่ทำให้ตรรกะทางธุรกิจของคุณพกพาได้และทดสอบแบบแยกเดี่ยวได้ ในโครงสร้างครีตเดียว คุณบังคับด้วยธรรมเนียมปฏิบัติและการรีวิวโค้ด (ซึ่งก็ใช่ คือต้องไว้ใจทีมของคุณ) ส่วนในเวิร์กสเปซ Cargo บังคับให้คุณผ่านกราฟดีเพนเดนซีของครีต ซึ่งดีกว่ามาก

**ทำให้ `main.rs` บาง** จุดเริ่มต้นของคุณควรทำสามอย่างเท่านั้น: โหลดการตั้งค่า สร้างแอปพลิเคชัน (ต่อสายดีเพนเดนซีเข้าด้วยกัน) แล้วเริ่มเซิร์ฟเวอร์ เท่านั้นแหละ ถ้า `main.rs` ของคุณเริ่มยาวขึ้น นั่นมักเป็นสัญญาณว่าตรรกะการจัดเตรียม (setup) ต้องย้ายไปอยู่ในโมดูลของตัวเอง

**ใช้การกำหนดระดับการเข้าถึงเพื่อสร้างขอบเขต** ระบบระดับการเข้าถึงของโมดูลใน Rust (`pub`, `pub(crate)`, `pub(super)`, และค่าเริ่มต้นคือ private) คือเครื่องมือของคุณในการควบคุมว่าโค้ดส่วนไหนเข้าถึงอะไรได้บ้าง เปิดเผยเฉพาะสิ่งที่ต้องเป็น public ผ่านไฟล์ `mod.rs` ของคุณ และเก็บรายละเอียดการนำไปใช้เป็น private ถ้าคุณมาจากฝั่ง JavaScript ลองนึกถึงแพตเทิร์น barrel-export แต่ถูกบังคับโดยคอมไพเลอร์แทนที่จะเป็นความตั้งใจที่ดี

### `main.rs` และ `lib.rs`

ไฟล์ `main.rs` คือจุดเริ่มต้นของเรา มันโหลดการตั้งค่า เริ่มต้น tracing สร้างแอปพลิเคชัน แล้วเริ่มเซิร์ฟเวอร์ มันทำแค่นี้ และผมอยากให้มันเป็นแบบนั้นต่อไป

```rust
use my_app::{config::Config, create_app, observability};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let config = Config::from_env()?;
    observability::init_tracing(&config.log_level);

    let app = create_app(config.clone()).await?;

    let addr = format!("0.0.0.0:{}", config.port);
    let listener = tokio::net::TcpListener::bind(&addr).await?;
    tracing::info!("listening on {}", listener.local_addr()?);
    axum::serve(listener, app)
        .with_graceful_shutdown(shutdown_signal()) // defined in the Deployment chapter
        .await?;

    Ok(())
}
```

ไฟล์ `lib.rs` ประกาศโมดูลของเราและจัดเตรียมฟังก์ชัน `create_app` นี่คือสิ่งที่การทดสอบการผสานของคุณจะเรียกด้วย ซึ่งแปลว่าการทดสอบของคุณทดสอบการต่อสายชุดเดียวกับระบบ production ผมชอบแพตเทิร์นนี้มากเพราะมันหมายความว่าไม่มีเส้นทางจัดเตรียม “สำหรับทดสอบเท่านั้น” ที่จะแอบเบี่ยงเบนไปจากของจริงได้เงียบๆ

```rust
pub mod api;
pub mod config;
pub mod domain;
pub mod error;
pub mod infra;
pub mod observability;

use axum::Router;
use config::Config;

pub async fn create_app(config: Config) -> anyhow::Result<Router> {
    let pool = infra::db::create_pool(
        config.database_url.expose_secret()
    ).await?;
    sqlx::migrate!("./migrations").run(&pool).await?;

    let state = AppState::new(config, pool);
    let router = api::routes::router(state);
    Ok(router)
}
```

### โมดูล `domain`

นี่คือหัวใจของแอปพลิเคชันของคุณ และมันควรมี**ดีเพนเดนซีเป็นศูนย์ต่อ Axum, SQLx หรือครีตเฟรมเวิร์กอื่นใด** ครีตภายนอกเดียวที่มันมักต้องใช้คือ `serde` (สำหรับการซีเรียลไลซ์), `thiserror` (สำหรับชนิดข้อมูลข้อผิดพลาด) และครีตอรรถประโยชน์พื้นฐานอย่าง `uuid` และ `chrono` อาจดูจำกัด แต่ข้อจำกัดนี้เองที่ทำให้เลเยอร์นี้ซื่อสัตย์ต่อหน้าที่ของมัน

ไดเรกทอรี `models/` เก็บเอนทิตีของโดเมนและวัตถุค่า (value object) ของคุณ ซึ่งเป็นชนิดข้อมูลที่แทนแนวคิดหลักที่แอปพลิเคชันของคุณทำงานด้วย ไดเรกทอรี `services/` คือที่อยู่ของตรรกะทางธุรกิจ โค้ดที่ทำงานกับโมเดลเหล่านั้น และ `errors.rs` นิยามชนิดข้อมูลข้อผิดพลาดเฉพาะของโดเมน

แล้วถ้าโดเมนของคุณต้องคุยกับโลกภายนอกล่ะ? ฐานข้อมูล, บริการอีเมล, API ของบุคคลที่สามบางเจ้า? มันนิยามสัญญาผ่านเทรตในไดเรกทอรี `ports/` ส่วนการนำเทรตเหล่านั้นไปปฏิบัติจริงจะอยู่ในฝั่ง `infra` เราจะเห็นแพตเทิร์นแบบนี้เพิ่มเติมในบทหลังๆ

### โมดูล `infra`

นี่คือที่อยู่ของโค้ดฐานข้อมูลของคุณ `db.rs` จัดการการสร้างพูลการเชื่อมต่อ และ `repositories/` เก็บการนำเทรตรีพอสิทอรีของโดเมนไปปฏิบัติจริงแบบรูปธรรม (concrete implementation)

แต่ละ struct ของรีพอสิทอรีถือรีเฟอเรนซ์ไปยังพูลการเชื่อมต่อและอิมพลีเมนต์เทรตที่ตรงกันจากเลเยอร์โดเมน หน้าที่ของมันคือแปลระหว่างชนิดข้อมูลแถว (row type) ของฐานข้อมูลกับชนิดข้อมูลโมเดลของโดเมน ลองนึกถึงนักแปลที่พูดได้ทั้งภาษา SQL และภาษาโดเมนของ Rust

### โมดูล `api`

นี่คือเลเยอร์เฉพาะของ Axum มันรู้จักแนวคิดของ HTTP อย่างรหัสสถานะ, บอดี้ JSON, ส่วนหัว และมิดเดิลแวร์ มันไม่ควรมีตรรกะทางธุรกิจ ถ้าคุณพบว่าตัวเองกำลังเขียนคำสั่ง `if` เกี่ยวกับกฎทางธุรกิจในแฮนด์เลอร์ นั่นคือสัญญาณว่าต้องย้ายมันเข้าเซอร์วิส

แฮนด์เลอร์ใน `handlers/` เป็นฟังก์ชันบางๆ ที่ดึงข้อมูลจากคำขอ เรียกเมธอดของเซอร์วิส แล้วส่งคืนการตอบกลับ ผมชอบให้มันสั้นมาก อุดมคติคือต่ำกว่า 20 บรรทัด `dtos/` นิยามรูปร่างของบอดี้คำขอและบอดี้การตอบกลับ โดยแยกจากโมเดลโดเมนเพื่อให้สัญญา API ของคุณพัฒนาได้โดยอิสระจากการแทนค่าภายในของคุณ `extractors/` เก็บตัวแยกข้อมูล (extractor) แบบกำหนดเองของ Axum อย่าง `ValidatedJson` หรือ `AuthUser` (เราจะสร้างมันในบทต่อๆ ไป) และ `middleware/` เก็บมิดเดิลแวร์ Tower แบบกำหนดเองใดๆ

สุดท้าย `routes.rs` ประกอบเราเตอร์ขึ้นมา โดยผสมกลุ่มเส้นทางแต่ละกลุ่มเข้าด้วยกันและประยุกต์ใช้เลเยอร์มิดเดิลแวร์

## โครงสร้างเวิร์กสเปซ

ถึงจุดหนึ่งโปรเจกต์ของคุณอาจโตจนเวลาในการคอมไพล์เริ่มบั่นทอน หรือบางทีคุณอาจมีหลายทีมทำงานบนคนละส่วนของระบบ นั่นคือตอนที่ผมจะเริ่มคิดแบ่งเป็น Cargo workspace เวิร์กสเปซบังคับกฎของดีเพนเดนซีในระดับครีต: ถ้าครีต `domain` ไม่ได้ระบุ `sqlx` ไว้ใน `Cargo.toml` ของมัน ก็ไม่มีใครเผลอ import มันที่นั่นได้ คอมไพเลอร์คอยช่วยคุณอยู่

`Cargo.toml` ระดับรากนิยามเวิร์กสเปซ และที่สำคัญไม่แพ้กันคือเวอร์ชันดีเพนเดนซีร่วมกัน นี่คือหนึ่งในฟีเจอร์ Cargo ที่ผมชอบที่สุด เพราะมันหมายความว่าคุณจะไม่จบลงด้วย `serde` สามเวอร์ชันต่างกันกระจายอยู่ตามครีตต่างๆ ของคุณ:

```toml
[workspace]
members = ["crates/*"]
resolver = "2"

[workspace.dependencies]
tokio = { version = "1", features = ["full"] }
serde = { version = "1", features = ["derive"] }
serde_json = "1"
sqlx = { version = "0.8", features = ["runtime-tokio-rustls", "postgres", "uuid", "chrono", "migrate"] }
axum = { version = "0.8", features = ["macros"] }
tower = "0.5"
tower-http = { version = "0.6", features = ["cors", "compression-gzip", "trace", "timeout", "request-id", "limit"] }
thiserror = "2"
anyhow = "1"
uuid = { version = "1", features = ["v4", "serde"] }
chrono = { version = "0.4", features = ["serde"] }
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
```

จากนั้นครีตแต่ละตัวก็สืบทอดเวอร์ชันร่วมเหล่านี้ด้วย `.workspace = true`:

```toml
# crates/domain/Cargo.toml
[package]
name = "domain"

[dependencies]
serde.workspace = true
thiserror.workspace = true
uuid.workspace = true
chrono.workspace = true
# Note: no axum, no sqlx
```

ประโยชน์หลักตรงนี้คือ Cargo เองที่ป้องกันการละเมิดสถาปัตยกรรม ถ้ามีคนในทีมของคุณพยายามเพิ่ม import ของ SQLx ในครีตโดเมน บิลด์ก็จะล้มเหลวเพราะ `sqlx` ไม่ได้อยู่ในรายการดีเพนเดนซีของมัน ผมเคยเห็นบั๊กจากความรู้สึกแบบ “อุ๊ย เผลอผูกโดเมนเข้ากับฐานข้อมูลซะแล้ว” มาเยอะพอที่ผมซาบซึ้งมากเวลาคอมไพเลอร์ช่วยจับแบบนี้ มันเป็นการการันตีที่แข็งแกร่งกว่าการพึ่งพาแค่การรีวิวโค้ดมาก

## เมื่อไหร่ควรเลือกแบบไหน

คำแนะนำของผม: เริ่มด้วยโครงสร้างครีตเดียว พูดจริงๆ มันให้ประโยชน์เชิงโครงสร้างทั้งหมดของการแยกอย่างสะอาดโดยไม่ต้องแบกภาระการจัดการเวิร์กสเปซ คุณแยกเป็นเวิร์กสเปซทีหลังได้เสมอเมื่อความต้องการเกิดขึ้นจริง และมันไม่ใช่รีแฟกเตอร์ที่ยากอะไรเพราะขอบเขตของโมดูลถูกวางไว้อยู่แล้ว

แล้วเมื่อไหร่ที่คุณควรย้ายไปเวิร์กสเปซจริงๆ ล่ะ? จากประสบการณ์ของผม มันคือตอนที่ข้อใดข้อหนึ่งต่อไปนี้เริ่มกัดกร่อน:

- เวลาคอมไพล์เริ่มเจ็บปวด และคุณอยากให้การคอมไพล์แบบเพิ่มหน่วย (incremental build) คอมไพล์เฉพาะส่วนที่เปลี่ยนเท่านั้น
- มีหลายทีมทำงานบนคนละส่วนของระบบ และคุณต้องการขอบเขตที่แข็งระหว่างพื้นที่ของแต่ละทีม
- คุณอยากเผยแพร่บางครีตอย่างอิสระ (เช่น ไลบรารีโดเมนร่วมที่ใช้โดยหลายเซอร์วิส)
- โปรเจกต์โตจนไดเรกทอรี `src/` เดียวเริ่มรู้สึกเทอะทะจัดการยาก

โครงสร้างเวิร์กสเปซยังทำงานได้ดีกับรูปแบบ monorepo ที่คุณมีหลายเซอร์วิส (เซิร์ฟเวอร์ API, วอร์กเกอร์เบื้องหลัง, เครื่องมือ CLI) ซึ่งใช้โค้ดโดเมนและอินฟราสตรักเจอร์ร่วมกัน เราจะพูดถึงรูปแบบดังกล่าวในบทหลังๆ เมื่อเราคุยเรื่องงานเบื้องหลัง
