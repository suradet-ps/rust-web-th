# HTTP ขาออกและความทนทานของบริการ

จนถึงตอนนี้เรามองเซอร์วิสของเราในฐานะเซิร์ฟเวอร์ ที่รับคำขอและส่งการตอบกลับ แต่ในทางปฏิบัติ เซอร์วิสส่วนใหญ่ก็เป็นไคลเอนต์ด้วยเช่นกัน เว็บเซิร์ฟเวอร์ของเราเรียกผู้ให้บริการชำระเงิน ส่งเว็บฮุก ควิวรี API ภายใน ดึงข้อมูลจากบุคคลที่สาม และส่งข้อความไปยังคิว ผมเคยเห็นระบบล่มที่ไม่มีอะไรเกี่ยวข้องกับวิธีที่เราจัดการทราฟฟิกขาเข้าเลย ปัญหาอยู่ที่วิธีที่เราเรียกออกไป ถ้าดีเพนเดนซีต้นทางปลายทาง (downstream) ช้าลงและคุณไม่มีรางกันชนที่ถูกต้อง มันจะพาเซอร์วิสทั้งตัวของคุณลงไปด้วย

ในบทนี้ เราจะเดินผ่านแพตเทิร์นที่ช่วยให้การเรียก HTTP ขาออกไม่ทำลายวันของคุณ: การหมดเวลา การลองใหม่ การถอยหน่วง การทำซ้ำแล้วได้ผลเหมือนเดิม การตัดวงจร และการส่งต่อบริบทเทรซ

## reqwest ในฐานะไคลเอนต์ HTTP

ครีต `reqwest` คือไคลเอนต์ HTTP ตัวเลือกหลักในนิเวศ Rust มันเป็น async โดยธรรมชาติ จัดการ TLS รองรับการทำพูลการเชื่อมต่อ และทำงานร่วมกับรันไทม์ Tokio ได้อย่างลงตัว สิ่งหนึ่งที่ทำให้หลายคนสะดุดตั้งแต่แรก: คุณควรสร้างอินสแตนซ์ `Client` ตัวเดียวตอนสตาร์ตอัปแล้วใช้ร่วมกันทั่วทั้งแอปพลิเคชันของคุณ `Client` จัดการพูลการเชื่อมต่อภายใน ดังนั้นถ้าคุณสร้างใหม่ทุกคำขอ คุณกำลังทิ้งประโยชน์ทั้งหมดของพูลนั้นไป

```rust
use reqwest::Client;
use std::time::Duration;

pub fn create_http_client() -> Client {
    Client::builder()
        .timeout(Duration::from_secs(10))
        .connect_timeout(Duration::from_secs(3))
        .pool_max_idle_per_host(10)
        .build()
        .expect("failed to create HTTP client")
}
```

เราจะเก็บไคลเอนต์ไว้ใน `AppState` ของเราและดึงมันออกมาใช้ในแฮนด์เลอร์หรือเซอร์วิสที่ต้องทำการเรียกขาออก ไคลเอนต์ตัวเดียวกันสามารถรองรับคำขอพร้อมกันหลายรายการได้อย่างปลอดภัย ซึ่งคือสิ่งที่เราต้องการพอดี

## การหมดเวลาในทุกระดับ

ถ้าผมต้องเลือกกลไกความทนทานหนึ่งอย่างสำหรับการเรียกขาออก มันคงเป็นการหมดเวลา (timeout) ถ้าไม่มีมัน เซอร์วิสต้นทางปลายทางที่ช้าหรือไม่ตอบสนองก็จะยึดการเชื่อมต่อของคุณไว้แบบไม่มีกำหนด ในที่สุดคุณจะใช้พูลการเชื่อมต่อ ตัวอธิบายไฟล์ หรือความจุในการจัดการคำขอของคุณจนหมด ผมเคยเห็นสิ่งนี้เกิดขึ้นใน production และมันไม่สนุกเลย

มีระดับการหมดเวลาสามระดับที่คุณควรคำนึงถึง:

**Connect timeout** ควบคุมว่าเราจะรอนานแค่ไหนเพื่อสร้างการเชื่อมต่อ TCP ถ้าเซิร์ฟเวอร์ระยะไกลเข้าถึงไม่ได้หรือเครือข่ายติดขัด คุณต้องการล้มเหลวเร็ว แทนที่จะรอค่าเริ่มต้นระดับระบบปฏิบัติการ (ซึ่งบน Linux อาจถึง 120 วินาที) สามถึงห้าวินาทีคือจุดเริ่มต้นที่สมเหตุสมผล

**Per-request timeout** จำกัดเวลาทั้งหมดสำหรับคำขอ HTTP หนึ่งรายการ รวมถึงการเชื่อมต่อ การจับมือ TLS การส่งคำขอ และการรับการตอบกลับทั้งหมด สิบถึงสามสิบวินาทีเป็นค่าทั่วไป แต่มันขึ้นอยู่กับว่าคุณคาดหวังให้ต้นทางปลายทางตอบสนองเร็วแค่ไหนจริงๆ

**Overall operation timeout** คือเส้นตายสำหรับปฏิบัติการทั้งหมด รวมถึงการลองใหม่ ถ้าตรรกะทางธุรกิจของคุณบอกว่า "ดึงสถานะการชำระเงินภายใน 30 วินาที" งบประมาณ 30 วินาทีนั้นครอบคลุมความพยายามลองใหม่ทั้งหมด ไม่ใช่แค่ครั้งเดียว ให้ใช้ `tokio::time::timeout` ครอบลูปการลองใหม่ทั้งหมด ไม่ใช่ครอบความพยายามแต่ละครั้ง

```rust
use tokio::time::timeout;

async fn fetch_with_deadline(
    client: &Client,
    url: &str,
    deadline: Duration,
) -> anyhow::Result<String> {
    timeout(deadline, async {
        // Individual attempts have their own timeout (via client config).
        // The outer timeout caps the total time including retries.
        let response = client.get(url).send().await?.error_for_status()?;
        Ok(response.text().await?)
    })
    .await
    .map_err(|_| anyhow::anyhow!("operation timed out after {:?}", deadline))?
}
```

## การลองใหม่และการถอยหน่วง

ความล้มเหลวชั่วคราวเป็นความจริงของชีวิตในระบบแบบกระจาย เครือข่ายสะดุด เซอร์วิสรีสตาร์ตสั้นๆ การหมดเวลาที่เกิดจากโหลด ทั้งหมดนี้สร้างข้อผิดพลาดที่ถ้าลองอีกครั้งอีกสักครู่ก็จะสำเร็จ ดังนั้นไคลเอนต์ขาออกที่ประพฤติดีควรลองใหม่กับความล้มเหลวเหล่านี้ โดยเพิ่มช่วงหน่วงระหว่างความพยายามเพื่อไม่ให้ซ้ำเติม

```rust
use std::time::Duration;
use tokio::time::sleep;

async fn fetch_with_retries(
    client: &Client,
    url: &str,
    max_retries: u32,
) -> anyhow::Result<reqwest::Response> {
    let mut last_error = None;

    for attempt in 0..=max_retries {
        if attempt > 0 {
            // Exponential backoff with jitter to prevent thundering herd.
            let base = Duration::from_millis(100 * 2u64.pow(attempt - 1));
            let jitter = Duration::from_millis(rand::random::<u64>() % 50);
            sleep(base + jitter).await;
        }

        match client.get(url).send().await {
            Ok(resp) if resp.status().is_server_error() => {
                // 5xx errors are retryable.
                last_error = Some(anyhow::anyhow!(
                    "server error: {}", resp.status()
                ));
            }
            Ok(resp) => return Ok(resp),
            Err(e) if e.is_timeout() || e.is_connect() => {
                // Timeouts and connection errors are retryable.
                last_error = Some(e.into());
            }
            Err(e) => return Err(e.into()), // Non-retryable error.
        }
    }

    Err(last_error.unwrap_or_else(|| anyhow::anyhow!("exhausted retries")))
}
```

เมื่อคุณกำลังสร้างกลยุทธ์การลองใหม่ มีการตัดสินใจสำคัญไม่กี่อย่างที่ต้องทำ:

**ข้อผิดพลาดไหนควรลองใหม่** ลองใหม่กับข้อผิดพลาดการเชื่อมต่อ การหมดเวลา และการตอบกลับ 5xx อย่าลองใหม่กับการตอบกลับ 4xx เพราะคำขอนั้นผิด และการส่งมันอีกครั้งก็ไม่ช่วยอะไร เช่นเดียวกับข้อผิดพลาดที่บ่งบอกปัญหาแบบถาวร เช่น ความล้มเหลวในการแก้ DNS สำหรับโดเมนที่ไม่มีอยู่จริง

**กลยุทธ์การถอยหน่วง** การถอยหน่วงแบบเอ็กซ์โปเนนเชียล (เพิ่มช่วงหน่วงเป็นสองเท่าในแต่ละครั้ง) ควบคู่กับ jitter (การเพิ่มองค์ประกอบสุ่มเล็กน้อย) คือแนวทางมาตรฐาน jitter สำคัญเพราะมันป้องกันปัญหาฝูงชนเหยียบกัน (thundering herd) ที่ไคลเอนต์จำนวนมากลองใหม่พร้อมกันพอดีหลังเหตุการณ์ล่มและทำให้เซอร์วิสที่กำลังฟื้นตัวท่วมท้น

**จำนวนความพยายามสูงสุด** การลองใหม่สามถึงห้าครั้งเป็นค่าทั่วไป มากกว่านั้นมักหมายความว่าต้นทางปลายทางล่มต่อเนื่อง และการลองใหม่ต่อไปก็แค่เพิ่มโหลดโดยไม่ช่วยอะไร

## การทำซ้ำแล้วได้ผลเหมือนเดิมของปฏิบัติการที่ลองใหม่

การลองใหม่กับคำขอ GET ปลอดภัยเพราะ GET ทำซ้ำแล้วได้ผลเหมือนเดิมตามนิยาม แต่การลองใหม่กับ POST ที่สร้างรีซอร์ส? นั่นเป็นเรื่องที่ต่างกัน เว้นแต่ API ต้นทางปลายทางจะรองรับคีย์ idempotency POST ที่ถูกลองใหม่สามารถสร้างระเบียนซ้ำ ซึ่งน่าจะเป็นสิ่งสุดท้ายที่คุณต้องการ

ถ้าคุณกำลังเรียก API ที่รองรับคีย์ idempotency (เช่น Stripe รับส่วนหัว `Idempotency-Key`) วิธีนั้นตรงไปตรงมา: สร้าง UUID สำหรับปฏิบัติการและใส่ลงในทุกความพยายาม:

```rust
let idempotency_key = Uuid::new_v4().to_string();

for attempt in 0..=max_retries {
    let result = client
        .post(url)
        .header("Idempotency-Key", &idempotency_key)
        .json(&payload)
        .send()
        .await;

    // Same retry logic as above.
}
```

แล้วถ้า API ต้นทางปลายทางไม่รองรับคีย์ idempotency ล่ะ? คุณมีสองทางเลือก: ออกแบบปฏิบัติการให้ทำซ้ำแล้วได้ผลเหมือนเดิมโดยธรรมชาติ (ใช้ PUT กับ ID ที่รู้จักแทนที่จะเป็น POST ไปยังคอลเล็กชัน) หรือไม่ลองใหม่กับปฏิบัติการแบบเขียนเลย และเปิดเผยความล้มเหลวเพื่อการแก้ไขด้วยมือ ไม่มีทางไหนสมบูรณ์แบบ แต่ทั้งสองดีกว่าการสร้างยอดเรียกเก็บซ้ำอย่างเงียบๆ

## การตัดวงจร (Circuit breaking)

คุณอาจสงสัย: ถ้าเซอร์วิสต้นทางปลายทางล้มเหลวอย่างต่อเนื่อง ทำไมยังส่งคำขอไปหามัน? คุณกำลังเสียทรัพยากรของตัวเองและเพิ่มโหลดให้กับระบบที่กำลังดิ้นรนอยู่แล้ว นี่คือที่มาของเซอร์กิตเบรกเกอร์ เซอร์กิตเบรกเกอร์ติดตามอัตราความล้มเหลว และเมื่อมันข้ามเกณฑ์ มันจะลัดวงจรคำขอในช่วงคูลดาวน์ก่อนจะลองอีกครั้ง

นิเวศ `tower` มี `tower-resilience` พร้อมมิดเดิลแวร์ circuit breaker, bulkhead, และ retry ที่คุณสามารถสแต็กต่อลงบนไคลเอนต์ reqwest หรือเซอร์วิส Tower ใดก็ได้ สำหรับความต้องการที่เรียบง่ายกว่า คุณสามารถสร้างเซอร์กิตเบรกเกอร์พื้นฐานด้วยตัวนับความล้มเหลว `AtomicU32` และ `tokio::time::Instant` สำหรับการบันทึกเวลาตรวจสอบครั้งล่าสุด

สามสถานะคือ:

- **Closed** (ปกติ): คำขอไหลผ่านได้ ความล้มเหลวเพิ่มตัวนับ
- **Open** (สะดุด): คำขอถูกปฏิเสธทันทีโดยไม่เรียกต้นทางปลายทาง หลังหมดเวลา เบรกเกอร์จะย้ายไปยัง half-open
- **Half-open** (ทดสอบ): คำขอหนึ่งรายการถูกปล่อยผ่าน ถ้ามันสำเร็จ เบรกเกอร์จะปิด ถ้ามันล้มเหลว มันจะเปิดใหม่

## การส่งต่อบริบทเทรซ

เมื่อเซอร์วิสของเราเรียกเซอร์วิสอื่น เราต้องการให้บริบทเทรซ (trace ID, span ID และการตัดสินใจสุ่มตัวอย่าง) เดินทางไปพร้อมกับคำขอ นี่คือสิ่งที่ทำให้คุณเชื่อมโยงล็อกและสแปนข้ามขอบเขตเซอร์วิสได้ และมันคือสิ่งที่ทำให้ distributed tracing มีประโยชน์จริงๆ แทนที่จะเป็นแค่เครื่องประดับ

ถ้าทั้งสองเซอร์วิสใช้ OpenTelemetry บริบทเทรซจะถูกส่งต่อผ่านส่วนหัว HTTP `traceparent` (ฟอร์แมต W3C Trace Context) ครีต `reqwest-tracing` หรือ `reqwest-middleware` สามารถฉีดส่วนหัวนี้โดยอัตโนมัติ ซึ่งดีมาก ถ้าคุณใช้การตั้งค่าที่เรียบง่ายกว่า อย่างน้อยที่สุดก็ส่งต่อ request ID ของคุณเป็นส่วนหัวแบบกำหนดเอง เพื่อให้คุณสามารถเชื่อมโยงล็อกด้วยมือได้ คุณจะขอบคุณตัวเองตอนตีสองเวลาที่คุณกำลังดีบักปัญหาที่เกิดใน production

```rust
let request_id = "req-abc-123"; // from the inbound request's span

let response = client
    .get(url)
    .header("x-request-id", request_id)
    .send()
    .await?;
```

## เมื่อไหร่ไม่ควรลองใหม่

ไม่ใช่ทุกความล้มเหลวที่ควรลองใหม่ นี่คือหนึ่งในสิ่งเหล่านั้นที่ดูเหมือนชัดเจนเมื่อคุณอ่าน แต่ในประสบการณ์ของผม มันง่ายที่จะทำผิด การลองใหม่แบบถล่มทลายกับเซอร์วิสที่โอเวอร์โหลดอยู่แล้วก็แค่ทำให้โอเวอร์โหลดแย่ลง นี่คือสถานการณ์ที่การลองใหม่เป็นการตัดสินใจที่ผิด:

- **ข้อผิดพลาดไคลเอนต์ 4xx** (ยกเว้น 429 Too Many Requests ซึ่งกำลังขอให้คุณถอยออกมาแล้วลองทีหลังอย่างชัดเจน)
- **ข้อผิดพลาดที่บ่งบอกปัญหาแบบถาวร** (ข้อมูลประจำตัวไม่ถูกต้อง รีซอร์สถูกลบ สกีมาไม่ตรงกัน)
- **เมื่อเส้นตายของปฏิบัติการหมดลงแล้ว** (ไม่มีประโยชน์ที่จะเริ่มความพยายามใหม่ถ้าผู้เรียกยอมแพ้ไปแล้ว)
- **เมื่อเซอร์กิตเบรกเกอร์เปิดอยู่** (รู้ว่าต้นทางปลายทางไม่แข็งแรง)

กฎทั่วไปที่ผมปฏิบัติตาม: ลองใหม่กับความล้มเหลวชั่วคราวด้วยการถอยหน่วง เคารพข้อจำกัดอัตราการเรียก และล้มเหลวเร็วเมื่อปัญหาเป็นเชิงโครงสร้าง มาดูกันว่าเราจะห่อทั้งหมดนี้เป็นอะไรที่สะอาดได้อย่างไร

## การห่อไคลเอนต์ขาออก

สำหรับเซอร์วิสต้นทางปลายทางที่แอปพลิเคชันของคุณเรียกบ่อยๆ ผมแนะนำให้ห่อ `reqwest::Client` ดิบๆ ใน struct ไคลเอนต์โดยเฉพาะ struct นี้ห่อหุ้ม base URL การยืนยันตัวตน นโยบายการหมดเวลา ตรรกะการลองใหม่ และการแปลงข้อผิดพลาดไว้ในที่เดียวทั้งหมด มองมันเป็นเวอร์ชันขาออกของแพตเทิร์นรีพอสิทอรีที่เราใช้สำหรับการเข้าถึงฐานข้อมูล

```rust
pub struct PaymentClient {
    http: Client,
    base_url: String,
    api_key: String,
}

impl PaymentClient {
    pub async fn charge(
        &self,
        amount_cents: i64,
        currency: &str,
        idempotency_key: &str,
    ) -> Result<PaymentResult, PaymentError> {
        let url = format!("{}/v1/charges", self.base_url);

        let response = self.http
            .post(&url)
            .bearer_auth(&self.api_key)
            .header("Idempotency-Key", idempotency_key)
            .json(&serde_json::json!({
                "amount": amount_cents,
                "currency": currency,
            }))
            .send()
            .await
            .map_err(PaymentError::Network)?;

        match response.status() {
            s if s.is_success() => {
                let result = response.json().await.map_err(PaymentError::Parse)?;
                Ok(result)
            }
            StatusCode::UNPROCESSABLE_ENTITY => {
                let body = response.text().await.unwrap_or_default();
                Err(PaymentError::Validation(body))
            }
            s => Err(PaymentError::Upstream(s)),
        }
    }
}
```

สิ่งนี้ทำให้เซอร์วิสโดเมนของเรามีอินเทอร์เฟซที่สะอาดและมีชนิดข้อมูลสำหรับดีเพนเดนซีต้นทางปลายทาง มันซ่อนรายละเอียด HTTP และให้จุดที่เป็นธรรมชาติแก่เราในการสอดใส่การลองใหม่ การตัดวงจร และเมตริกในภายหลังโดยไม่ต้องแตะโค้ดผู้เรียก สิ่งที่ผมพบคือแพตเทิร์นนี้คืนทุนให้ตัวเองอย่างรวดเร็ว โดยเฉพาะเมื่อจำนวนดีเพนเดนซีต้นทางปลายทางเพิ่มขึ้น
