# แพตเทิร์นสถาปัตยกรรม

ถ้าคุณเคยทำงานบนโค้ดเบสที่ตรรกะควิวรีฐานข้อมูลปนอยู่ใน HTTP แฮนด์เลอร์ และกฎทางธุรกิจกระจายอยู่สามแห่ง คุณคงรู้ว่ามันเจ็บปวดแค่ไหนเมื่อเวลาผ่านไป ผมเคยเจอมาแล้วมากกว่าหนึ่งครั้ง และมันจบลงแบบเดิมเสมอ: คุณกลัวที่จะเปลี่ยนอะไรเพราะบอกไม่ได้ว่าอะไรขึ้นอยู่กับอะไร

บทนี้ว่าด้วยแพตเทิร์นที่ป้องกันความเละเทะแบบนั้น เราจะดูวิธีจัดโครงสร้างเว็บแอปพลิเคชัน Rust ให้ชิ้นส่วนต่างๆ ยังสะอาดและเป็นอิสระต่อกัน ผมจะไม่ชี้ขาดว่าทางเดียวที่ถูกต้องคืออะไร เพราะระดับโครงสร้างที่เหมาะสมขึ้นอยู่กับโปรเจกต์ของคุณ แต่ผมอยากให้คุณเข้าใจตัวเลือกต่างๆ ดีพอที่จะตัดสินใจเอง

เส้นด้ายร่วมของแพตเทิร์นทั้งหมดนี้คือ**กฎของดีเพนเดนซี**: ดีเพนเดนซีชี้เข้าหาแกนกลาง จากอินฟราสตรักเจอร์ไปสู่โดเมน ตรรกะทางธุรกิจของคุณไม่ควรรู้จักรหัสสถานะ HTTP, ควิวรี SQL หรือว่าเว็บเฟรมเวิร์กไหนที่คุณใช้อยู่ เมื่อคุณทำข้อนี้ถูก โดเมนของคุณจะพกพาได้ ทดสอบได้ และวิวัฒนาการได้ง่ายอย่างน่าประหลาดใจเมื่อสิ่งรอบข้างมันเปลี่ยนไป

## โมเดลแบบเลเยอร์

สถาปัตยกรรมที่เรียบง่ายที่สุดที่ยืนหยัดได้จริงใน production แบ่งโค้ดของคุณเป็นสามเลเยอร์ คุณอาจเคยเห็นอะไรทำนองนี้ในเวอร์ชันใดเวอร์ชันหนึ่งมาก่อนแล้ว แต่มาดูกันว่าแต่ละเลเยอร์ทำอะไร และที่สำคัญกว่าคือมันไม่ควรทำอะไร

```
┌──────────────────────────────────────────────┐
│   API Layer                                  │
│   Handlers, routes, middleware, DTOs         │
│   Knows about: Axum, HTTP, JSON              │
├──────────────────────────────────────────────┤
│   Domain Layer                               │
│   Models, services, business rules, ports    │
│   Knows about: nothing external              │
├──────────────────────────────────────────────┤
│   Infrastructure Layer                       │
│   Repositories, database, external APIs      │
│   Knows about: SQLx, Diesel, reqwest, etc.   │
└──────────────────────────────────────────────┘
```

เลเยอร์ API คือเลเยอร์แปลภาษาระหว่าง HTTP กับโดเมนของคุณ มันดีซีเรียลไลซ์บอดี้คำขอให้เป็นชนิดข้อมูลของโดเมน เรียกเมธอดเซอร์วิส แล้วซีเรียลไลซ์ผลลัพธ์กลับเป็นการตอบสนอง HTTP ให้มันบางไว้ ถ้าคุณพบว่าตัวเองกำลังเขียนตรรกะทางธุรกิจในแฮนด์เลอร์ ให้หยุด ตรรกะนั้นควรอยู่ที่เลเยอร์โดเมน ผมเห็นแฮนด์เลอร์กลายเป็นสัตว์ประหลาดสองร้อยบรรทัดมามากพอที่จะรู้ว่าควรเคร่งครัดกับเรื่องนี้ตั้งแต่เนิ่นๆ

เลเยอร์โดเมนคือหัวใจของทั้งหมด นี่คือที่อยู่ของเอนทิตีทางธุรกิจ วัตถุค่า (value object) ฟังก์ชันเซอร์วิส และนิยามเทรต (พอร์ต) ที่อธิบายว่าโดเมนต้องการอะไรจากโลกภายนอก อย่าง “บันทึกผู้ใช้” หรือ “ส่งการแจ้งเตือน” จุดสำคัญคือ: เลเยอร์นี้ไม่รู้เลยว่าความสามารถเหล่านั้นถูกนำไปปฏิบัติจริงอย่างไร มันไม่ import `sqlx` หรือ `axum` หรือครีตเฟรมเวิร์กอื่นใด มันเป็นเพียงตรรกะทางธุรกิจบริสุทธิ์

เลเยอร์อินฟราสตรักเจอร์จัดหาการนำเทรตของโดเมนไปปฏิบัติจริงแบบรูปธรรม มันรู้จักฐานข้อมูลเฉพาะ, API HTTP ภายนอก, ผู้ให้บริการอีเมล, คิวข้อความ อะไรทำนองนั้นทั้งหมด มันขึ้นอยู่กับเลเยอร์โดเมน (เพราะมันอิมพลีเมนต์เทรตของโดเมน) แต่เลเยอร์โดเมนไม่ต้องพึ่งมันเลย ดีเพนเดนซีทางเดียวแบบนี้เองที่ทำให้ทั้งหมดทำงานได้

### ทำไมลำดับนี้จึงสำคัญ

คุณอาจมองแผนภาพนี้แล้วคิดว่า “โอเค ไดอะแกรมสวยดี แต่ในทางปฏิบัติมันสำคัญจริงหรือ?” จริงๆ แล้วสำคัญมาก ขอผมยกผลตอบแทนที่เป็นรูปธรรมให้ดู

เมื่อโดเมนของคุณไม่ขึ้นอยู่กับฐานข้อมูล คุณจะทดสอบตรรกะทางธุรกิจได้โดยเสียบอิมพลีเมนเทชันในหน่วยความจำง่ายๆ ของเทรตรีพอสิทอรี ไม่ต้องรัน PostgreSQL ทั้งอินสแตนซ์เพื่อพิสูจน์ว่าการคำนวณราคาของคุณถูกต้อง ชุดทดสอบของคุณรันจบในหน่วยมิลลิวินาที และคุณรันมันบนเครื่องบินได้ด้วย ผมชอบข้อนี้มาก

เมื่อโดเมนของคุณไม่ขึ้นอยู่กับ Axum คุณจะนำมันกลับมาใช้ในเครื่องมือ CLI, วอร์กเกอร์เบื้องหลัง หรือเซอร์วิส gRPC ได้โดยไม่ต้องลากเลเยอร์ HTTP ทั้งหมดไปเป็นลูกหาบด้วย

และเมื่อการนำไปปฏิบัติจริงฝั่งฐานข้อมูลของคุณเปลี่ยน (เช่นคุณไมเกรตจาก PostgreSQL ไป CockroachDB หรือสลับจาก SQLx เป็น Diesel) เลเยอร์โดเมนก็ไม่ต้องเปลี่ยนอะไรเลย คุณเขียนเลเยอร์อินฟราสตรักเจอร์ใหม่ แล้วแอปพลิเคชันส่วนที่เหลือไม่รู้สึกตัวด้วยซ้ำ ผมเคยทำไมเกรชันแบบนี้บนโปรเจกต์จริง และมันราบรื่นเกินคาดมาก เพราะเรามีการแยกแบบนี้อยู่แล้ว

## การแยกชั้นเชิงนามธรรมด้วยเทรต (พอร์ตและอะแดปเตอร์)

แล้วเราบังคับการแยกนี้ใน Rust ได้อย่างไร? ด้วยเทรต เลเยอร์โดเมนนิยามเทรตที่อธิบายการดำเนินการที่มันต้องการ เลเยอร์อินฟราสตรักเจอร์จัดหา struct ที่อิมพลีเมนต์เทรตเหล่านั้น และเลเยอร์แอปพลิเคชันต่อสายทุกอย่างเข้าด้วยกันตอนเริ่มระบบ ถ้าคุณเคยทำงานกับอินเทอร์เฟซในภาษาอื่น คุณจะรู้สึกคุ้นเคยกับแนวคิดนี้ แต่ระบบเทรตของ Rust ยังให้การการันตีตอนคอมไพล์ที่ดีงามเพิ่มอีกชั้น

นี่คือหน้าตาของพอร์ตรีพอสิทอรีในเลเยอร์โดเมน:

```rust
// domain/ports/user_repository.rs

use std::future::Future;
use crate::domain::models::{User, UserId, Email};
use crate::domain::errors::CreateUserError;

pub trait UserRepository: Send + Sync + 'static {
    fn create(
        &self,
        req: &CreateUserRequest,
    ) -> impl Future<Output = Result<User, CreateUserError>> + Send;

    fn find_by_id(
        &self,
        id: &UserId,
    ) -> impl Future<Output = Result<Option<User>, anyhow::Error>> + Send;

    fn find_by_email(
        &self,
        email: &Email,
    ) -> impl Future<Output = Result<Option<User>, anyhow::Error>> + Send;
}
```

มีบางอย่างเกี่ยวกับขอบเขตเทรต (trait bound) ที่ควรสังเกต ขอบเขต `Send + Sync + 'static` มีไว้เพราะ Axum ต้องแชร์สถานะข้ามทาสก์แอซิงก์ที่อาจรันบนเธรดต่างกัน ถ้าคุณเคยสู้กับคอมไพล์เออร์รอร์แบบ “future is not Send” นี่คือเหตุผลที่ขอบเขตเหล่านั้นสำคัญ ตั้งแต่ Rust 1.75 เป็นต้นมา `async fn` ในเทรตและ `impl Trait` แบบ return-position เสถียรแล้ว คุณจึงเขียนลายเซ็นเหล่านี้ได้โดยไม่ต้องใช้มาโคร `#[async_trait]` นั่นคือการเปลี่ยนแปลงที่ยินดีต้อนรับมาก

แต่มีข้อจำกัดสองอย่างที่ควรรู้ อย่างแรก เทรตที่ใช้ `-> impl Future` หรือ `async fn` จะ**ไม่เป็น object-safe** ซึ่งแปลว่าคุณใช้มันเป็น trait object (`dyn Trait`) ไม่ได้ พูดให้ชัดคือ `Arc<dyn UserRepository>` จะคอมไพล์ไม่ผ่าน ถ้าคุณต้องการไดนามิกดิสแพตช์ (เราจะพูดถึงด้านล่าง) คุณยังต้องใช้ครีต `async_trait` หรือไม่ก็บ็อกซ์ future ด้วยมือ แพตเทิร์นที่แสดงตรงนี้ทำงานกับสแตติกดิสแพตช์ (เจนเนอริก) ซึ่งคือสิ่งที่ผมแนะนำให้ใช้เป็นค่าเริ่มต้น

อย่างที่สอง สำหรับ**เทรตไลบรารีสาธารณะ** (ตรงข้ามกับพอร์ตภายในของแอปพลิเคชัน) `async fn` เปล่าๆ เป็นปัญหาเพราะผู้เรียกไม่สามารถเพิ่มขอบเขตอย่าง `Send` ให้กับ future ที่ส่งกลับได้โดยไม่ทำลาย API (breaking change) ถ้าคุณกำลังเขียนเทรตที่จะถูกใช้โดยโค้ดภายนอกครีตของคุณ ลองพิจารณาใช้ครีต `trait_variant` (จาก Rust async working group) เพื่อสร้างวาเรียนต์ `Send` ให้อัตโนมัติ:

```rust
#[trait_variant::make(UserRepositorySend: Send)]
pub trait UserRepository { ... }
```

สำหรับพอร์ตภายในของแอปพลิเคชัน (ซึ่งคือสิ่งที่เซอร์วิส Axum ส่วนใหญ่ต้องการ) เทรตแอซิงก์แบบเนทีฟทำงานได้ดีเยี่ยม

อีกเรื่องเล็กๆ หนึ่ง: สังเกตว่า `Clone` ไม่ได้อยู่ในนิยามเทรต ความสามารถในการโคลนเป็นคุณสมบัติของผู้ถือ (wrapper `Arc`, struct `AppState`) ไม่ใช่ข้อกำหนดของสัญญาโดเมนเอง การนำเทรตรีพอสิทอรีไปปฏิบัติจริงแบบรูปธรรมของคุณยัง derive `Clone` ได้ถ้าจำเป็น การไม่ใส่ `Clone` ไว้ในเทรตช่วยให้สัญญาโฟกัสกับสิ่งที่โดเมนสนใจจริงๆ

ต่อไปมาดูการนำไปปฏิบัติจริงแบบรูปธรรมในเลเยอร์อินฟราสตรักเจอร์:

```rust
// infra/repositories/postgres_user_repo.rs

use domain::ports::UserRepository;

#[derive(Clone)]
pub struct PostgresUserRepo {
    pool: PgPool,
}

impl PostgresUserRepo {
    pub fn new(pool: PgPool) -> Self {
        Self { pool }
    }
}

impl UserRepository for PostgresUserRepo {
    async fn create(&self, req: &CreateUserRequest) -> Result<User, CreateUserError> {
        let row = sqlx::query_as!(
            UserRow,
            r#"INSERT INTO users (id, email, name, password_hash)
               VALUES ($1, $2, $3, $4)
               RETURNING *"#,
            Uuid::new_v4(),
            req.email.as_str(),
            req.name.as_str(),
            req.password_hash,
        )
        .fetch_one(&self.pool)
        .await
        .map_err(|e| match e {
            sqlx::Error::Database(ref db_err) if db_err.is_unique_violation() => {
                CreateUserError::Duplicate { email: req.email.clone() }
            }
            other => CreateUserError::Unknown(other.into()),
        })?;

        Ok(row.into())
    }

    // ... other methods
}
```

สังเกตว่าเลเยอร์อินฟราสตรักเจอร์แปลข้อผิดพลาดเฉพาะของฐานข้อมูล (เช่นการละเมิดคอนสเตรนต์เอกลักษณ์) เป็นข้อผิดพลาดเฉพาะของโดเมน ชนิดข้อมูลข้อผิดพลาดของโดเมนรู้จัก “ผู้ใช้ซ้ำ” ไม่ใช่รหัสข้อผิดพลาดของ SQL นี่คือเรื่องเล็กที่สร้างความต่างอย่างใหญ่หลวงตอนคุณดีบั๊กตอนตีสอง เพราะข้อความข้อผิดพลาดของคุณจะบอกจริงๆ ว่ามีอะไรผิดพลาดในเชิงธุรกิจ

## เลเยอร์เซอร์วิส

เซอร์วิสอยู่ภายในเลเยอร์โดเมนและทำหน้าที่ออร์เคสตราตรรกะทางธุรกิจ พวกมันรับพอร์ตของโดเมนเป็นพารามิเตอร์เจนเนอริก (หรือเป็น trait object ถ้าคุณเลือกเส้นทางไดนามิกดิสแพตช์) เรียกตามลำดับที่ถูกต้อง และบังคับใช้กฎทางธุรกิจ นี่คือที่อยู่ของของที่น่าสนใจ ถ้าคุณอยากเข้าใจว่าแอปพลิเคชันทำอะไรจริงๆ คุณควรอ่านเลเยอร์เซอร์วิสแล้วเห็นภาพทั้งหมดได้โดยไม่ต้องมุดผ่านความกังวลเรื่อง HTTP หรือควิวรี SQL

```rust
// domain/services/user_service.rs

#[derive(Clone)]
pub struct UserService<R: UserRepository> {
    repo: R,
}

impl<R: UserRepository> UserService<R> {
    pub fn new(repo: R) -> Self {
        Self { repo }
    }

    pub async fn register(
        &self,
        name: UserName,
        email: Email,
        password: &str,
    ) -> Result<User, CreateUserError> {
        let password_hash = hash_password(password)?;

        let req = CreateUserRequest {
            name,
            email,
            password_hash,
        };

        self.repo.create(&req).await
    }

    pub async fn get_by_id(&self, id: &UserId) -> Result<Option<User>, anyhow::Error> {
        self.repo.find_by_id(id).await
    }
}
```

เซอร์วิสไม่รู้เลยว่า `R` คือรีพอสิทอรี PostgreSQL มันอาจเป็นอิมพลีเมนเทชันในหน่วยความจำที่ใช้ในทดสอบ หรือ wrapper แคชที่เช็ก Redis ก่อนจะไปที่ฐานข้อมูล เซอร์วิสรู้อีกแค่ว่าไม่ว่า `R` จะเป็นอะไร มันก็เป็นไปตามสัญญา `UserRepository` นั่นคือเวทมนตร์ทั้งหมดของแพตเทิร์นนี้ และมันคือสิ่งที่ทำให้การเขียนทดสอบสำหรับตรรกะทางธุรกิจของคุณน่าทำจริงๆ

## สแตติกดิสแพตช์กับไดนามิกดิสแพตช์

เมื่อคุณใช้การแยกชั้นเชิงนามธรรมด้วยเทรตแล้ว คุณจะเจอคำถามนี้: ควรใช้เจนเนอริก (สแตติกดิสแพตช์) หรือ trait object (ไดนามิกดิสแพตช์)? การทำความเข้าใจการแลกเปลี่ยนนี้ไว้เป็นเรื่องคุ้มค่า

**สแตติกดิสแพตช์** ใช้เจนเนอริก คอมไพเลอร์ทำ monomorphize (สร้างโค้ดเฉพาะชนิด) ให้กับชนิดข้อมูลรูปธรรมแต่ละชนิด ซึ่งแปลว่าไม่มีโอเวอร์เฮดตอนรันไทม์จากการเรียกแบบเสมือน (virtual dispatch) นี่คือแนวทางที่เราใช้ข้างบนกับ `UserService<R: UserRepository>`

```rust
// Static dispatch: zero runtime cost, resolved at compile time
pub struct UserService<R: UserRepository> {
    repo: R,
}
```

**ไดนามิกดิสแพตช์** ใช้ trait object ภายใต้ `Arc` การเรียกเมธอดวิ่งผ่าน vtable ตอนรันไทม์ ซึ่งเพิ่มโอเวอร์เฮดเล็กน้อย ในทางปฏิบัตินี่เล็กน้อยจนแทบไม่รู้สึกสำหรับเว็บแอปพลิเคชันที่รอบไปกลับฐานข้อมูลกินงบประมาณความหน่วงเป็นส่วนใหญ่อยู่แล้ว จุดดีคือลายเซ็นชนิดข้อมูลที่เรียบง่ายกว่าและสลับเปลี่ยนได้ง่ายกว่าตอนรันไทม์

แต่มีเงื่อนงำอยู่: เทรตที่ใช้ `-> impl Future` หรือ `async fn` ไม่เป็น object-safe ใน Rust คุณจึงใช้มันกับ `dyn Trait` โดยตรงไม่ได้ ถ้าคุณต้องการไดนามิกดิสแพตช์ คุณมีสองทางเลือก ครีต `async_trait` เขียนเมธอดแอซิงก์ใหม่ให้เป็น boxed future ทำให้เทรตเป็น object-safe:

```rust
use async_trait::async_trait;

#[async_trait]
pub trait UserRepository: Send + Sync + 'static {
    async fn create(&self, req: &CreateUserRequest) -> Result<User, CreateUserError>;
    async fn find_by_id(&self, id: UserId) -> anyhow::Result<Option<User>>;
}

// Now this works:
pub struct UserService {
    repo: Arc<dyn UserRepository>,
}
```

คุณจะเขียน boxed future ด้วยมือก็ได้ แต่พูดตรงๆ มาโคร `async_trait` ทำสิ่งเดียวกันด้วยโบยเลอร์เพลตที่น้อยกว่า และมันไม่คุ้มที่จะพิมพ์เพิ่ม

คำแนะนำของผม: **เริ่มด้วยสแตติกดิสแพตช์** การการันตีตอนคอมไพล์แข็งแกร่งกว่า ข้อความข้อผิดพลาดชัดเจนกว่า และคุณเลี่ยงคำถามเรื่อง object-safety ไปได้ทั้งเรื่อง หันไปใช้ไดนามิกดิสแพตช์เมื่อคุณต้องการความยืดหยุ่นตอนรันไทม์จริงๆ อย่างการสลับอิมพลีเมนเทชันตามการตั้งค่า หรือเมื่อพารามิเตอร์เจนเนอริกเริ่มทำให้ลายเซ็นของคุณเทอะทะพะรุงพะรังข้ามหลายเลเยอร์ คุณจะรู้เองว่าถึงจุดนั้นแล้ว เพราะคุณจะจ้องลายเซ็นชนิดข้อมูลที่ดูเหมือนซุปตัวอักษร

## สถาปัตยกรรมเฮกซะโกนัลและสถาปัตยกรรมแบบหัวหอม

ถ้าคุณเคยใช้เวลาอ่านเรื่องสถาปัตยกรรมซอฟต์แวร์บ้าง คุณคงเคยชนกับศัพท์สองคำนี้ มันฟังดูเลิศหรู แต่จริงๆ แล้วมันเป็นเพียงรูปแบบแปรผันของแนวคิดแกนกลางเดียวกับที่เราคุยกันมา นั่นคือวางโดเมนไว้ตรงกลาง แล้วดันโค้ดเฉพาะเฟรมเวิร์กออกไปที่ขอบ

**สถาปัตยกรรมเฮกซะโกนัล** (หรือที่เรียกว่าพอร์ตและอะแดปเตอร์) เน้นความสมมาตรระหว่างอะแดปเตอร์ขาเข้า (inbound adapter) ซึ่งคือสิ่งที่เรียกเข้ามาหาโดเมนของคุณ อย่าง HTTP แฮนด์เลอร์หรือเซิร์ฟเวอร์ gRPC กับอะแดปเตอร์ขาออก (outbound adapter) ซึ่งคือสิ่งที่โดเมนของคุณเรียกออกไป อย่างฐานข้อมูลหรือบริการอีเมล “พอร์ต” คือนิยามเทรต และ “อะแดปเตอร์” คือการนำไปปฏิบัติจริงแบบรูปธรรม เราทำแบบนี้อยู่แล้ว

**สถาปัตยกรรมแบบหัวหอม** มองภาพแนวคิดเดียวกันเป็นวงแหวนที่ซ้อนกันโดยมีศูนย์กลางร่วม วงแหวนในสุดคือแบบจำลองโดเมน วงถัดออกมาคือเลเยอร์แอปพลิเคชัน/เซอร์วิส จากนั้นคือเลเยอร์อินฟราสตรักเจอร์ และวงนอกสุดคือเลเยอร์การนำเสนอ (presentation) ดีเพนเดนซีชี้เข้าหาแกนกลางเสมอ

ในทางปฏิบัติ สิ่งเหล่านี้คือชื่อที่ต่างกันของแพตเทิร์นพื้นฐานเดียวกัน โมเดลสามเลเยอร์ที่เราไล่ดูตอนต้นบทคือการนำแนวคิดเหล่านี้ไปใช้จริงในเชิงปฏิบัติ คุณไม่จำเป็นต้องรับเอาระบบการตั้งชื่อแบบใดแบบหนึ่ง หรือทำตามโครงสร้างทางการเป๊ะๆ สิ่งที่ผมสนใจ (และที่คุณควรสนใจ) คือกฎของดีเพนเดนซีต้องเป็นที่เข้าใจและถูกบังคับใช้ ป้ายชื่อก็แค่ป้ายชื่อ

## การเลือกระดับของสถาปัตยกรรมที่เหมาะสม

หัวใจของผมคือคนเชิงปฏิบัติ และอยากพูดตรงๆ กับคุณ: ไม่ใช่ทุกโปรเจกต์ที่ต้องการสถาปัตยกรรมเฮกซะโกนัลเต็มรูปแบบพร้อมพอร์ตแบบเทรต เซอร์วิสเจนเนอริก และเวิร์กสเปซห้าครีต Over-engineering คือต้นทุนจริง มันเพิ่มโบยเลอร์เพลต เพิ่มภาระทางปัญญา (cognitive overhead) และถ่วงความเร็วการพัฒนาเพื่อผลประโยชน์ที่อาจไม่เกิดขึ้นจริง ผมเองก็ over-engineer อะไรหลายอย่างและเสียใจทุกครั้ง

นี่คือแนวทางคร่าวๆ ที่อิงกับสิ่งที่ผมพบว่าใช้ได้ผลดี:

**โมดูลเรียบๆ (flat module)** เหมาะกับโปรโตไทป์, API เล็กๆ และโปรเจกต์ที่มีเอนด์พอยต์ไม่กี่ตัว วางแฮนด์เลอร์ โมเดล และควิวรีในโมดูลแยกกัน แต่ไม่ต้องวุ่นวายกับเทรตหรือเลเยอร์เซอร์วิส คุณรีแฟกเตอร์ทีหลังได้เสมอ และสำหรับเซอร์วิสเล็กๆ แนวทางที่ง่ายกว่าคือสิ่งที่ดีกว่าจริงๆ

**สถาปัตยกรรมแบบเลเยอร์ (โครงสร้างครีตเดียว)** คือจุดหวานสำหรับแอปพลิเคชัน production ส่วนใหญ่ แยกโดเมนของคุณออกจากอินฟราสตรักเจอร์ ใช้เซอร์วิสเพื่อห่อหุ้มตรรกะทางธุรกิจ และทำให้แฮนด์เลอร์บาง สิ่งนี้ให้ความสามารถในการทดสอบและการดูแลรักษาโดยไม่ต้องมีพิธีรีตองเกินจำเป็น ถ้าคุณกำลังสร้างอะไรที่จะรันใน production และถูกดูแลโดยทีม นี่น่าจะเป็นจุดที่คุณอยากเริ่ม

**สถาปัตยกรรมเฮกซะโกนัล/แบบหัวหอม (เวิร์กสเปซ)** สมเหตุสมผลเมื่อคุณมีโดเมนซับซ้อนพร้อมตรรกะทางธุรกิจจำนวนมาก มีหลายทีมทำงานคู่ขนาน หรือจำเป็นต้องรองรับช่องทางขาเข้าหลายช่องทาง (HTTP, gRPC, CLI, ผู้บริโภคข้อความ) กับโดเมนเดียวกัน การลงทุนช่วงแรกมีจริง แต่มันคืนกำไรตลอดอายุขัยของโค้ดเบสที่อยู่ยาวนาน ผมเคยทำงานในโปรเจกต์แบบนี้ที่การแยกที่สะอาดช่วยประหยัดความเจ็บปวดจากการรีแฟกเตอร์หลายสัปดาห์ในภายหลัง

สิ่งสำคัญคือเริ่มด้วยการแยกระหว่างเลเยอร์ให้ชัดเจน แม้ในโครงสร้างที่เรียบง่ายที่สุด แพตเทิร์นเฉพาะที่คุณใช้บังคับการแยกนั้นจะวิวัฒนาการไปตามการเติบโตของโปรเจกต์ การย้ายจากการเรียกฟังก์ชันโดยตรงไปเป็นการแยกชั้นเชิงนามธรรมด้วยเทรตคือรีแฟกเตอร์ที่ตรงไปตรงมาเมื่อขอบเขตของโมดูลสะอาดอยู่แล้ว ดังนั้นอย่ากดดันตัวเองให้ได้สถาปัตยกรรม “สมบูรณ์แบบ” ตั้งแต่วันแรก ทำให้เลเยอร์ถูกต้อง ที่เหลือจะตามมาเอง
