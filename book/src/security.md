# ความปลอดภัย

ถ้ามีสิ่งหนึ่งที่ผมอยากให้คุณได้จากหนังสือเล่มนี้ มันคือความปลอดภัยไม่ใช่สิ่งที่คุณติดตั้งเพิ่มทีหลังตอนจบ มันคือชุดแนวปฏิบัติที่ดำรงอยู่ในทุกเลเยอร์ของแอปพลิเคชันคุณ ตั้งแต่วิธีจัดการอินพุตจากผู้ใช้จนถึงวิธีตั้งค่าการดีพลอยต์ของคุณ เราแตะเรื่องความปลอดภัยตลอดบทก่อนหน้านี้ บทนี้จึงรวบรวมเส้นด้ายทั้งหมดนั้นเข้าเป็นข้อมูลอ้างอิงชิ้นเดียว และผมยังใส่หัวข้อสองสามหัวข้อที่ไปไม่ลงตัวกับที่อื่นมาไว้ที่นี่ด้วย

## การจัดการอินพุต

แนวป้องกันแรกของเราง่ายมาก: มองว่าอินพุตภายนอกทั้งหมดไม่น่าเชื่อถือ คุณอาจคิดว่านี่ชัดเจนอยู่แล้ว แต่มันง่ายมากที่จะเผลอวางการ์ดลงเมื่อคุณควบคุมทั้งฝั่งไคลเอนต์และเซิร์ฟเวอร์ อย่าทำแบบนั้น

**ใช้ควิวรีแบบมีพารามิเตอร์เท่านั้น** ห้ามสร้าง SQL ด้วยการต่อสตริงเด็ดขาด ทุกควิวรีฐานข้อมูลควรใช้ตัววางพารามิเตอร์ (`$1`, `$2`, ฯลฯ) พร้อมค่าที่ถูกผูกไว้ มาโคร `query!` และ `query_as!` ของ SQLx บังคับเรื่องนี้ตอนคอมไพล์ ซึ่งพูดตรงๆ ว่านี่คือหนึ่งในเหตุผลที่แข็งแกร่งที่สุดที่จะใช้มัน

**ตรวจสอบความถูกต้องที่ขอบเขต API** เรากล่าวถึงเรื่องนี้อย่างละเอียดในบท [การตรวจสอบความถูกต้องของคำขอ](./validation.md) แล้ว แนวคิดคือปฏิเสธอินพุตที่ผิดรูปแบบก่อนที่มันจะไปถึงตรรกะทางธุรกิจของคุณ ตรวจความยาวสตริง ข้อจำกัดของรูปแบบ และฟิลด์ที่ต้องมีตรงขอบเขตเลย

**แยกวิเคราะห์เป็นชนิดข้อมูลของโดเมน** ถ้าคุณอ่านบท [การสร้างแบบจำลองโดเมน](./domain-modeling.md) คุณก็รู้เรื่องนี้แล้ว แปลงอินพุตดิบเป็นอ็อบเจกต์โดเมนที่มีชนิดข้อมูลเร็วที่สุดเท่าที่จะทำได้ `UserName` ที่ผ่านคอนสตรักเตอร์ `parse` มาแล้วจะไม่มีทางบรรจุอักขระต้องห้ามได้เลยโดยโครงสร้างของมัน ระบบชนิดข้อมูลทำงานหนักให้เรา

**จำกัดขนาดบอดี้ของคำขอ** ใช้ `RequestBodyLimitLayer` เพื่อปฏิเสธเพย์โหลดที่ใหญ่เกินไปก่อนที่มันจะกินหน่วยความจำ ขีดจำกัด 1 MB เหมาะสมกับ API แบบ JSON ส่วนใหญ่

## การยืนยันตัวตนและความลับ

**แฮชรหัสผ่านด้วย Argon2** เรากล่าวถึงเรื่องนี้ในบท [การยืนยันตัวตนและการอนุญาตสิทธิ์](./authentication.md) แล้ว แต่มันคุ้มที่จะย้ำ: Argon2 คือแนวปฏิบัติที่ดีที่สุดในปัจจุบันสำหรับการแฮชรหัสผ่าน ใช้เกลือสุ่มใหม่สำหรับรหัสผ่านทุกรายการเสมอ

**ใช้ JWT secret ที่ยาวและสุ่ม** JWT secret ของคุณควรเป็นข้อมูลสุ่มอย่างน้อย 48 ตัวอักษร secret ที่สั้นกว่านั้นเสี่ยงต่อการโจมตีแบบเดารหัส (brute-force) และคุณคงไม่อยากค้นพบมันด้วยวิธีที่โหดร้าย เก็บ secret ใน `SecretString` จากครีต `secrecy` และตรวจสอบความยาวของมันตอนเริ่มระบบ

**ตั้งเวลาหมดอายุโทเคนที่สมเหตุสมผล** access token ที่มีอายุสั้น (15 นาทีถึงสองสามชั่วโมง) จำกัดความเสียหายถ้าโทเคนถูกขโมยไป ถ้าคุณต้องการเซสชันที่ยาวกว่านั้น ให้อิมพลีเมนต์กลไก refresh token โดยเก็บ refresh token อย่างปลอดภัยและสามารถเพิกถอนได้

**ห้ามเก็บโทเคนใน localStorage** สำหรับไคลเอนต์บนเบราว์เซอร์ ให้ใช้คุกกี้แบบ `HttpOnly`, `Secure` และ `SameSite=Strict` คุกกี้เหล่านี้ JavaScript เข้าถึงไม่ได้ ซึ่งป้องกันการขโมยโทเคนผ่าน XSS

## CORS

คุณอาจเคยเจอข้อผิดพลาด CORS ในระหว่างการพัฒนา Cross-Origin Resource Sharing เป็นกลไกความปลอดภัยของเบราว์เซอร์ที่ควบคุมว่าโอริจินใดบ้างที่สามารถส่งคำขอไปยัง API ของคุณได้ นโยบาย CORS ที่ตั้งผิดเป็นหนึ่งในปัญหาความปลอดภัยที่พบบ่อยที่สุดที่ผมเห็นในเว็บ API ส่วนหนึ่งเพราะวิธีแก้อันเร็วระหว่างการพัฒนา ("แค่ทำให้มันอนุญาตหมดก็พอ") มีนิสัยเล็ดลอดเข้าสู่ production

```rust
// Production: explicit allow list
CorsLayer::new()
    .allow_origin([
        "https://myapp.com".parse().unwrap(),
    ])
    .allow_methods([Method::GET, Method::POST, Method::PUT, Method::DELETE])
    .allow_headers([header::CONTENT_TYPE, header::AUTHORIZATION])
    .allow_credentials(true)
```

ในระหว่างการพัฒนา `CorsLayer::permissive()` สะดวกดี แต่ต้องมั่นใจว่ามันไม่มีทางไปถึง production นโยบาย CORS แบบอนุญาตทั้งหมดยอมให้โอริจินใดก็ได้ส่งคำขอมาที่ API ของคุณ คำขอเหล่านั้นจะพกเครดิตเชียล (คุกกี้, ส่วนหัวการอนุญาตสิทธิ์) หรือไม่ ขึ้นกับโหมด credentials ของเบราว์เซอร์และการตั้งค่า `allow_credentials` ของคุณ แต่ถึงแม้ไม่มีเครดิตเชียล นโยบายแบบอนุญาตทั้งหมดก็ยังเปิดผิว API ของคุณให้ถูกสำรวจข้ามโอริจิน `CorsLayer::very_permissive()` อันตรายยิ่งกว่าเพราะมันเปิดเครดิตเชียลด้วย จำกัดโอริจินใน production เสมอ

## การป้องกัน CSRF

ถ้า API ของคุณใช้คุกกี้ในการยืนยันตัวตน (ต่างจาก Bearer token) คุณต้องกังวลกับการโจมตีแบบ Cross-Site Request Forgery ครีต `axum-csrf-sync-pattern` อิมพลีเมนต์แพตเทิร์นโทเคนแบบซิงโครไนซ์ (Synchronizer Token Pattern) ที่ OWASP แนะนำ และมันทำงานแบบนี้:

1. เซิร์ฟเวอร์สร้างโทเคน CSRF แบบสุ่มและส่งให้ไคลเอนต์ในส่วนหัวการตอบกลับแบบกำหนดเอง
2. ไคลเอนต์ใส่โทเคนนั้นในส่วนหัวคำขอแบบกำหนดเองของทุกคำขอที่เปลี่ยนสถานะ
3. เซิร์ฟเวอร์ตรวจสอบว่าโทเคนในส่วนหัวคำขอตรงกับโทเคนที่มันออกให้

ทำไมวิธีนี้ถึงได้ผล? เว็บไซต์อันตรายสามารถทำให้เบราว์เซอร์ส่งคุกกี้โดยอัตโนมัติได้ แต่มันไม่สามารถอ่านหรือตั้งส่วนหัวแบบกำหนดเองบนคำขอข้ามโอริจินได้ (สมมติว่านโยบาย CORS ของคุณไม่เปิดเผยมัน)

## การจำกัดอัตราการเรียก

การจำกัดอัตราการเรียกเป็นหนึ่งในสิ่งที่รู้สึกว่าไม่จำเป็นจนกระทั่งมีคนเริ่มถล่มเอนด์พอยต์ล็อกอินของคุณ มันป้องกันการโจมตีแบบเดารหัส การยัดเยียดเครดิตเชียล (credential stuffing) และความพยายามปฏิเสธการให้บริการ ครีต `tower-governor` ให้มิดเดิลแวร์ Tower แก่เราที่จำกัดคำขอโดยอิงกับที่อยู่ IP ของไคลเอนต์:

```rust
use tower_governor::{GovernorConfigBuilder, GovernorLayer};

let governor_config = GovernorConfigBuilder::default()
    .per_second(2)
    .burst_size(10)
    .finish()
    .unwrap();

let app = Router::new()
    .merge(api_routes())
    .layer(GovernorLayer { config: governor_config })
    .with_state(state);
```

สำหรับเอนด์พอยต์การยืนยันตัวตน (ล็อกอิน, รีเซ็ตรหัสผ่าน) ผมแนะนำให้ใช้ข้อจำกัดที่เข้มงวดกว่า เช่น 5 ครั้งต่อนาทีต่อ IP บนเอนด์พอยต์ล็อกอินจะทำให้การโจมตีแบบยัดเยียดเครดิตเชียลทำได้จริงยาก

มีเรื่องหนึ่งที่ต้องจำไว้: ถ้าคุณรันแอปพลิเคชันหลายอินสแตนซ์ใน production การจำกัดอัตราโดยอิง IP ที่ระดับแอปพลิเคชันยังไม่พอเพียงด้วยตัวมันเอง เพราะแต่ละอินสแตนซ์รักษาตัวนับของตัวเอง คุณต้องมองหาเรตลิมิตเตอร์ที่หนุนด้วย Redis หรือจัดการการจำกัดอัตราการเรียกที่ระดับโหลดบาลานเซอร์หรือ API gateway แทน

## ส่วนหัวด้านความปลอดภัย

ส่วนหัวด้านความปลอดภัย HTTP บอกเบราว์เซอร์ให้เปิดใช้กลไกการป้องกันต่างๆ คุณต้องใช้ส่วนหัวใดขึ้นกับว่าแอปพลิเคชันของคุณเสิร์ฟ HTML หรือเป็น API แบบ JSON ล้วน สำหรับแอปพลิเคชันที่เสิร์ฟ HTML ส่วนหัวอย่าง `Content-Security-Policy` และ `X-Frame-Options` เป็นสิ่งจำเป็น สำหรับ API แบบ JSON อย่างเดียว บางส่วนหัวสำคัญน้อยลงเพราะไม่มีบริบทการเรนเดอร์ของเบราว์เซอร์ให้ปกป้อง แต่ผมก็ยังแนะนำให้ตั้งไว้แบบตั้งรับ มันไม่เสียหายอะไรและคุณจะไม่เสียใจภายหลัง

มาลองใช้มันเป็นเลเยอร์มิดเดิลแวร์กัน:

```rust
use axum::http::{HeaderName, HeaderValue};

async fn security_headers(req: Request, next: Next) -> Response {
    let mut response = next.run(req).await;
    let headers = response.headers_mut();

    // Prevent MIME-type sniffing
    headers.insert(
        HeaderName::from_static("x-content-type-options"),
        HeaderValue::from_static("nosniff"),
    );

    // Control framing (prefer CSP frame-ancestors for modern browsers,
    // but X-Frame-Options is still useful for older ones)
    headers.insert(
        HeaderName::from_static("x-frame-options"),
        HeaderValue::from_static("DENY"),
    );

    // Content Security Policy: the primary defense against XSS.
    // Adjust the directives to match your application's needs.
    headers.insert(
        HeaderName::from_static("content-security-policy"),
        HeaderValue::from_static("default-src 'none'; frame-ancestors 'none'"),
    );

    // Enforce HTTPS connections
    headers.insert(
        HeaderName::from_static("strict-transport-security"),
        HeaderValue::from_static("max-age=63072000; includeSubDomains"),
    );

    headers.insert(
        HeaderName::from_static("referrer-policy"),
        HeaderValue::from_static("strict-origin-when-cross-origin"),
    );

    response
}
```

ผมจะพาคุณเดินดูว่ามีอะไรอยู่ในนี้บ้าง และมีอะไรที่ผมจงใจไม่ใส่

`Content-Security-Policy` (CSP) คือแนวป้องกันชั้นเลิศสมัยใหม่ต่อ cross-site scripting CSP ที่เข้มงวดมีประสิทธิภาพเหนือส่วนหัว `X-XSS-Protection` แบบเก่า ซึ่ง OWASP และ MDN ประกาศเลิกใช้แล้ว อย่าตั้ง `X-XSS-Protection` ในบางกรณีขอบมันสามารถสร้างช่องโหว่ขึ้นมาจริงๆ ได้ ใช้ CSP แทน

`Strict-Transport-Security` (HSTS) บอกเบราว์เซอร์ให้เชื่อมต่อผ่าน HTTPS เท่านั้น มันป้องกันการโจมตีแบบลดโปรโตคอล (protocol downgrade) และจำเป็นสำหรับการดีพลอยต์ใน production ทุกรูปแบบที่อยู่หลัง TLS

`X-Frame-Options` ให้การป้องกันคลิกแจ็ก (clickjacking) สำหรับเบราว์เซอร์รุ่นเก่า สำหรับเบราว์เซอร์สมัยใหม่ ไดเรกทีฟ `frame-ancestors` ใน CSP คือกลไกที่นิยมกว่า แต่ทั้งสองสามารถอยู่ร่วมกันได้โดยไม่มีปัญหา

ส่วนหัวเหล่านี้ไม่ใช่สิ่งทดแทนการเขียนโค้ดที่ปลอดภัย แต่มันให้การป้องกันแบบหลายชั้น (defense-in-depth) ด้วยการเปิดใช้การป้องกันฝั่งเบราว์เซอร์ต่อเวกเตอร์การโจมตีทั่วไป มองมันเป็นตาข่ายนิรภัย

## การตรวจสอบดีเพนเดนซี

ดีเพนเดนซีจากบุคคลที่สามสามารถนำช่องโหว่เข้ามาได้ และในโปรเจกต์ Rust คุณจะมีมันมากกว่าที่คาดไว้ รัน `cargo audit` เป็นประจำ (และดีที่สุดคือในไปป์ไลน์ CI ของคุณ) เพื่อตรวจหาช่องโหว่ที่รู้จักในต้นไม้ดีเพนเดนซีของคุณ:

```
cargo install cargo-audit
cargo audit
```

มันตรวจสอบ `Cargo.lock` ของคุณกับฐานข้อมูลคำแนะนำ RustSec (RustSec Advisory Database) และรายงานดีเพนเดนซีใดๆ ที่มีปัญหาความปลอดภัยที่รู้จัก จากประสบการณ์ของผม การรักษาดีเพนเดนซีของคุณให้ทันสมัยเป็นหนึ่งในแนวปฏิบัติด้านความปลอดภัยที่ง่ายและมีประสิทธิภาพที่สุดที่คุณนำมาใช้ได้

## เช็กลิสต์ความปลอดภัย

นี่คือข้อมูลอ้างอิงแบบย่อของแนวปฏิบัติด้านความปลอดภัยที่เรากล่าวถึงตลอดทั้งเล่ม ผมแนะนำให้ไล่เช็กลิสต์นี้ก่อนที่คุณจะดีพลอยต์อะไรก็ตามขึ้น production:

- [ ] SQL ทั้งหมดใช้ควิวรีแบบมีพารามิเตอร์ (ไม่มีการแทรกสตริง)
- [ ] ขนาดบอดี้ของคำขอถูกจำกัดด้วย `RequestBodyLimitLayer`
- [ ] การหมดเวลาของคำขอถูกตั้งค่าด้วย `TimeoutLayer`
- [ ] อินพุตถูกตรวจสอบความถูกต้องที่ขอบเขต API
- [ ] ชนิดข้อมูลโดเมนบังคับใช้ค่าคงที่ (invariant) ผ่านระบบชนิดข้อมูล
- [ ] รหัสผ่านถูกแฮชด้วย Argon2
- [ ] JWT secret ยาวอย่างน้อย 48 ตัวอักษรสุ่ม
- [ ] JWT secret ถูกเก็บใน `SecretString` และไม่ถูกล็อก

- [ ] การจำกัดอัตราการเรียกถูกใช้กับเอนด์พอยต์สาธารณะทั้งหมด

- [ ] CORS ขับเคลื่อนโดยการตั้งค่าตอนรันไทม์ ไม่ใช่บิลด์โพรไฟล์
- [ ] รายละเอียดข้อผิดพลาดภายในไม่ถูกเปิดเผยในการตอบกลับของ API
